## 1. Présentation

*1 minute*

L'architecture en médaillon est un pattern de conception de données qui organise les données dans un data lake en couches progressives de qualité et de raffinement. Popularisée par Databricks, cette architecture est maintenant la référence de l'industrie pour les data lakes modernes, et Microsoft Fabric la supporte et la recommande nativement.

L'idée fondamentale est simple : les données brutes arrivent dans une couche d'entrée, puis sont progressivement nettoyées, validées, et enrichies à travers des couches successives, jusqu'à atteindre une couche finale optimisée pour la consommation analytique et le reporting.

## 2. Décrire l'architecture en médaillon

*Durée : 5 min*

### Vue d'ensemble : Bronze → Silver → Gold

```
Sources                Bronze              Silver              Gold
externes               (Brut)              (Validé)            (Agrégé)
──────────             ──────────          ──────────          ──────────
ERP            →       Fichiers CSV    →   Tables Delta   →   Star Schema
CRM                    JSON bruts          Nettoyées           Dimensions
APIs                   Parquet             Enrichies           Facts
Fichiers               Log files           Dédupliquées        KPIs agrégés
                       Données IoT         Typées              Prêts pour BI
                       
                       OneLake Files/      OneLake Tables/     OneLake Tables/
                       bronze/             silver/             gold/
```

**Analogie** : Imaginez une raffinerie de pétrole. Le pétrole brut (Bronze) arrive directement des puits — il est là, non transformé, mais précieux. Il passe ensuite par des étapes de raffinage (Silver) où les impuretés sont retirées. Finalement, on obtient des produits finis (Gold) — essence, kérosène, plastique — prêts à être consommés.

### La couche Bronze : Les données brutes

La couche Bronze est la **zone d'atterrissage** (landing zone) des données. Elle contient les données exactement telles qu'elles arrivent de leurs sources, sans transformation.

**Caractéristiques :**
- Données brutes, potentiellement sales (duplicates, nulls, formats incorrects)
- Historique complet conservé — on ne supprime jamais de données Bronze
- Format variable : CSV, JSON, Parquet, XML, logs texte
- Stockage dans la zone **Files/** du lakehouse (pas nécessairement des tables Delta)
- Utilisée comme source de vérité pour rejouer les transformations

**Exemples de données Bronze :**
```
Files/bronze/
├── 2019.csv       ← Commandes 2019 (CSV brut)
├── 2020.csv       ← Commandes 2020 (CSV brut)
├── 2021.csv       ← Commandes 2021 (CSV brut)
├── crm_export_20240527.json    ← Export CRM brut
└── iot_readings_2024-05.parquet  ← Données IoT brutes
```

**Ce qu'on fait en Bronze :**
- Ingestion depuis les sources via Copy Activity, Dataflows, ou streaming
- Aucune transformation sur le fond
- Parfois : ajout de métadonnées techniques (nom du fichier source, horodatage d'ingestion)

### La couche Silver : Les données validées et nettoyées

La couche Silver contient des données **nettoyées, validées et enrichies**. C'est la couche de confiance où les données sont de qualité suffisante pour la plupart des usages analytiques.

**Caractéristiques :**
- Tables Delta Lake (avec transactions ACID)
- Données typées correctement (dates, nombres, textes)
- Doublons éliminés
- Valeurs nulles gérées (remplacement ou suppression)
- Schéma imposé et documenté
- Données dénormalisées ou légèrement normalisées
- Accessible aux data analysts et data scientists

**Transformations typiques Bronze → Silver :**
- Inférence et validation des types (string → date, string → float)
- Suppression des lignes dupliquées
- Standardisation des formats (noms de clients, codes pays)
- Ajout de colonnes de traçabilité (source_file, ingestion_timestamp, is_flagged)
- Gestion des valeurs manquantes

### La couche Gold : Les données prêtes pour la consommation

La couche Gold contient des données **hautement transformées**, agrégées, et structurées pour la consommation directe par les outils de reporting et de BI.

**Caractéristiques :**
- Schéma en étoile (star schema) ou flocon (snowflake schema)
- Tables de faits (mesures quantitatives) et de dimensions (contexte)
- KPIs pré-calculés et agrégats
- Optimisée pour les performances des requêtes analytiques
- Accessible directement par Power BI, Tableau, et autres outils BI
- Compatible avec DirectLake (mode de connexion Power BI ultra-rapide)

**Structure typique d'une couche Gold :**
```
Tables/gold/
├── dbo.fact_sales          ← Table de faits : lignes de commandes avec clés étrangères
├── dbo.dim_customer        ← Dimension client
├── dbo.dim_product         ← Dimension produit
├── dbo.dim_date            ← Dimension date (calendrier complet)
└── dbo.kpi_monthly_revenue ← KPI agrégé : CA mensuel pré-calculé
```

### Pourquoi trois couches ?

**Traçabilité** : Les données brutes Bronze permettent de rejouer n'importe quelle transformation depuis le début si une erreur est découverte.

**Séparation des préoccupations** : Chaque couche a un rôle clair. L'ingestion (Bronze), la qualité (Silver), l'analytique (Gold) peuvent évoluer indépendamment.

**Gouvernance** : Les permissions peuvent être définies par couche — les développeurs accèdent à Bronze, les analystes à Silver et Gold, les utilisateurs finaux uniquement à Gold.

**Performance** : La couche Gold, optimisée pour les requêtes, offre d'excellentes performances sans surcharger les couches Bronze et Silver.

## 3. Implémenter une architecture en médaillon dans Fabric

*Durée : 15 min*

### Organisation des dossiers dans le Lakehouse

```
Lakehouse "Sales"
├── Files/
│   └── bronze/
│       ├── 2019.csv
│       ├── 2020.csv
│       └── 2021.csv
└── Tables/
    └── dbo/
        ├── sales_silver        ← Couche Silver (table Delta)
        ├── dimdate_gold        ← Couche Gold - Dimension Date
        ├── dimcustomer_gold    ← Couche Gold - Dimension Client
        ├── dimproduct_gold     ← Couche Gold - Dimension Produit
        └── factsales_gold      ← Couche Gold - Table de Faits
```

### Étape 1 : Ingestion Bronze

Charger les données brutes dans la zone Files/bronze du lakehouse :

```python
# Les fichiers CSV sont uploadés manuellement ou via Copy Activity
# Ils restent en l'état dans Files/bronze/
# Aucune transformation — on capture la donnée telle quelle

# Aperçu des données brutes (sans schéma imposé)
df_raw = spark.read.format("csv") \
    .option("header", "false") \
    .load("Files/bronze/*.csv")

print(f"Lignes brutes ingérées : {df_raw.count()}")
display(df_raw.head(5))
```

### Étape 2 : Transformation Bronze → Silver

```python
from pyspark.sql.types import *
from pyspark.sql.functions import when, lit, col, current_timestamp, input_file_name

# Définir le schéma de la table Silver
orderSchema = StructType([
    StructField("SalesOrderNumber", StringType()),
    StructField("SalesOrderLineNumber", IntegerType()),
    StructField("OrderDate", DateType()),
    StructField("CustomerName", StringType()),
    StructField("Email", StringType()),
    StructField("Item", StringType()),
    StructField("Quantity", IntegerType()),
    StructField("UnitPrice", FloatType()),
    StructField("Tax", FloatType())
])

# Lire tous les fichiers CSV de Bronze avec le schéma imposé
df = spark.read.format("csv") \
    .option("header", "false") \
    .schema(orderSchema) \
    .load("Files/bronze/*.csv")

# Transformations de qualité Silver
df = df \
    .withColumn("FileName", input_file_name()) \
    .withColumn("IsFlagged", when(col("OrderDate") < '2019-08-01', True).otherwise(False)) \
    .withColumn("CreatedTS", current_timestamp()) \
    .withColumn("ModifiedTS", current_timestamp())

# Gérer les noms de clients manquants
df = df.withColumn(
    "CustomerName",
    when(
        col("CustomerName").isNull() | (col("CustomerName") == ""),
        lit("Unknown")
    ).otherwise(col("CustomerName"))
)

display(df.head(10))
```

```python
from delta.tables import *

# Créer la structure de la table Silver
DeltaTable.createIfNotExists(spark) \
    .tableName("sales.dbo.sales_silver") \
    .addColumn("SalesOrderNumber", StringType()) \
    .addColumn("SalesOrderLineNumber", IntegerType()) \
    .addColumn("OrderDate", DateType()) \
    .addColumn("CustomerName", StringType()) \
    .addColumn("Email", StringType()) \
    .addColumn("Item", StringType()) \
    .addColumn("Quantity", IntegerType()) \
    .addColumn("UnitPrice", FloatType()) \
    .addColumn("Tax", FloatType()) \
    .addColumn("FileName", StringType()) \
    .addColumn("IsFlagged", BooleanType()) \
    .addColumn("CreatedTS", DateType()) \
    .addColumn("ModifiedTS", DateType()) \
    .execute()
```

```python
# MERGE (UPSERT) : Insérer les nouvelles lignes, mettre à jour les existantes
deltaTable = DeltaTable.forPath(spark, 'Tables/dbo/sales_silver')

deltaTable.alias('silver') \
    .merge(
        df.alias('updates'),
        '''silver.SalesOrderNumber = updates.SalesOrderNumber 
           AND silver.OrderDate = updates.OrderDate 
           AND silver.CustomerName = updates.CustomerName 
           AND silver.Item = updates.Item'''
    ) \
    .whenMatchedUpdate(set={}) \
    .whenNotMatchedInsert(values={
        "SalesOrderNumber": "updates.SalesOrderNumber",
        "SalesOrderLineNumber": "updates.SalesOrderLineNumber",
        "OrderDate": "updates.OrderDate",
        "CustomerName": "updates.CustomerName",
        "Email": "updates.Email",
        "Item": "updates.Item",
        "Quantity": "updates.Quantity",
        "UnitPrice": "updates.UnitPrice",
        "Tax": "updates.Tax",
        "FileName": "updates.FileName",
        "IsFlagged": "updates.IsFlagged",
        "CreatedTS": "updates.CreatedTS",
        "ModifiedTS": "updates.ModifiedTS"
    }) \
    .execute()

print("Données chargées dans la couche Silver avec succès !")
```

### Étape 3 : Transformation Silver → Gold (Star Schema)

#### Créer la Dimension Date

```python
from pyspark.sql.types import *
from pyspark.sql.functions import col, dayofmonth, month, year, date_format
from delta.tables import *

# Charger les données Silver
df = spark.read.table("Sales.dbo.sales_silver")

# Créer la structure de la table Dimension Date
DeltaTable.createIfNotExists(spark) \
    .tableName("sales.dbo.dimdate_gold") \
    .addColumn("OrderDate", DateType()) \
    .addColumn("Day", IntegerType()) \
    .addColumn("Month", IntegerType()) \
    .addColumn("Year", IntegerType()) \
    .addColumn("mmmyyyy", StringType()) \
    .addColumn("yyyymm", StringType()) \
    .execute()

# Créer le DataFrame pour dimDate_gold
dfdimDate_gold = df.dropDuplicates(["OrderDate"]).select(
    col("OrderDate"),
    dayofmonth("OrderDate").alias("Day"),
    month("OrderDate").alias("Month"),
    year("OrderDate").alias("Year"),
    date_format(col("OrderDate"), "MMM-yyyy").alias("mmmyyyy"),
    date_format(col("OrderDate"), "yyyyMM").alias("yyyymm")
).orderBy("OrderDate")

display(dfdimDate_gold.head(10))
```

```python
# Upsert vers la dimension Date Gold
deltaTable = DeltaTable.forPath(spark, 'Tables/dbo/dimdate_gold')

deltaTable.alias('gold') \
    .merge(
        dfdimDate_gold.alias('updates'),
        'gold.OrderDate = updates.OrderDate'
    ) \
    .whenMatchedUpdate(set={}) \
    .whenNotMatchedInsert(values={
        "OrderDate": "updates.OrderDate",
        "Day": "updates.Day",
        "Month": "updates.Month",
        "Year": "updates.Year",
        "mmmyyyy": "updates.mmmyyyy",
        "yyyymm": "updates.yyyymm"
    }) \
    .execute()

print("Dimension Date Gold chargée !")
```

#### Créer la Dimension Client

```python
from pyspark.sql.functions import monotonically_increasing_id, when, lit

# Créer la structure de la table Dimension Client
DeltaTable.createIfNotExists(spark) \
    .tableName("sales.dbo.dimcustomer_gold") \
    .addColumn("CustomerName", StringType()) \
    .addColumn("Email", StringType()) \
    .addColumn("First", StringType()) \
    .addColumn("Last", StringType()) \
    .addColumn("CustomerID", LongType()) \
    .execute()

# Créer le DataFrame pour dimCustomer_gold
from pyspark.sql.functions import split, col

dfdimCustomer_gold = df.dropDuplicates(["CustomerName", "Email"]).select(
    col("CustomerName"),
    col("Email"),
    split(col("CustomerName"), " ").getItem(0).alias("First"),
    split(col("CustomerName"), " ").getItem(1).alias("Last")
).withColumn("CustomerID", monotonically_increasing_id())

display(dfdimCustomer_gold.head(10))
```

```python
# Charger la dimension Client
deltaTable = DeltaTable.forPath(spark, 'Tables/dbo/dimcustomer_gold')

deltaTable.alias('gold') \
    .merge(
        dfdimCustomer_gold.alias('updates'),
        'gold.CustomerName = updates.CustomerName AND gold.Email = updates.Email'
    ) \
    .whenMatchedUpdate(set={}) \
    .whenNotMatchedInsert(values={
        "CustomerName": "updates.CustomerName",
        "Email": "updates.Email",
        "First": "updates.First",
        "Last": "updates.Last",
        "CustomerID": "updates.CustomerID"
    }) \
    .execute()

print("Dimension Client Gold chargée !")
```

#### Créer la Table de Faits

```python
from pyspark.sql.functions import col, round

# Lire les données Silver et les dimensions Gold
df_silver = spark.read.table("Sales.dbo.sales_silver")
df_dim_customer = spark.read.table("Sales.dbo.dimcustomer_gold")
df_dim_date = spark.read.table("Sales.dbo.dimdate_gold")

# Jointure pour créer la table de faits
df_fact_sales = df_silver \
    .join(df_dim_customer, ["CustomerName", "Email"], "left") \
    .join(df_dim_date, "OrderDate", "left") \
    .select(
        col("SalesOrderNumber"),
        col("SalesOrderLineNumber"),
        col("OrderDate"),
        col("CustomerID"),          # Clé étrangère → dim_customer
        col("yyyymm").alias("OrderMonthKey"),  # Clé étrangère → dim_date
        col("Item"),
        col("Quantity"),
        col("UnitPrice"),
        col("Tax"),
        round(col("Quantity") * (col("UnitPrice") + col("Tax")), 2).alias("TotalAmount")
    )

# Sauvegarder la table de faits Gold
df_fact_sales.write \
    .format("delta") \
    .mode("overwrite") \
    .saveAsTable("Sales.dbo.factsales_gold")

print(f"Table de faits Gold créée : {df_fact_sales.count()} lignes")
display(df_fact_sales.limit(5))
```

### Analyser la couche Gold avec SQL

```sql
%%sql

-- KPI : Chiffre d'affaires mensuel
SELECT 
    OrderMonthKey,
    SUM(TotalAmount) AS MonthlyRevenue,
    COUNT(DISTINCT SalesOrderNumber) AS NumOrders,
    COUNT(DISTINCT CustomerID) AS NumCustomers,
    AVG(TotalAmount) AS AvgOrderValue

```

```sql
%%sql

-- Top 10 clients par CA
SELECT 
    c.CustomerName,
    c.Email,
    SUM(f.TotalAmount) AS TotalRevenue,
    COUNT(DISTINCT f.SalesOrderNumber) AS NumOrders
FROM dbo.factsales_gold f
JOIN dbo.dimcustomer_gold c ON f.CustomerID = c.CustomerID
GROUP BY c.CustomerName, c.Email
ORDER BY TotalRevenue DESC
LIMIT 10;
```

```sql
%%sql

-- Analyse par période (Year/Month) avec la dimension Date
SELECT 
    d.Year,
    d.Month,
    d.mmmyyyy,
    SUM(f.TotalAmount) AS Revenue,
    SUM(f.Quantity) AS TotalUnits

```

### DirectLake dans Power BI

La couche Gold du lakehouse Fabric est parfaitement intégrée avec Power BI via le mode **DirectLake** — un mode de connexion révolutionnaire qui combine la vitesse du mode Import avec la fraîcheur des données du mode DirectQuery.

**Avantages de DirectLake :**
- Lecture directe depuis OneLake (pas de copie dans le moteur Power BI)
- Performances équivalentes au mode Import pour la plupart des requêtes
- Données toujours à jour (pas de refresh nécessaire pour les petits changements)

**Configurer un modèle sémantique avec DirectLake :**

## 5. Considérations relatives à la sécurité et à la gouvernance

*Durée : 5 min*

### Sécurité par couche

L'architecture en médaillon facilite la mise en place d'une sécurité granulaire basée sur les couches :

| Couche | Accès recommandé | Outils Fabric |
|--------|-----------------|---------------|
| **Bronze** | Data Engineers uniquement | Permissions Workspace (Admin, Member) |
| **Silver** | Data Engineers + Data Scientists | Permissions Workspace + Row-Level Security |
| **Gold** | Tous les utilisateurs analytiques | Workspace Reader + permissions sur le modèle sémantique |

**Configurer les permissions dans Fabric :**
```
Workspace → Settings → Permissions
├── Admin : Data Engineers (full access)
├── Member : Data Scientists (can create items, read all data)
├── Contributor : Data Analysts (can publish reports)
└── Viewer : Business Users (read-only access to Gold)
```

### Gouvernance avec Microsoft Purview

Microsoft Fabric s'intègre nativement avec **Microsoft Purview** pour :
- **Catalogage des données** : Documenter chaque table (Bronze, Silver, Gold) avec des descriptions, propriétaires, et tags
- **Lignage des données** : Tracer automatiquement comment les données circulent de Bronze → Silver → Gold → Power BI
- **Classification des données** : Identifier et étiqueter les données sensibles (PII, confidentielles) dans chaque couche
- **Politiques d'accès** : Définir des règles d'accès centralisées appliquées à toutes les couches

**Lignage automatique :**
Dans le lakehouse Fabric, cliquer sur **View lineage** pour visualiser automatiquement la chaîne complète :
```
CSV Files (Bronze) → sales_silver (Silver) → factsales_gold (Gold) → Power BI Report
```

### Best Practices de nommage et organisation

**Nommage des tables :**
```
# Convention recommandée
bronze_<source>_<entity>     → bronze_erp_orders (si stocké en table)
silver_<entity>              → sales_silver (ou simplement sales_silver)
dim_<dimension>_gold         → dimcustomer_gold, dimproduct_gold, dimdate_gold
fact_<sujet>_gold            → factsales_gold, factinventory_gold
```

**Organisation des schémas :**
```
Lakehouse "Sales"
└── dbo (schéma par défaut)
    ├── sales_silver
    ├── dimdate_gold
    ├── dimcustomer_gold
    └── factsales_gold

// Alternative avec plusieurs schémas
Lakehouse "Sales"
├── bronze (schéma)
│   └── raw_orders
├── silver (schéma)
│   └── sales
└── gold (schéma)
    ├── dimdate
    ├── dimcustomer
    └── factsales
```

**Best Practices générales :**
1. **Immuabilité du Bronze** : Ne jamais modifier les données Bronze — c'est la source de vérité originale
2. **Idempotence** : Les transformations Silver et Gold doivent être re-jouables sans dupliquer les données (utiliser MERGE/UPSERT)
3. **Séparation des notebooks** : Un notebook par couche (Bronze→Silver, Silver→Gold) pour faciliter le débogage
4. **Documentation** : Documenter chaque table avec des descriptions dans le lakehouse et dans Purview
5. **Tests de qualité** : Ajouter des assertions de qualité dans les transformations Silver (nulls, ranges, unicité)

## 7. Évaluation des connaissances

*5 minutes*

**Question 1** : Dans l'architecture en médaillon, quelle couche contient les données exactement telles qu'elles arrivent de leurs sources, sans transformation ?

- A) Gold
- B) Silver
- C) Bronze
- D) Platinum

> **Réponse : C** — La couche **Bronze** est la zone d'atterrissage (landing zone). Elle contient les données brutes, non transformées, dans leur format original. C'est la source de vérité qui permet de rejouer les transformations si nécessaire.

---

**Question 2** : Pourquoi utilise-t-on un MERGE (UPSERT) plutôt qu'un simple INSERT pour charger la couche Silver ?

- A) Le MERGE est plus rapide que l'INSERT pour les grandes quantités de données
- B) Le MERGE permet d'insérer les nouvelles lignes tout en évitant les doublons, rendant le pipeline idempotent (rejouable sans dupliquer les données)
- C) L'INSERT n'est pas supporté dans les tables Delta Lake de Fabric
- D) Le MERGE compresse automatiquement les données lors de l'insertion

> **Réponse : B** — L'idempotence est essentielle dans les pipelines de données. Si le pipeline est re-exécuté (suite à une erreur ou manuellement), le MERGE garantit que les données existantes ne sont pas dupliquées — seules les nouvelles lignes sont insérées.

---

**Question 3** : Qu'est-ce qu'un star schema (schéma en étoile) dans la couche Gold ?

- A) Une structure où chaque table Gold est liée aux tables Silver correspondantes
- B) Une structure composée d'une table de faits centrale reliée à plusieurs tables de dimensions
- C) Un schéma graphique de la lignée des données de Bronze à Gold
- D) Une technique d'indexation pour accélérer les requêtes dans la couche Gold

> **Réponse : B** — Le star schema est un modèle dimensionnel composé d'une **table de faits** (mesures quantitatives : ventes, quantités, revenus) au centre, entourée de **tables de dimensions** (contexte : client, produit, date). C'est le modèle optimisé pour le reporting analytique.

**Question 4** : Quel mode de connexion Power BI permet de lire directement depuis les tables Delta Lake du lakehouse Fabric sans copier les données dans le moteur Power BI ?

- A) Import mode
- B) DirectQuery
- C) DirectLake
- D) Hybrid Tables

> **Réponse : C** — **DirectLake** est un mode de connexion propre à Microsoft Fabric qui lit directement depuis les fichiers Parquet sur OneLake. Il combine les avantages du mode Import (performance) et du mode DirectQuery (fraîcheur) sans les inconvénients de chacun.

**Question 5** : Quelle est la bonne pratique concernant les données de la couche Bronze ?

- A) Les supprimer après 30 jours pour économiser le stockage
- B) Les transformer directement en place avec des UPDATE pour gagner de l'espace
- C) Les conserver intactes et immuables car elles sont la source de vérité originale permettant de rejouer les transformations
- D) Les compresser avec OPTIMIZE et VACUUM dès qu'elles ont été traitées en Silver

> **Réponse : C** — La couche Bronze doit être **immuable** (jamais modifiée). En conservant les données brutes, vous pouvez toujours rejouer les transformations Silver et Gold depuis zéro si une erreur de logique est découverte, même des mois plus tard.

## 8. Résumé

*2 minutes*

Dans ce module, vous avez appris à implémenter l'architecture en médaillon dans Microsoft Fabric :

- L'architecture en médaillon organise les données en 3 couches progressives : **Bronze → Silver → Gold**
- **Bronze** = données brutes, immuables, zone d'atterrissage
- **Silver** = données nettoyées, validées, enrichies, dans des tables Delta
- **Gold** = données agrégées, star schema, optimisées pour la BI
- Les transformations utilisent **PySpark + Delta Lake** (DeltaTable.createIfNotExists, MERGE)
- **DirectLake** dans Power BI permet de consommer directement la couche Gold
- La gouvernance par couche définit qui peut accéder à quoi (Bronze = Engineers, Gold = tous)
- **Microsoft Purview** assure le catalogage, la lignée, et la classification des données

### Points clés pour l'examen DP-700

1. Bronze = brut + immuable / Silver = propre + Delta / Gold = agrégé + star schema
2. MERGE/UPSERT = idempotence (rejouable sans doublons)
3. DirectLake = connexion Power BI directe à OneLake (pas de copie)
4. Sécurité par couche : Workspace permissions + RLS
5. `DeltaTable.createIfNotExists` = créer une table Delta vide avec schéma
6. Lignée automatique visible dans le lakehouse : View lineage
