## 1. Présentation

*1 minute*

Les tables d'un lakehouse Microsoft Fabric sont toutes basées sur le format **Delta Lake** — un projet open source initialement développé par Databricks, maintenant partie de la Linux Foundation et intégré nativement dans Microsoft Fabric, Azure Databricks, et Apache Spark.

Delta Lake résout les problèmes fondamentaux que rencontrent les data engineers lorsqu'ils travaillent avec des données à grande échelle : manque de transactions atomiques, absence de gestion des schémas, performances dégradées avec de nombreux petits fichiers, et absence de cohérence pour les lectures concurrentes.

Dans ce module, vous allez apprendre à exploiter toutes les fonctionnalités avancées de Delta Lake dans Fabric.

## 2. Comprendre Delta Lake

*3 minutes*

### Le problème que Delta Lake résout

Les data lakes traditionnels basés sur des fichiers Parquet ou CSV ont plusieurs limitations critiques :

**Pas de transactions atomiques** : Si un job Spark échoue pendant qu'il écrit des données, vous pouvez vous retrouver avec un état partiel — certains fichiers écrits, d'autres manquants. Récupérer de cet état nécessite une intervention manuelle complexe.

**Pas de gestion des schémas** : Rien n'empêche un job d'écrire des données avec un schéma différent, corrompant silencieusement les données en aval.

**Pas de cohérence pour les lectures concurrentes** : Pendant qu'un job écrit, un autre job lisant les mêmes données peut voir un état intermédiaire incohérent.

**Performance dégradée avec de nombreux petits fichiers** : Les opérations de streaming ou d'ingestion fréquente créent des centaines de petits fichiers Parquet, dégradant les performances des requêtes analytiques.

### Comment Delta Lake résout ces problèmes

Delta Lake ajoute une couche transactionnelle au-dessus du stockage de fichiers Parquet. Chaque opération d'écriture est enregistrée dans un **transaction log** (le dossier `_delta_log`), qui contient l'historique complet de toutes les modifications de la table.

**Structure d'une table Delta Lake :**
```
tables/sales/
├── _delta_log/                    # Journal de transactions
│   ├── 00000000000000000000.json  # Commit 0 : création initiale
│   ├── 00000000000000000001.json  # Commit 1 : première insertion
│   ├── 00000000000000000002.json  # Commit 2 : mise à jour
│   └── 00000000000000000010.checkpoint.parquet  # Snapshot compact
├── part-00000-xxxx.snappy.parquet  # Données
├── part-00001-xxxx.snappy.parquet  # Données
└── part-00002-xxxx.snappy.parquet  # Données
```

### Les propriétés ACID de Delta Lake

**A — Atomicité** : Une opération (INSERT, UPDATE, DELETE) réussit entièrement ou échoue entièrement. Jamais d'état intermédiaire visible.

**C — Cohérence** : La table est toujours dans un état valide. Les contraintes de schéma sont respectées.

**I — Isolation** : Les lectures concurrentes voient toujours un état cohérent, même pendant une écriture en cours. Delta Lake utilise le protocole MVCC (Multi-Version Concurrency Control).

**D — Durabilité** : Une fois qu'un commit est confirmé, les données sont persistées de façon durable sur OneLake (ADLS Gen2).

### Comparaison Delta Lake vs Parquet classique

| Fonctionnalité | Parquet classique | Delta Lake |
|----------------|-------------------|------------|
| Transactions ACID | Non | Oui |
| Time Travel | Non | Oui (historique complet) |
| Évolution de schéma | Manuelle | Automatique ou contrôlée |
| MERGE (upsert) | Non natif | Oui, natif |
| UPDATE / DELETE | Non | Oui |
| Streaming + Batch | Séparés | Unifié |
| Compaction automatique | Non | Oui (OPTIMIZE) |
| Statistiques par fichier | Non | Oui (data skipping) |
| Cohérence lecture/écriture | Non garantie | Garantie |

## 3. Créer des tables Delta

*5 minutes*

### Méthode 1 : Écriture directe avec saveAsTable

La façon la plus simple de créer une table Delta dans Fabric :

```python
from pyspark.sql.types import *

# Définir le schéma
schema = StructType([
    StructField("ProductID", IntegerType(), True),
    StructField("ProductName", StringType(), True),
    StructField("Category", StringType(), True),
    StructField("ListPrice", DoubleType(), True)
])

# Lire les données source
df = spark.read.format("csv") \
    .option("header", "true") \
    .schema(schema) \
    .load("Files/products/products.csv")

# Sauvegarder comme table Delta (gérée par le lakehouse)
df.write.format("delta").saveAsTable("dbo.products_table")

print("Table Delta 'products_table' créée !")
```

### Méthode 2 : Création avec DeltaTable API

```python
from delta.tables import DeltaTable
from pyspark.sql.types import *

# Créer une table vide avec un schéma défini
DeltaTable.createIfNotExists(spark) \
    .tableName("dbo.sales_orders") \
    .addColumn("OrderID", IntegerType()) \
    .addColumn("CustomerID", IntegerType()) \
    .addColumn("OrderDate", DateType()) \
    .addColumn("TotalAmount", DoubleType()) \
    .addColumn("Status", StringType()) \
    .execute()

print("Table Delta vide créée avec succès !")
```

### Méthode 3 : Création avec SQL

```sql
%%sql

-- Créer une table Delta avec SQL DDL
CREATE TABLE IF NOT EXISTS dbo.customers (
    CustomerID INT,
    CustomerName STRING,
    Email STRING,
    Country STRING,
    CreatedDate DATE
)
USING DELTA
COMMENT 'Table des clients';

-- Insérer des données
INSERT INTO dbo.customers VALUES
    (1, 'Alice Martin', 'alice@contoso.com', 'France', '2024-01-15'),
    (2, 'Bob Dupont', 'bob@contoso.com', 'Belgique', '2024-02-20'),
    (3, 'Carol Smith', 'carol@fabrikam.com', 'UK', '2024-03-10');
```

### Méthode 4 : Table externe vs Table gérée

```python
# Table GÉRÉE (managed) - Fabric contrôle les fichiers
# Les fichiers sont dans Tables/ du lakehouse
df.write.format("delta").saveAsTable("dbo.products_managed")

# Table EXTERNE - vous contrôlez l'emplacement des fichiers
df.write.format("delta").save("Files/external/products")

# Pour créer une table externe pointant vers un emplacement existant :
spark.sql("""
    CREATE TABLE dbo.products_external 
    USING DELTA 
    LOCATION 'Files/external/products'
""")
```

> **Important** : Pour les tables gérées dans Fabric, `DROP TABLE` supprime également les fichiers. Pour les tables externes, `DROP TABLE` supprime seulement les métadonnées, pas les fichiers.

### Opérations DML sur une table Delta

```python
# UPDATE : Modifier des données existantes
spark.sql("""
    UPDATE dbo.products_table
    SET ListPrice = ListPrice * 0.9
    WHERE Category = 'Mountain Bikes'
""")

# DELETE : Supprimer des données
spark.sql("""
    DELETE FROM dbo.products_table
    WHERE ListPrice > 5000
""")

# MERGE (UPSERT) : Insérer ou mettre à jour
spark.sql("""
    MERGE INTO dbo.products_table AS target
    USING new_products AS source
    ON target.ProductID = source.ProductID
    WHEN MATCHED THEN
        UPDATE SET target.ListPrice = source.ListPrice
    WHEN NOT MATCHED THEN
        INSERT (ProductID, ProductName, Category, ListPrice)
        VALUES (source.ProductID, source.ProductName, source.Category, source.ListPrice)
""")
```

## 4. Optimiser les tables Delta

*5 minutes*

### Le problème des petits fichiers

Dans un data lake, les opérations d'ingestion fréquentes (streaming, ingestion incrémentale toutes les heures) créent de nombreux petits fichiers. Requêter 10 000 fichiers de 1 MB est beaucoup plus lent que requêter 10 fichiers de 1 GB, même si le volume total est identique — car Spark doit ouvrir chaque fichier séparément.

**Symptômes du problème :**
- Requêtes de plus en plus lentes avec le temps
- Beaucoup de petits fichiers (< 128 MB) dans le dossier de la table
- Temps de planification des jobs Spark élevé

### OPTIMIZE : Compacter les petits fichiers

La commande `OPTIMIZE` fusionne les petits fichiers en fichiers plus grands (cible : 1 GB par fichier).

```sql
%%sql

-- Compacter tous les fichiers de la table
OPTIMIZE dbo.products_table;

-- Résultat affiché :
-- numFilesAdded: 1
-- numFilesRemoved: 47
-- filesAdded: {avg: 892.5 MB, ...}
-- filesRemoved: {avg: 19.0 MB, ...}
```

```python
# Avec PySpark
from delta.tables import DeltaTable

deltaTable = DeltaTable.forName(spark, "dbo.products_table")
deltaTable.optimize().executeCompaction()
```

### Z-ORDER : Optimisation de la localité des données

Z-ORDER est une technique d'index multi-dimensionnel qui co-localise les données similaires dans les mêmes fichiers. Cela accélère dramatiquement les requêtes filtrées sur les colonnes indexées.

```sql
%%sql

-- Optimiser ET créer un index Z-ORDER sur Category et ListPrice
OPTIMIZE dbo.products_table
ZORDER BY (Category, ListPrice);
```

**Quand utiliser Z-ORDER :**
- Sur les colonnes les plus fréquemment utilisées dans les clauses WHERE
- Sur des colonnes à faible cardinalité ou pour des plages de valeurs (dates, prix)
- Après l'ingestion de grandes quantités de données

**Exemple d'impact :**
```
# AVANT ZORDER : requête scanne 10 GB de données
SELECT * FROM products WHERE Category = 'Mountain Bikes' AND ListPrice < 3000

# APRÈS ZORDER sur (Category, ListPrice) : scanne ~0.5 GB (data skipping)
# Spark peut ignorer 95% des fichiers grâce aux statistiques par fichier
```

### VACUUM : Nettoyer les anciennes versions

Delta Lake conserve les anciens fichiers de données pour permettre le Time Travel (voir section suivante). Ces fichiers s'accumulent et consomment du stockage. `VACUUM` supprime les fichiers anciens qui ne sont plus référencés.

```sql
%%sql

-- Supprimer les fichiers anciens de plus de 7 jours (défaut)
VACUUM dbo.products_table;

-- Supprimer les fichiers de plus de 24 heures (période de rétention personnalisée)
VACUUM dbo.products_table RETAIN 24 HOURS;

-- ATTENTION : Après VACUUM, le Time Travel ne peut plus revenir 
-- aux versions antérieures à la période de rétention !
```

> **Bonne pratique** : Conserver au moins 7 jours de rétention (défaut). Ne jamais descendre en dessous de 24 heures en production — des jobs longs pourraient référencer des fichiers qu'un VACUUM trop agressif aurait supprimés.

### Statistiques et Data Skipping

Delta Lake maintient automatiquement des statistiques sur chaque fichier (min/max de chaque colonne). Ces statistiques permettent à Spark de sauter (*skip*) des fichiers entiers lors de requêtes filtrées, sans même les ouvrir.

```python
# Voir les statistiques d'une table Delta
from delta.tables import DeltaTable

deltaTable = DeltaTable.forName(spark, "dbo.products_table")
detail = deltaTable.detail()
display(detail.select("numFiles", "sizeInBytes", "numRows"))

# Voir les fichiers avec leurs statistiques
df_files = spark.sql("""
    DESCRIBE DETAIL dbo.products_table
""")
display(df_files)
```

## 5. Utiliser des tables Delta dans Spark — Time Travel

*5 minutes*

### Qu'est-ce que le Time Travel ?

Delta Lake enregistre chaque opération (INSERT, UPDATE, DELETE, MERGE) dans son journal de transactions. Cette fonctionnalité permet de **"voyager dans le temps"** et d'interroger la table telle qu'elle était à n'importe quel moment dans le passé.

**Cas d'usage du Time Travel :**
- **Audit** : Voir qui a modifié quelles données et quand
- **Rollback** : Restaurer une version précédente après une erreur
- **Reproduction** : Reproduire les résultats d'un rapport généré à une date passée
- **Débogage** : Comparer l'état avant/après une transformation

### Voir l'historique des transactions

```sql
%%sql

-- Voir toutes les transactions de la table
DESCRIBE HISTORY dbo.products_table;
```

```python
# Avec PySpark
from delta.tables import DeltaTable

deltaTable = DeltaTable.forName(spark, "dbo.products_table")
history = deltaTable.history()
display(history.select("version", "timestamp", "operation", "operationParameters", "userName"))
```

Résultat typique :
| version | timestamp | operation | operationParameters |
|---------|-----------|-----------|---------------------|
| 2 | 2024-05-27 10:30:00 | UPDATE | `{"predicate": "Category = 'Mountain Bikes'"}` |
| 1 | 2024-05-27 09:15:00 | WRITE | `{"mode": "Append", "partitionBy": "[]"}` |
| 0 | 2024-05-27 08:00:00 | CREATE TABLE | `{}` |

### Interroger une version historique

```sql
%%sql

-- Interroger la version 0 (état initial)
SELECT * FROM dbo.products_table VERSION AS OF 0;

-- Interroger à une date/heure précise
SELECT * FROM dbo.products_table TIMESTAMP AS OF '2024-05-27T08:00:00';
```

```python
# PySpark : comparer version 0 (avant update) et version actuelle
df_original = spark.read.format("delta") \
    .option("versionAsOf", 0) \
    .table("dbo.products_table")

df_current = spark.table("dbo.products_table")

# Comparer les prix des Mountain Bikes
df_original.filter("Category = 'Mountain Bikes'") \
    .select("ProductName", "ListPrice") \
    .join(
        df_current.filter("Category = 'Mountain Bikes'") \
            .select("ProductName", "ListPrice"),
        "ProductName",
        "inner"
    ) \
    .withColumnRenamed("ListPrice", "OriginalPrice") \
    .show()
```

```sql
%%sql

-- Comparer prix original et mis à jour pour les Mountain Bikes
SELECT
    o.ProductName,
    o.ListPrice AS OriginalPrice,
    u.ListPrice AS UpdatedPrice,
    ROUND((u.ListPrice - o.ListPrice) / o.ListPrice * 100, 2) AS PctChange
FROM dbo.products_table VERSION AS OF 0 o
JOIN dbo.products_table u ON o.ProductID = u.ProductID
WHERE o.Category = 'Mountain Bikes'
ORDER BY o.ProductName;
```

### Restaurer une version précédente

```python
from delta.tables import DeltaTable

# Restaurer la table à la version 0
deltaTable = DeltaTable.forName(spark, "dbo.products_table")
deltaTable.restoreToVersion(0)

# OU restaurer à un timestamp
deltaTable.restoreToTimestamp("2024-05-27T08:00:00")

print("Table restaurée à la version 0 !")
```

## 6. Utiliser des tables Delta avec des données de streaming

*5 minutes*

### Delta Lake comme destination de streaming

Delta Lake est compatible avec Spark Structured Streaming. Vous pouvez écrire des données en continu dans une table Delta, qui devient ainsi une **sink de streaming**.

```python
from notebookutils import mssparkutils
from pyspark.sql.types import *
from pyspark.sql.functions import *

# Créer un dossier source pour simuler du streaming
inputPath = 'Files/streaming-data/'
mssparkutils.fs.mkdirs(inputPath)

# Définir le schéma du stream IoT
jsonSchema = StructType([
    StructField("device", StringType(), False),
    StructField("temperature", DoubleType(), False),
    StructField("timestamp", StringType(), False)
])

# Créer le stream de lecture
iotstream = spark.readStream \
    .schema(jsonSchema) \
    .option("maxFilesPerTrigger", 1) \
    .json(inputPath)

# Écrire des données IoT simulées
device_data = '''{"device":"Sensor-A","temperature":23.5,"timestamp":"2024-05-27T10:00:00"}
{"device":"Sensor-B","temperature":31.2,"timestamp":"2024-05-27T10:00:05"}
{"device":"Sensor-A","temperature":24.1,"timestamp":"2024-05-27T10:00:10"}
{"device":"Sensor-C","temperature":19.8,"timestamp":"2024-05-27T10:00:15"}'''

mssparkutils.fs.put(inputPath + "batch1.json", device_data, True)
print("Données IoT créées !")
```

```python
# Écrire le stream vers une table Delta
checkpointPath = 'Files/checkpoints/iot'
delta_stream_path = 'Tables/dbo/iot_sensor_data'

deltastream = iotstream.writeStream \
    .format("delta") \
    .option("checkpointLocation", checkpointPath) \
    .start(delta_stream_path)

print("Streaming vers Delta Lake démarré...")
```

```sql
%%sql

-- Interroger la table Delta pendant que le streaming est actif
SELECT device, AVG(temperature) AS AvgTemp, COUNT(*) AS ReadingCount
FROM dbo.iot_sensor_data
GROUP BY device
ORDER BY device;
```

```python
# Arrêter le stream quand terminé
deltastream.stop()
print("Stream arrêté.")
```

### Delta Lake comme source de streaming

Une table Delta peut aussi être une **source** pour un pipeline de streaming — elle lit automatiquement les nouveaux commits :

```python
# Lire en continu les nouvelles données insérées dans une table Delta
stream_from_delta = spark.readStream \
    .format("delta") \
    .table("dbo.iot_sensor_data")

# Traiter et écrire vers une autre destination
processed_stream = stream_from_delta \
    .withColumn("alert", col("temperature") > 30)

processed_stream.writeStream \
    .format("delta") \
    .option("checkpointLocation", "Files/checkpoints/alerts") \
    .outputMode("append") \
    .start("Tables/dbo/temperature_alerts")
```

## 8. Évaluation des connaissances

*3 minutes*

**Question 1** : Qu'est-ce que le `_delta_log` dans une table Delta Lake ?

- A) Un fichier de log des erreurs Spark pour les tables Delta
- B) Le journal de transactions contenant l'historique de toutes les modifications de la table
- C) Un index columnar accélérant les requêtes de type GROUP BY
- D) Une sauvegarde compressée des dernières données insérées

> **Réponse : B** — Le `_delta_log` est le journal de transactions Delta Lake. Il enregistre chaque commit (INSERT, UPDATE, DELETE) sous forme de fichiers JSON, permettant les propriétés ACID et le Time Travel.

---

**Question 2** : Quelle est la différence entre `OPTIMIZE` et `VACUUM` dans Delta Lake ?

- A) `OPTIMIZE` supprime les doublons, `VACUUM` compresse les données
- B) `OPTIMIZE` compacte les petits fichiers en plus grands, `VACUUM` supprime les anciens fichiers devenus inutiles
- C) `OPTIMIZE` crée des index, `VACUUM` vide le cache Spark
- D) Ce sont deux syntaxes différentes pour la même opération

> **Réponse : B** — `OPTIMIZE` fusionne les petits fichiers Parquet en fichiers plus grands pour améliorer les performances. `VACUUM` supprime les anciens fichiers de données qui ne sont plus référencés par aucune version du journal de transactions.

---

**Question 3** : Comment interroger une table Delta Lake à une version historique spécifique ?

- A) `SELECT * FROM table HISTORY VERSION 0`
- B) `SELECT * FROM table WHERE _version = 0`
- C) `SELECT * FROM table VERSION AS OF 0`
- D) `RESTORE TABLE table TO VERSION 0`

> **Réponse : C** — La syntaxe SQL pour le Time Travel est `VERSION AS OF <numéro>` ou `TIMESTAMP AS OF '<datetime>'`. `RESTORE` est une commande différente qui modifie la table courante.

---

**Question 4** : Quel est le rôle de `Z-ORDER BY` dans la commande `OPTIMIZE` ?

- A) Trier les données par ordre alphabétique dans les fichiers Parquet
- B) Co-localiser les données similaires dans les mêmes fichiers pour accélérer les requêtes filtrées (data skipping)
- C) Créer une partition physique par valeur unique de la colonne
- D) Compresser les données avec l'algorithme Zstandard

> **Réponse : B** — Z-ORDER est une technique d'indexation multi-dimensionnelle qui organise les données pour que les valeurs similaires se retrouvent dans les mêmes fichiers. Cela permet à Spark d'ignorer (skip) des fichiers entiers lors de requêtes filtrées sur les colonnes indexées.

---

**Question 5** : Pourquoi faut-il faire attention avec `VACUUM RETAIN 0 HOURS` ?

- A) Cela supprime toute la table, y compris les métadonnées
- B) Cela rend le Time Travel impossible car tous les fichiers historiques sont supprimés immédiatement
- C) Cela génère une erreur car la rétention minimale est de 1 heure
- D) Cela vide uniquement le cache Spark, pas les fichiers OneLake

> **Réponse : B** — VACUUM avec une rétention de 0 heures supprime tous les fichiers non référencés par la version actuelle, rendant impossible tout Time Travel vers une version antérieure. Cela peut aussi causer des erreurs si des jobs longs lisent encore des fichiers référencés par des versions précédentes.

## 9. Résumé

*1 minute*

Dans ce module, vous avez appris à utiliser Delta Lake dans Microsoft Fabric :

- **Delta Lake** résout les problèmes des data lakes traditionnels avec les transactions ACID
- **`_delta_log`** est le journal de transactions enregistrant chaque modification
- **CREATE TABLE / saveAsTable** crée des tables Delta dans le lakehouse
- **UPDATE, DELETE, MERGE** sont supportés nativement sur les tables Delta
- **OPTIMIZE** compacte les petits fichiers pour améliorer les performances
- **Z-ORDER** co-localise les données similaires pour accélérer les requêtes filtrées
- **VACUUM** nettoie les anciens fichiers (attention à la rétention minimale)
- **Time Travel** permet d'interroger des versions historiques de la table
- **Streaming** : Delta Lake peut être source ET sink de Spark Structured Streaming

### Points clés pour l'examen DP-700

1. Toutes les tables d'un lakehouse Fabric sont **Delta Lake** par défaut
2. `_delta_log` = journal de transactions = base du Time Travel
3. `OPTIMIZE ZORDER BY` améliore les requêtes filtrées par **data skipping**
4. `VACUUM` supprime les fichiers historiques — irréversible pour le Time Travel
5. `VERSION AS OF` / `TIMESTAMP AS OF` pour interroger des versions passées
6. Delta Lake supporte le **streaming unifié** (batch + streaming sur la même table)
