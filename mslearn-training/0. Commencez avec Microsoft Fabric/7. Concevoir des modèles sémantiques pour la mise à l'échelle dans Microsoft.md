- Concevoir des éléments dynamiques pour étendre les calculs dans un modèle sémantique.

## Présentation
Effectué
100 XP
3 minutes

Les rapports Power BI ne peuvent être aussi performants que le modèle sémantique qui les alimente. Un modèle sémantique mal conçu — avec trop de données importées, des relations ambiguës, ou des calculs DAX répétitifs — engendre des rapports lents, des actualisations longues et une maintenance complexe.

La conception de **modèles sémantiques évolutifs** consiste à faire les bons choix architecturaux dès le départ : choisir le bon mode de stockage selon la source de données et les exigences de fraîcheur, configurer des relations claires et performantes, et utiliser les fonctionnalités DAX avancées pour des calculs réutilisables et maintenables.

Ce module couvre les patterns et pratiques qui permettent aux modèles sémantiques de passer de projets pilotes à des solutions d'entreprise robustes.

## Choisir le meilleur mode de stockage
Effectué
100 XP
6 minutes

Lorsque vous concevez un modèle sémantique évolutif, la sélection du mode de stockage approprié est cruciale. Selon votre source de données, quatre options s'offrent à vous.

### Mode Importation

**Importation** implique l'importation et le stockage de données dans Power BI, offrant la meilleure flexibilité et les performances les plus rapides. Toutefois, il nécessite des actualisations périodiques pour maintenir les données à jour.

**Quand utiliser le mode Import :**
- Données qui changent périodiquement (pas besoin de temps réel)
- Sources de données lentes (amélioration des performances)
- Transformations Power Query complexes
- Données de petite à moyenne taille (< 10 Go par défaut, extensible)

**Bonnes pratiques pour l'Import :**
- Connectez à des vues plutôt qu'à des tables lors de l'utilisation de bases de données relationnelles.
- Incluez uniquement les tables, lignes et colonnes nécessaires.
- Configurez un partitionnement et une actualisation incrémentielle pour éviter de recharger toutes les données.
- Utilisez les types de données appropriés (entier pour les ID, décimal pour les montants).
- Assurez le *Query Folding* pour réduire le travail dans le moteur Power BI.

### Mode DirectQuery

Le mode **DirectQuery** vous permet d'interroger des données directement à partir de la source sans les stocker dans Power BI, idéal pour gérer de grands volumes de données et des livraisons de données en quasi-temps réel.

**Quand utiliser DirectQuery :**
- Données volumineuses qui ne peuvent pas être importées
- Exigences de fraîcheur des données strictes (quasi-temps réel)
- Sources de données qui appliquent leur propre sécurité au niveau des lignes
- Règles de gouvernance qui interdisent la copie des données

**Bonnes pratiques pour DirectQuery :**
- Évitez les calculs complexes à la source en simplifiant les expressions DAX.
- Appliquez le mode de stockage **Double** pour les dimensions liées aux tables de faits.
- Utilisez la propriété *Intégrité référentielle supposée* sur les relations.
- Évitez les relations sur les colonnes avec des identificateurs uniques calculés.

### Mode Direct Lake

**Direct Lake** est le mode innovant de Microsoft Fabric. Il permet d'interroger des données directement à partir d'un entrepôt ou d'un lac Fabric (fichiers Delta dans OneLake) sans les stocker dans un modèle sémantique séparé.

**Caractéristiques du mode Direct Lake :**
- Chargement rapide des données en mémoire depuis les tables Delta OneLake
- Pas d'actualisation planifiée nécessaire — les données sont toujours à jour
- Performances proches de l'Import, fraîcheur des données comme DirectQuery
- Requiert un lakehouse ou un entrepôt Fabric configuré
- Possibilité de configurer un **fallback sur DirectQuery** pour les requêtes DAX complexes

**Bonnes pratiques pour Direct Lake :**
- Configurez Direct Lake pour accéder au stockage ADLS via des raccourcis.
- Configurez le comportement de secours sur DirectQuery pour les requêtes DAX complexes.

### Mode Composite

Le mode **Modèle Composite** peut combiner des modes Import et DirectQuery, ou intégrer plusieurs sources de données DirectQuery. Ce mode prend en charge les relations plusieurs-à-plusieurs sans avoir besoin de tables de pont.

**Quand utiliser le mode Composite :**
- Combinaison de données cloud (DirectQuery) avec des données locales (Import)
- Optimisation de certaines tables pour les performances (Import) tout en maintenant d'autres en temps réel (DirectQuery)
- Relations plusieurs-à-plusieurs nécessaires

**Comparaison des modes de stockage :**

| Critère | Import | DirectQuery | Direct Lake | Composite |
|---|---|---|---|---|
| **Performances** | Excellent | Moyen | Très bon | Variable |
| **Fraîcheur des données** | Selon planning | Temps réel | Temps réel | Mixte |
| **Taille des données** | Limitée (mémoire) | Illimitée | Très grande | Variable |
| **Transformations** | Toutes | Limitées | Limitées | Variable |
| **Source requise** | Toute source | Source compatible | Fabric OneLake | Toute source |

## Configurer des modèles sémantiques pour les données volumineuses
Effectué
100 XP
5 minutes

Lorsque vous utilisez des sources de données très volumineuses, vous devez changer de stratégie de chargement des données.

### Format de stockage de modèles sémantiques volumineux

Le *format de stockage de modèle sémantique volumineux* dans Microsoft Fabric vous permet de gérer efficacement des sources de données plus volumineuses, dépassant la limite standard de 10 Go. Votre limite maximale peut varier selon les paramètres de capacité ou de l'administrateur Fabric.

Activer cette fonctionnalité est simple : cochez une case dans les **paramètres de l'espace de travail** > section des modèles sémantiques volumineux.

> **Astuce** : Si votre modèle continue de croître et consomme progressivement plus de mémoire, configurez également l'actualisation incrémentielle.

### Actualisation incrémentielle

L'**actualisation incrémentielle** vous permet d'actualiser uniquement les données qui ont changé ou qui ont été ajoutées depuis la dernière actualisation. Cette fonctionnalité réduit le temps et les ressources nécessaires pour les actualisations, idéale pour les sources fréquemment mises à jour.

**Exemple pratique :** Votre table de ventes est très volumineuse et l'actualisation complète prend beaucoup de temps. En configurant l'actualisation incrémentielle, seules les nouvelles transactions (par exemple les 30 derniers jours) sont rechargées à chaque actualisation, tandis que les données historiques (plus d'un an) restent intactes.

**Configuration de l'actualisation incrémentielle :**

1. Définissez des **paramètres RangeStart et RangeEnd** dans Power Query.
2. Filtrez votre table de dates sur ces paramètres.
3. Dans **Power BI Desktop**, configurez la **stratégie d'actualisation incrémentielle** sur la table (clic droit > Actualisation incrémentielle).
4. Définissez la **plage d'archivage** (données historiques conservées) et la **plage d'actualisation** (données rechargées).
5. Optionnellement, activez l'accès DirectQuery aux données les plus récentes.
6. Publiez dans un espace de travail Fabric pris en charge.

### Partitionnement

Le **partitionnement** divise une table volumineuse en morceaux plus petits et plus gérables appelés partitions. Chaque partition peut être traitée indépendamment, améliorant les performances des requêtes et la facilité de gestion.

**Différence avec l'actualisation incrémentielle :**
- L'**actualisation incrémentielle** se concentre sur n'actualiser que les données nouvelles/modifiées.
- Le **partitionnement** divise la table entière en segments — les deux peuvent être utilisés ensemble.

**Exemple :** créer des partitions par mois ou par trimestre sur votre table de ventes, permettant aux requêtes de cibler des partitions spécifiques plutôt que l'ensemble du jeu de données.

**Outils pour le partitionnement :**
- SQL Server Management Studio (SSMS)
- Tabular Editor (outil tiers recommandé pour la gestion avancée)

## Utiliser les relations
Effectué
100 XP
8 minutes

Après avoir choisi l'infrastructure de modèle et transformé des données, vous devez créer des relations pour permettre aux données d'être filtrées et agrégées en fonction des données d'une autre table.

### Créer un schéma en étoile

Dans un schéma en étoile, les **tables de faits** et les **tables de dimensions** fonctionnent ensemble pour organiser et analyser des données. La table de faits stocke les données principales sur les activités commerciales, tandis que les tables de dimensions fournissent des informations contextuelles.

![Diagramme montrant une table de faits au centre et plusieurs tables de dimension connectées par des relations organisées en forme d'étoile.](https://learn.microsoft.com/fr-fr/training/wwl/design-scalable-semantic-models/media/model-frameworks-star-schema-design.png)

### Types de relations

Les relations se présentent sous différents types :

| Type | Description | Usage typique |
|---|---|---|
| **Un-à-plusieurs** | Un enregistrement d'une table se rapporte à plusieurs d'une autre | Table de dimension (1) vers table de faits (N) — le plus courant |
| **Plusieurs-à-un** | Identique à un-à-plusieurs, selon la direction du filtre | Voir ci-dessus |
| **Un-à-un** | Les deux tables ont des données uniques | Rare — envisagez de fusionner les tables |
| **Plusieurs-à-plusieurs** | Plusieurs enregistrements des deux côtés | Données complexes — peut nécessiter une table de pont |

**Table de pont** : pour les relations plusieurs-à-plusieurs, utilisez une table intermédiaire qui lie les deux tables via des clés partagées.

### Direction du filtre

Lorsque vous créez une relation, vous configurez la direction dans laquelle les données sont filtrées :

- **Filtre simple (unidirectionnel)** : la dimension filtre la table de faits. Paramètre standard pour les schémas en étoile — prévisible et performant.
- **Filtre bidirectionnel** : les filtres se propagent dans les deux sens. Utile pour les relations un-à-un ou certaines relations plusieurs-à-plusieurs. **Attention** : peut dégrader les performances et dérouter les utilisateurs.

**Intégrité référentielle** : garantit que les relations entre les tables restent cohérentes (chaque valeur de clé étrangère a une correspondance dans la clé primaire). Cette propriété améliore également les performances des requêtes en utilisant des jointures INNER plutôt que LEFT OUTER.

### Relations dormantes et USERELATIONSHIP

Parfois, vous avez besoin de plusieurs relations entre les mêmes tables, mais une seule peut être active à la fois. Utilisez la fonction DAX `USERELATIONSHIP` pour activer une relation inactive dans un calcul spécifique :

```dax
Sales by Order Date = 
CALCULATE(
    SUM(Sales[Amount]),
    USERELATIONSHIP(Sales[OrderDate], Calendar[Date])
)

Sales by Ship Date = 
CALCULATE(
    SUM(Sales[Amount]),
    USERELATIONSHIP(Sales[ShipDate], Calendar[Date])
)
```

### Tables déconnectées

Une **table déconnectée** n'est associée à aucune autre table du modèle. Elle sert à accepter des "entrées utilisateur" (via un segment), permettant aux calculs de modèle d'utiliser ces valeurs de manière significative.

**Exemple classique :** un paramètre "What-If" Power BI Desktop crée une table déconnectée avec des valeurs de scénario (taux de change, pourcentages de croissance...). Les mesures DAX utilisent alors ces valeurs pour des calculs dynamiques.

## Écrire DAX pour une meilleure lisibilité avec des calculs complexes
Effectué
100 XP
5 minutes

DAX fournit un ensemble puissant de fonctions pour créer des calculs de base à complexes. En utilisant des conditions de filtrage, des variables et des fonctions d'itérateur, de fenêtre et d'information, vous créez des formules efficaces et lisibles.

### Variables

Les variables dans DAX simplifient les expressions et améliorent les performances en stockant le résultat d'une expression pour le réutiliser plusieurs fois, réduisant les calculs répétés.

```dax
Average Sales per Customer = 
VAR TotalSales = SUM(Sales[Amount])
VAR CustomerCount = DISTINCTCOUNT(Sales[CustomerID])
RETURN
    DIVIDE(TotalSales, CustomerCount, 0)
```

**Avantages des variables :**
- Lisibilité améliorée
- Performance optimisée (l'expression n'est évaluée qu'une fois)
- Débogage facilité

### Itérateurs

Les fonctions itératives (SUMX, AVERAGEX, MAXX, MINX, COUNTX, RANKX...) effectuent des calculs ligne par ligne sur une table et retournent une valeur unique.

```dax
Total Profit = 
SUMX(
    Sales,
    Sales[Quantity] * (Sales[UnitPrice] - Sales[UnitCost])
)
```

> **Attention** : les fonctions itératives sur de grandes tables peuvent impacter les performances en raison du traitement ligne par ligne.

### Filtrage de table

Les fonctions FILTER, ALL et CALCULATETABLE permettent de créer des tables filtrées dynamiques :

```dax
Electronics Sales =
CALCULATE(
    SUM(Sales[Amount]),
    FILTER(Products, Products[Category] = "Electronics")
)
```

### Fonctions de fenêtrage

Les fonctions INDEX, OFFSET et WINDOW permettent des calculs basés sur l'ordre des données :

```dax
Previous Month Sales = 
CALCULATE(
    SUM(Sales[Amount]),
    OFFSET(-1, ALLSELECTED(Calendar[YearMonth]), ORDERBY(Calendar[YearMonth], ASC))
)
```

### Fonctions d'information

Les fonctions ISBLANK, ISNUMBER, HASONEVALUE, CONTAINS permettent des vérifications conditionnelles :

```dax
Total Sales for Single Category = 
IF(
    HASONEVALUE(Products[Category]),
    SUM(Sales[Amount]),
    BLANK()
)
```

## Créer des éléments de calcul dynamiques
Effectué
100 XP
8 minutes

Les éléments de calcul dynamiques ajoutent de la flexibilité à votre modèle sémantique, simplifiant les calculs et réduisant le nombre de visuels dans les rapports.

### Groupes de calcul

Les **groupes de calcul** vous permettent de définir des calculs réutilisables qui s'appliquent dynamiquement à plusieurs mesures, réduisant la redondance et simplifiant la maintenance.

**Exemple classique : Intelligence temporelle**

Au lieu de créer des mesures distinctes "Ventes YTD", "Bénéfice YTD", "Ventes QTD", "Bénéfice QTD"... créez un groupe de calcul "Time Intelligence" avec des éléments de calcul réutilisables :

```dax
-- Élément YTD (Year-to-Date)
Year-to-Date (YTD) = 
CALCULATE(
    SELECTEDMEASURE(),
    DATESYTD('Date'[Date])
)

-- Élément QTD (Quarter-to-Date)
Quarter-to-Date (QTD) = 
CALCULATE(
    SELECTEDMEASURE(),
    DATESQTD('Date'[Date])
)

-- Élément MTD (Month-to-Date)
Month-to-Date (MTD) = 
CALCULATE(
    SELECTEDMEASURE(),
    DATESMTD('Date'[Date])
)
```

Ces éléments peuvent être utilisés dans un segment pour que les utilisateurs basculent dynamiquement entre YTD, QTD et MTD pour n'importe quelle mesure du modèle.

![Capture d'écran du visuel matrice montrant le total des ventes pour YTD, QTD et MTD.](https://learn.microsoft.com/fr-fr/training/wwl/design-scalable-semantic-models/media/calculation-group-matrix.png)

**Avantage** : sans groupes de calcul, vous devriez créer des mesures YTD, QTD et MTD pour chaque mesure de base (Ventes, Bénéfice, Coût, etc.) — explosion combinatoire des mesures.

### Paramètres de champ

Les **paramètres de champ** permettent aux utilisateurs de rapports de sélectionner dynamiquement différents champs ou mesures dans un visuel, sans changer de page ou de rapport.

**Exemple :** Créez un paramètre incluant les champs Produit, Catégorie et Couleur. Les utilisateurs peuvent basculer dynamiquement l'axe X d'un graphique entre ces trois dimensions via un segment.

![Capture d'écran d'un histogramme avec un paramètre de champ et un segment.](https://learn.microsoft.com/fr-fr/training/wwl/design-scalable-semantic-models/media/column-chart-parameter-slicer.png)

**Avantage** : réduit la multiplication des visuels similaires (un seul visuel remplace trois visuels statiques), améliorant les performances du rapport.

### Chaînes de format dynamique

Les **chaînes de format dynamique** ajustent le format d'affichage d'une mesure selon des conditions :

```dax
Total Sales with Dynamic Format = 
SWITCH(
    TRUE(),
    [Total Sales] > 1000000, FORMAT([Total Sales], "$#,##0,,M"),
    [Total Sales] > 1000,    FORMAT([Total Sales], "$#,##0,K"),
    FORMAT([Total Sales], "$#,##0")
)
```

**Résultat :** "1.2M", "350K" ou "850" selon la valeur, améliorant la lisibilité sans créer plusieurs mesures pour différentes échelles.

## Vérification des connaissances
10 minutes

1. **Quel mode de stockage dans Microsoft Fabric lit directement les données depuis des fichiers Delta dans OneLake sans les importer dans le modèle sémantique ?**
   - a) Mode Import
   - b) Mode DirectQuery
   - c) Mode Direct Lake ✓
   - d) Mode Composite
   
   *Le mode Direct Lake est spécifique à Microsoft Fabric. Il lit directement les données depuis les fichiers Delta (tables Delta-Parquet) dans OneLake, offrant des performances proches de l'Import et une fraîcheur des données comparable à DirectQuery, sans actualisation planifiée nécessaire.*

2. **Vous avez une table de ventes qui reçoit quotidiennement de nouvelles transactions. Vous souhaitez éviter de recharger l'historique complet (plusieurs années) à chaque actualisation. Quelle fonctionnalité devez-vous configurer ?**
   - a) Le partitionnement manuel
   - b) Le mode DirectQuery
   - c) L'actualisation incrémentielle ✓
   - d) Le format de stockage volumineux
   
   *L'actualisation incrémentielle permet de ne recharger que les données nouvelles ou modifiées (par exemple les 30 derniers jours) à chaque actualisation, laissant l'historique ancien intact. Cela réduit significativement la durée des actualisations pour les grandes tables.*

3. **Dans un modèle sémantique avec un schéma en étoile, quelle est la cardinalité typique des relations entre les tables de faits et les tables de dimension ?**
   - a) Un-à-un
   - b) Plusieurs-à-plusieurs
   - c) Un-à-plusieurs (côté dimension vers faits)
   - d) Plusieurs-à-un (côté faits vers dimension) ✓
   
   *Dans un schéma en étoile, la relation typique va d'une dimension (valeur unique/clé primaire) vers la table de faits (plusieurs lignes ayant la même clé). La cardinalité est "plusieurs-à-un" du point de vue de la table de faits, ou "un-à-plusieurs" du point de vue de la dimension.*

4. **Vous souhaitez créer une mesure "Ventes Year-to-Date" et "Bénéfice Year-to-Date" sans dupliquer la logique temporelle. Quelle fonctionnalité DAX devez-vous utiliser ?**
   - a) Les variables DAX (VAR/RETURN)
   - b) Les paramètres de champ
   - c) Les groupes de calcul ✓
   - d) Les chaînes de format dynamique
   
   *Les groupes de calcul permettent de définir une logique temporelle (YTD, QTD, MTD) une seule fois, puis de l'appliquer dynamiquement à n'importe quelle mesure de base (Ventes, Bénéfice, Coût...) via la fonction SELECTEDMEASURE(), évitant la duplication de code.*

5. **Quel est l'avantage principal de l'utilisation des variables (VAR/RETURN) dans les formules DAX ?**
   - a) Elles permettent d'effectuer des calculs en temps réel depuis la source
   - b) Elles améliorent la lisibilité du code et évitent d'évaluer la même expression plusieurs fois ✓
   - c) Elles remplacent les groupes de calcul pour l'intelligence temporelle
   - d) Elles activent le mode Direct Lake automatiquement
   
   *Les variables DAX (VAR/RETURN) améliorent la lisibilité en nommant les expressions intermédiaires et optimisent les performances en évaluant chaque expression une seule fois, même si elle est référencée plusieurs fois dans la formule.*

## Résumé
3 minutes

Dans ce module, vous avez appris les principes de conception de modèles sémantiques évolutifs dans Microsoft Fabric :

- **Modes de stockage** : Import (performances maximales, actualisation planifiée), DirectQuery (temps réel, performances modérées), Direct Lake (exclusif Fabric, performances optimales + fraîcheur des données sans actualisation), et Composite (combinaison).
- **Données volumineuses** : le format de stockage volumineux (> 10 Go) et l'actualisation incrémentielle (ne recharger que les données nouvelles/modifiées) permettent de gérer des modèles qui dépassent les limites standard.
- **Relations** : les relations un-à-plusieurs unidirectionnelles sont le standard dans les schémas en étoile. Les relations dormantes et USERELATIONSHIP permettent de gérer les dimensions à rôle multiple (ex. : table calendrier avec OrderDate et ShipDate).
- **DAX avancé** : les variables (VAR/RETURN) améliorent la lisibilité et les performances ; les itérateurs (SUMX, AVERAGEX) calculent ligne par ligne ; les fonctions de filtrage (CALCULATE, FILTER) modifient le contexte de filtre.
- **Éléments dynamiques** : les groupes de calcul éliminent la duplication des mesures pour l'intelligence temporelle ; les paramètres de champ permettent des rapports interactifs ; les chaînes de format dynamique adaptent l'affichage selon la valeur.
