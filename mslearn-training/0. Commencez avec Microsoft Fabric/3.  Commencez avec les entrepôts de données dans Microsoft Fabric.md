Les entrepôts de données sont au cœur de la stratégie d'analytique des entreprises modernes. Ils permettent de consolider des données provenant de multiples sources dans un référentiel centralisé, optimisé pour les requêtes analytiques et le reporting. Cependant, les solutions d'entrepôt de données traditionnelles exigent une infrastructure complexe à gérer et des processus ETL lourds pour maintenir les données à jour.

Microsoft Fabric réinvente l'expérience d'entreposage de données avec un **data warehouse entièrement géré**, construit sur OneLake et offrant des fonctionnalités T-SQL transactionnelles complètes. Les données sont stockées au format Delta ouvert, ce qui signifie que d'autres charges de travail Fabric peuvent y accéder sans duplication, et que des outils familiers comme SQL Server Management Studio (SSMS) ou Azure Data Studio peuvent se connecter directement.

Dans ce module, vous apprendrez les fondements de la modélisation dimensionnelle, comment créer et interroger un entrepôt Fabric, comment modéliser les données pour le reporting et comment le sécuriser et le surveiller.

## Comprendre les entrepôts de données
Effectué
100 XP
7 minutes

Un data warehouse est un magasin centralisé et structuré conçu pour les requêtes analytiques et les rapports. Contrairement aux bases de données opérationnelles qui gèrent des transactions métier quotidiennes, un data warehouse consolide les données de plusieurs sources dans un format optimisé pour l'analyse.

La création d'un data warehouse moderne implique généralement :

- **Ingestion des données** : déplacement de données à partir de systèmes sources vers l'entrepôt.
- **Stockage des données** : stockage des données dans un format optimisé pour l'analytique.
- **Traitement des données** : transformation des données dans un format prêt à être consommé par les outils analytiques.
- **Analyse et livraison des données** : analyse des données pour obtenir des insights et les distribuer à l'entreprise.

### Tables d'un entrepôt de données

Vous organisez les tables d'entrepôt de données pour prendre en charge une analyse efficace de grandes quantités de données. Cette organisation, appelée **modélisation dimensionnelle**, implique de structurer des tables en tables de faits et des tables de dimension.

**Les tables de faits** contiennent les données numériques que vous souhaitez analyser. Elles comprennent généralement un grand nombre de lignes et constituent la principale source de données pour l'analyse. Par exemple, une table de faits peut contenir le montant total payé pour des commandes passées à une date spécifique ou dans un magasin particulier.

**Les tables de dimension** contiennent des informations descriptives sur les données des tables de faits. Elles ont généralement quelques lignes et fournissent un contexte pour les données. Par exemple, une table de dimension peut contenir des informations sur les clients qui ont passé des commandes.

En plus des colonnes d'attribut, une table de dimension contient une colonne clé unique qui identifie de manière unique chaque ligne :

- Une **clé de substitution** est un identificateur unique pour chaque ligne de la table de dimension, souvent une valeur entière générée automatiquement.
- Une **clé alternative** est souvent une clé naturelle ou métier qui identifie une instance spécifique dans le système source transactionnel.

#### Types spéciaux de tables de dimension

- **Dimensions de temps** : fournissent des informations sur la période pendant laquelle un événement s'est produit (année, trimestre, mois, jour). Elles permettent l'agrégation des données sur des intervalles temporels.
- **Dimensions à variation lente (SCD)** : suivent les modifications apportées aux attributs de dimension au fil du temps (ex. : changement d'adresse d'un client, modification du prix d'un produit). Essentielles pour analyser les données historiques.

### Conception de schémas d'entrepôt de données

Dans un data warehouse, les données de dimension sont **dénormalisées** pour réduire le nombre de jointures requises lors des requêtes.

**Schéma en étoile** : une table de faits se rapporte directement aux tables de dimension.

![Diagramme d'une conception de schéma en étoile affichant une table FactSales avec cinq dimensions.](https://learn.microsoft.com/fr-fr/training/wwl/get-started-data-warehouse/media/star-schema.png)

**Schéma flocon de neige** : utilisé quand il existe un grand nombre de niveaux ou d'attributs partagés. Les tables de dimension sont normalisées en tables supplémentaires.

![Diagramme d'un schéma flocon de neige affichant plusieurs dimensions normalisées.](https://learn.microsoft.com/fr-fr/training/wwl/get-started-data-warehouse/media/snowflake-schema.png)

Le schéma en étoile est généralement préféré pour ses performances de requête et sa simplicité, tandis que le schéma flocon peut réduire la redondance des données dans certains cas.

## Comprendre les entrepôts de données dans Fabric
Effectué
100 XP
8 minutes

Un entrepôt de données Fabric est une base de données relationnelle à l'échelle de l'entreprise, entièrement gérée et construite sur OneLake. Il fournit des fonctionnalités T-SQL transactionnelles complètes, notamment les instructions DDL (CREATE, ALTER, DROP) et DML (INSERT, UPDATE, DELETE, MERGE), avec une conformité ACID complète pour la cohérence des données.

Les données sont stockées au format **Delta ouvert** sur OneLake, ce qui signifie que d'autres charges de travail Fabric peuvent accéder aux mêmes données sans duplication.

### Fonctionnalités clés de l'entrepôt Fabric

| Fonctionnalité | Description |
|---|---|
| **Prise en charge complète de T-SQL** | Écrire des instructions DDL et DML, notamment MERGE pour les scénarios upsert |
| **Entièrement managé** | Aucune infrastructure à configurer ; la capacité de calcul se met à l'échelle automatiquement |
| **Intégration OneLake** | Données stockées au format Delta, accessibles par toutes les charges de travail Fabric |
| **Requêtes inter-bases de données** | Interroger des données entre entrepôts et lakehouses avec un nommage en trois parties (database.schema.table) |
| **Outils familiers** | Connexion avec SSMS, Azure Data Studio ou tout client SQL via des connexions TDS standard |
| **Assistance Copilot** | Génération de requêtes SQL depuis le langage naturel, saisie semi-automatique, explication et correction de requêtes |

### Entrepôt vs Point de terminaison analytique SQL

Les espaces de travail Fabric peuvent contenir deux types d'éléments SQL qui servent des objectifs différents.

| Capacité | Entrepôt | Point de terminaison des analyses SQL |
|---|---|---|
| Lire les données | Oui | Oui |
| Écrire des données (INSERT, UPDATE, DELETE, MERGE) | Oui | Non |
| Créer des tables (DDL) | Oui | Non |
| Créer des vues et des procédures stockées | Oui | Oui |
| Source de données | Tables d'entrepôt natives | Tables Lakehouse Delta |

Utilisez un entrepôt lorsque vous avez besoin de fonctionnalités T-SQL en lecture/écriture complètes. Utilisez le point de terminaison d'analytique SQL lorsque vous avez besoin d'un accès SQL en lecture seule pour les données lakehouse.

### Créer un data warehouse

Vous pouvez créer un data warehouse dans Fabric à partir du hub **Créer** ou dans un **workspace**. Après avoir créé un entrepôt vide, vous pouvez ajouter des tables, des vues et d'autres objets.

![Capture d'écran de l'interface Fabric avec une flèche pointant vers le hub de création.](https://learn.microsoft.com/fr-fr/training/wwl/get-started-data-warehouse/media/create-data-warehouse.png)

### Ingérer des données dans un entrepôt

Il existe plusieurs façons de charger des données dans un entrepôt de données Fabric :

- **COPY INTO** : chargez en bloc des données à partir de fichiers externes (CSV, Parquet) dans Azure Storage dans des tables d'entrepôt.
- **OPENROWSET** : interrogez les fichiers directement à partir de stockages externes ou d'emplacements OneLake pour l'analyse ou l'ingestion ad hoc, sans créer de tables.
- **Pipelines et dataflows** : utilisez Data Factory pipelines ou Dataflows Gen2 pour orchestrer le déplacement et la transformation des données.
- **Requêtes inter-bases de données** : interroger des tables lakehouse directement depuis l'entrepôt à l'aide d'un nommage en trois parties, sans copier de données.

Exemple de commande `COPY INTO` :

```sql
COPY INTO dbo.Region
FROM 'https://mystorageaccount.blob.core.windows.net/data/Region.csv'
WITH (
    FILE_TYPE = 'CSV',
    CREDENTIAL = (
        IDENTITY = 'Shared Access Signature',
        SECRET = 'xxx'
    ),
    FIRSTROW = 2
)
GO
```

### Créer des tables et charger des données

Vous créez des tables à l'aide d'instructions T-SQL `CREATE TABLE`. Définissez des colonnes avec des types de données appropriés pour les charges de travail d'analytique.

```sql
CREATE TABLE dbo.DimCustomer
(
    CustomerKey INT NOT NULL,
    CustomerAltKey NVARCHAR(10) NOT NULL,
    CustomerName NVARCHAR(100) NOT NULL,
    Region NVARCHAR(50) NULL
);
GO

CREATE TABLE dbo.FactSales
(
    SalesKey INT NOT NULL,
    CustomerKey INT NOT NULL,
    ProductKey INT NOT NULL,
    DateKey INT NOT NULL,
    SalesAmount DECIMAL(10,2) NOT NULL,
    Quantity INT NOT NULL
);
GO
```

### Utiliser des tables intermédiaires pour le chargement des données

Un modèle courant consiste à déposer des données brutes dans des tables de **staging** avant de les transformer et de les charger dans les tables de dimensions et de faits finales.

```sql
INSERT INTO dbo.FactSales (SalesKey, CustomerKey, ProductKey, DateKey, SalesAmount, Quantity)
SELECT
    s.OrderID,
    c.CustomerKey,
    p.ProductKey,
    d.DateKey,
    s.Amount,
    s.Qty
FROM dbo.StgSales AS s
INNER JOIN dbo.DimCustomer AS c ON s.CustomerID = c.CustomerAltKey
INNER JOIN dbo.DimProduct AS p ON s.ProductID = p.ProductAltKey
INNER JOIN dbo.DimDate AS d ON s.OrderDate = d.DateValue;
GO
```

### Clones de table

Vous pouvez créer des clones de table sans copie dans un entrepôt Fabric. Le clonage copie les métadonnées de la table tout en référençant les mêmes fichiers de données sous-jacents dans OneLake — sans duplication de données.

```sql
-- Clone dans le même schéma
CREATE TABLE dbo.Employee AS CLONE OF dbo.EmployeeUSA;
```

Les clones de table sont utiles pour le développement et le test, la récupération des données après une mise en production ayant échoué, et la conservation des données à des points spécifiques dans le temps.

## Interroger et transformer des données
Effectué
100 XP
6 minutes

Les données brutes arrivent rarement dans le format exact dont vous avez besoin pour l'analyse. Un data warehouse Fabric vous offre deux outils pour ce travail : le query editor SQL pour T-SQL et le query editor Visuel pour une approche sans code.

### Interroger des données avec le query editor SQL

Le **SQL query editor** offre une expérience de requête qui inclut IntelliSense, la complétion du code, la mise en surbrillance de la syntaxe, l'analyse côté client et la validation.

Pour créer une requête, utilisez le bouton **Nouvelle requête SQL** dans le menu. **Copilot pour Data Warehouse** est disponible dans l'éditeur pour vous aider à générer des requêtes depuis le langage naturel, compléter le code et expliquer ou corriger les requêtes existantes.

### Interroger des données avec le Visual query editor

Le *Visual query editor* offre une expérience similaire à la vue de diagramme Power Query. Faites glisser une table de votre entrepôt sur la zone de travail pour commencer. Vous pouvez ensuite utiliser le menu **Transformer** pour ajouter des colonnes, des filtres et d'autres transformations.

![Capture d'écran de l'Éditeur de requêtes visuelles.](https://learn.microsoft.com/fr-fr/training/wwl/get-started-data-warehouse/media/visual-query.png)

### Transformer des données avec des vues et des procédures stockées

**Les vues** définissent une requête enregistrée que vous pouvez référencer comme une table. Elles permettent de normaliser la façon dont les analystes accèdent aux données :

```sql
CREATE VIEW dbo.vw_SalesByRegion
AS
SELECT
    c.Region,
    SUM(f.SalesAmount) AS TotalSales,
    COUNT(f.OrderID) AS OrderCount
FROM dbo.FactSales AS f
INNER JOIN dbo.DimCustomer AS c
    ON f.CustomerKey = c.CustomerKey
GROUP BY c.Region;
```

![Capture d'écran du SQL query editor affichant une requête T-SQL créant une vue.](https://learn.microsoft.com/fr-fr/training/wwl/get-started-data-warehouse/media/create-view.png)

**Les procédures stockées** contiennent une logique T-SQL que vous pouvez exécuter à la demande pour les tâches de transformation reproductibles.

> **Astuce** : Les vues et procédures stockées aident également à rendre vos données plus accessibles aux outils basés sur l'IA. Les agents de données Copilot et Fabric IQ peuvent interroger les vues comme des tables, améliorant la précision des requêtes en langage naturel.

## Données de modèle dans un entrepôt
Effectué
100 XP
7 minutes

Sans modélisation des données, chaque consommateur doit déterminer les tables qui se rapportent les unes aux autres, écrire sa propre logique d'agrégation et deviner les significations des colonnes. Dans un entrepôt Microsoft Fabric, vous préparez des données pour la clarté, définissez des relations entre les tables, standardisez l'accès via des vues et des mesures, et publiez des modèles sémantiques pour l'élaboration de rapports.

### Préparer les données pour la consommation

Avant de définir des relations ou d'ajouter des calculs, nettoyez ce que les consommateurs voient. Dans l'affichage du modèle, vous pouvez :

- **Masquer les objets internes** comme les tables intermédiaires, les colonnes clés de substitution et les artifacts ETL.
- **Renommer les colonnes** pour utiliser des noms conviviaux (ex. : renommer `CustRgn` en `Customer Region`).
- **Ajouter des descriptions** aux tables et aux colonnes pour que les consommateurs comprennent ce que les données représentent.

> **Important** : Copilot dans Power BI et les agents de données Fabric IQ s'appuient sur les noms de tables, les noms de colonnes et les descriptions pour interpréter les questions en langage naturel. Une colonne bien nommée avec une description claire produit de meilleurs résultats en langage naturel.

### Comprendre les relations entre les tables

Une relation est une connexion logique entre deux tables qui active le filtrage, le regroupement et l'agrégation. Chaque relation a deux propriétés importantes :

- **Cardinalité** : décrit la façon dont les lignes des deux tables correspondent. Dans un schéma en étoile, les relations faits-dimensions sont généralement plusieurs-à-un.
- **Sens du filtrage croisé** : détermine la façon dont les filtres se propagent entre les tables. La direction unique (dimension vers faits) est le paramètre standard pour la plupart des conceptions en étoile.

### Normaliser l'accès aux données avec des vues et des mesures

- **Les vues** assurent la cohérence pour les consommateurs T-SQL. Elles encapsulent la logique de jointure, les filtres et les sélections de colonnes dans une requête réutilisable.
- **Les mesures** fournissent la cohérence pour les calculs DAX. Une mesure est une expression DAX réutilisable qui définit un calcul (total, moyenne, ratio, nombre). Créées dans la vue du modèle d'entrepôt, elles deviennent la source unique de vérité pour une métrique.

### Créer un modèle sémantique pour la création de rapports Power BI

Avec des tables préparées, des relations définies et des mesures en place, l'entrepôt est prêt pour la création de rapports. Les modèles sémantiques créés depuis un entrepôt Fabric utilisent le mode **Direct Lake**.

Contrairement au mode d'importation traditionnel (qui copie des données dans la mémoire Power BI), Direct Lake lit les données directement depuis les fichiers Parquet OneLake. Cela signifie :
- Les rapports reflètent les dernières données de l'entrepôt sans actualisations planifiées.
- Pas de surcharge de stockage et de traitement liée au maintien d'une copie séparée.

![Capture d'écran d'un rapport Power BI connecté à un entrepôt Fabric.](https://learn.microsoft.com/fr-fr/training/wwl/get-started-data-warehouse/media/sales-report.png)

## Sécuriser et surveiller un entrepôt
Effectué
100 XP
4 minutes

La sécurité et la surveillance sont des aspects essentiels de la gestion de votre data warehouse. Fabric fournit plusieurs couches de protection et des outils de visibilité.

### Sécurité

La sécurité de l'entrepôt de données Fabric fonctionne à plusieurs niveaux, de l'accès à l'espace de travail jusqu'aux lignes et colonnes individuelles.

#### Rôles de l'espace de travail

Les données dans Fabric sont organisées en *workspaces* et les rôles d'espace de travail constituent la première couche de contrôle d'accès. Affectez des utilisateurs aux rôles appropriés :

| Rôle | Permissions |
|---|---|
| Administrateur | Contrôle total |
| Membre | Peut modifier et partager |
| Contributeur | Peut modifier |
| Visionneuse | Peut visualiser uniquement |

#### Autorisations d'élément

En plus des rôles d'espace de travail, vous pouvez accorder des **autorisations item** pour partager des entrepôts individuels sans accorder l'accès à l'ensemble de l'espace de travail :

- **Read** : permet de se connecter via le point de terminaison d'analytique SQL.
- **ReadData** : permet de lire les données à partir d'une table ou d'une vue dans l'entrepôt.
- **ReadAll** : permet de lire les fichiers Parquet bruts dans OneLake.

#### Sécurité SQL granulaire

Pour une access control plus précise, Fabric data warehouse prend en charge la sécurité granulaire via T-SQL :

- **Sécurité au niveau de l'objet** : contrôle l'accès à des tables, vues ou procédures spécifiques.
- **Sécurité au niveau des lignes (RLS)** : limite les lignes qu'un utilisateur peut voir via des prédicats WHERE.
- **Sécurité au niveau des colonnes (CLS)** : limite les colonnes visibles par des utilisateurs spécifiques.
- **Masquage dynamique des données** : masque les données sensibles (emails, numéros de compte) des utilisateurs non privilégiés.

### Supervision

#### Query Insights

*Query Insights* fournit un emplacement central pour les données de requête historiques et les informations de performances exploitables. Il conserve les données pendant 30 jours.

Vues système disponibles :

```sql
-- Historique des requêtes SQL exécutées
SELECT * FROM queryinsights.exec_requests_history;

-- Requêtes les plus longues
SELECT * FROM queryinsights.long_running_queries;

-- Historique des sessions
SELECT * FROM queryinsights.exec_sessions_history;
```

#### Vues de gestion dynamique (DMV)

Utilisez les DMV pour surveiller les connexions actives, les sessions et les requêtes en temps réel :

```sql
SELECT request_id, session_id, start_time, total_elapsed_time
FROM sys.dm_exec_requests
WHERE status = 'running'
ORDER BY total_elapsed_time DESC;
```

> **Important** : Vous devez être administrateur de l'espace de travail pour exécuter la commande `KILL` afin de terminer les sessions longues. Les membres, contributeurs et visionneuses peuvent voir leurs propres résultats, mais ne peuvent pas voir les requêtes d'autres utilisateurs.

## Vérification des connaissances
10 minutes

1. **Quel type de table contient les données numériques mesurables dans un schéma en étoile ?**
   - a) Table de dimension
   - b) Table de faits ✓
   - c) Table de staging
   - d) Table de clés
   
   *Les tables de faits contiennent les mesures numériques quantitatives (montants de vente, quantités, etc.) que vous souhaitez analyser, tandis que les tables de dimension fournissent le contexte descriptif.*

2. **Quelle est la principale différence entre un entrepôt Fabric et le point de terminaison analytique SQL d'un lakehouse ?**
   - a) L'entrepôt supporte uniquement les requêtes en lecture, le point de terminaison supporte l'écriture
   - b) L'entrepôt supporte les opérations de lecture ET d'écriture T-SQL complètes, le point de terminaison est en lecture seule ✓
   - c) L'entrepôt ne peut pas se connecter à OneLake
   - d) Le point de terminaison analytique SQL est plus performant pour les grandes tables
   
   *L'entrepôt Fabric offre des fonctionnalités T-SQL transactionnelles complètes (DDL et DML), tandis que le point de terminaison analytique SQL d'un lakehouse ne permet que la lecture des données lakehouse via SQL.*

3. **Quelle commande T-SQL est utilisée pour charger en masse des données depuis des fichiers CSV ou Parquet dans un entrepôt Fabric ?**
   - a) BULK INSERT
   - b) INSERT INTO ... SELECT
   - c) COPY INTO ✓
   - d) LOAD DATA
   
   *La commande COPY INTO est optimisée pour le chargement en masse dans Fabric depuis des fichiers dans Azure Storage (CSV, Parquet, ORC, JSON).*

4. **Quel mode de connexion les modèles sémantiques Power BI créés depuis un entrepôt Fabric utilisent-ils par défaut ?**
   - a) Mode Import
   - b) Mode DirectQuery
   - c) Mode Direct Lake ✓
   - d) Mode Live Connection
   
   *Les modèles sémantiques créés depuis un entrepôt Fabric utilisent le mode Direct Lake, qui lit directement les fichiers Parquet dans OneLake sans copier les données dans la mémoire Power BI.*

5. **Quelle fonctionnalité de sécurité T-SQL permet de restreindre les lignes visibles par un utilisateur dans une table d'entrepôt Fabric ?**
   - a) Masquage dynamique des données
   - b) Sécurité au niveau des colonnes (CLS)
   - c) Sécurité au niveau des objets
   - d) Sécurité au niveau des lignes (RLS) ✓
   
   *La sécurité au niveau des lignes (RLS) permet de filtrer les lignes qu'un utilisateur peut voir en appliquant des prédicats de clause WHERE basés sur l'identité de l'utilisateur.*

## Résumé
1 minute

Dans ce module, vous avez appris les concepts fondamentaux des entrepôts de données dans Microsoft Fabric :

- Les **entrepôts de données** sont des référentiels centralisés optimisés pour l'analytique, organisés selon des schémas en étoile ou flocon de neige avec des tables de faits et de dimension.
- L'**entrepôt Fabric** est entièrement géré, construit sur OneLake, et offre une prise en charge T-SQL complète (DDL + DML avec conformité ACID).
- Les méthodes d'**ingestion de données** incluent COPY INTO, OPENROWSET, les pipelines Data Factory et les requêtes inter-bases de données.
- Les **vues et procédures stockées** permettent d'encapsuler la logique de transformation et de normaliser l'accès aux données pour les consommateurs et les outils d'IA.
- La **modélisation** dans l'entrepôt (relations, mesures DAX, nommage) alimente directement la qualité des rapports Power BI en mode Direct Lake et les réponses des agents IA.
- La **sécurité** est multicouche : rôles d'espace de travail, autorisations d'élément, et sécurité SQL granulaire (RLS, CLS, masquage des données).
- La **surveillance** via Query Insights et les DMV permet d'identifier les requêtes longues et d'optimiser les performances.
