## Présentation
*4 min* | 100 XP

### Le défi des données en temps réel

Dans le monde actuel, les entreprises génèrent et consomment des données à une vitesse et un volume sans précédent. Des exemples incluent :

- **IoT industriel** : Des capteurs de machines envoyant des mesures toutes les secondes
- **E-commerce** : Des millions de clics et d'événements d'utilisateurs par heure
- **Finance** : Des flux de cours boursiers mis à jour en millisecondes
- **Transports** : La position GPS de flottes de véhicules en temps réel
- **Réseaux sociaux** : Des flux d'événements de publications, likes, partages

Les bases de données relationnelles traditionnelles (SQL Server, PostgreSQL) ne sont pas conçues pour ingérer et interroger ce type de données à haute fréquence et en grande quantité. Elles sont optimisées pour les opérations transactionnelles (OLTP), pas pour l'analytique en temps réel à grande échelle.

**La solution : Kusto Query Engine**

Microsoft a développé **Azure Data Explorer (ADX)**, un service d'analyse de données en temps réel basé sur le moteur **Kusto**. Dans Microsoft Fabric, cette technologie est intégrée sous le nom d'**Eventhouse** avec ses **bases de données KQL** (KQL = Kusto Query Language).

### Qu'est-ce qu'un Eventhouse ?

Un **Eventhouse** est un artefact Fabric qui :

- **Contient** une ou plusieurs **bases de données KQL**
- **Optimisé** pour l'ingestion de grandes quantités de données à haute fréquence
- **Indexe** automatiquement les données pour des requêtes ultra-rapides (secondes)
- **Supporte** le langage KQL (Kusto Query Language) et un sous-ensemble de T-SQL
- **S'intègre** nativement avec les Eventstreams pour recevoir des données en streaming
- **Permet** la création de tableaux de bord temps réel via Real-Time Dashboards

**Analogie** : Si un Lakehouse est une bibliothèque bien organisée pour des ouvrages de référence (données historiques, batch), un Eventhouse est une **salle de presse en temps réel** — des dépêches arrivent en permanence, sont immédiatement indexées et peuvent être consultées en quelques secondes.

### Créer un Eventhouse

Dans Microsoft Fabric, un Eventhouse se crée depuis l'expérience **Real-Time Intelligence** :

1. Dans la barre de navigation gauche, sélectionnez **Workloads > Real-Time Intelligence**
2. Sur la page d'accueil, vous pouvez :

   - Utiliser l'exemple de démarrage rapide via **Explore Real-Time Intelligence Sample**

> L'exemple de démarrage rapide crée automatiquement un Eventhouse `RTISample` avec des données de vélos en libre-service de Londres (**Bikestream**), ce qui permet de pratiquer KQL sans configurer d'ingestion.

### Structure d'un Eventhouse

Quand vous créez un Eventhouse, Fabric crée automatiquement :
- Une **base de données KQL** portant le même nom que l'Eventhouse
- Un **queryset** (fichier de requêtes) par défaut avec des exemples

Depuis la page de l'Eventhouse, le panneau gauche affiche :
```
Mon-Eventhouse
└── KQL Database : Mon-Eventhouse
    ├── Tables
    │   └── Bikestream (exemple)
    ├── Materialized views
    ├── Functions
    └── Shortcuts
```

### Ingérer des données dans un Eventhouse

Il existe plusieurs méthodes pour charger des données dans une base de données KQL :

**1. Depuis un Eventstream (streaming temps réel)**
C'est le cas d'usage principal. Un Eventstream reçoit des événements depuis Azure Event Hub, IoT Hub, ou Kafka, et les route vers la base de données KQL.

**2. Ingestion depuis un fichier (one-time)**
Vous pouvez ingérer des données depuis des fichiers CSV, JSON, Parquet directement dans l'interface.

**3. Ingestion depuis OneLake / Azure Storage**
Connexion directe à un stockage Azure pour importer des données historiques en masse.

**4. Via le SDK (.NET, Python, Java, Go)**
Pour des ingestions programmatiques depuis vos applications.

**5. Commande KQL `.ingest`**
```kql
.ingest into table MyTable
  (h'https://storage.blob.core.windows.net/data/file.csv')
  with (format='csv', ignoreFirstRecord=true)
```

### Tables dans une base de données KQL

Les **tables KQL** sont différentes des tables SQL traditionnelles :

| Caractéristique | Table SQL (Lakehouse) | Table KQL (Eventhouse) |
|---|---|---|
| Optimisée pour | OLAP / batch | Streaming / temps réel |
| Ingestion | Batch ou streaming | Streaming haute fréquence |
| Compression | Variable | Colonnaire haute compression |
| Index | B-tree, index explicites | Auto-indexation par temps |
| Requêtes | SQL | KQL (+ sous-ensemble T-SQL) |
| Latence de requête | Secondes à minutes | Millisecondes à secondes |
| Données | Mutable (UPDATE, DELETE) | Append-only (immutable) |
| Rétention | Illimitée | Configurable (jours, semaines) |

## Utiliser KQL efficacement
*5 min* | 100 XP

### Introduction à KQL

Le **Kusto Query Language (KQL)** est un langage de requête optimisé pour l'analyse de données en temps réel. Sa syntaxe est **tabulaire** : chaque opérateur reçoit une table en entrée et produit une table en sortie, chaînés par le symbole `|` (pipe).

**Structure générale d'une requête KQL :**

```kql
NomDeLaTable
| operateur1 arguments
| operateur2 arguments
| operateur3 arguments
```

### Opérateurs KQL fondamentaux

**`take` : Récupérer N lignes**

```kql
// Prendre 100 lignes de la table Bikestream
Bikestream
| take 100
```

> `take` est l'équivalent de `SELECT TOP N` en T-SQL. L'ordre des lignes retournées n'est pas garanti (similaire à `TABLESAMPLE`). Pour un ordre déterministe, utilisez `top`.

**`project` : Sélectionner des colonnes**

```kql
// Sélectionner uniquement Street et No_Bikes
Bikestream
| project Street, No_Bikes
| take 10
```

```kql
// Renommer une colonne avec project
Bikestream
| project Street, ["Number of Empty Docks"] = No_Empty_Docks
| take 10
```

> `project` peut aussi calculer de nouvelles colonnes : `| project Revenue = UnitPrice * Quantity`

**`where` : Filtrer des lignes**

```kql
// Filtrer les résultats pour le quartier Chelsea uniquement
Bikestream
| where Neighbourhood == "Chelsea"
| project Street, No_Bikes, No_Empty_Docks
| take 20
```

```kql
// Combiner plusieurs conditions
Bikestream
| where Neighbourhood == "Chelsea" and No_Bikes > 5
| project Street, No_Bikes
```

```kql
// Filtrer avec des opérateurs de comparaison
Bikestream
| where No_Bikes between (5 .. 20)
| project Street, No_Bikes, Neighbourhood
```

**`summarize` : Agréger des données**

```kql
// Compter le nombre total de vélos disponibles
Bikestream
| summarize ["Total Number of Bikes"] = sum(No_Bikes)
```

```kql
// Grouper par quartier
Bikestream
| summarize ["Total Number of Bikes"] = sum(No_Bikes) by Neighbourhood
| project Neighbourhood, ["Total Number of Bikes"]
```

```kql
// Gérer les valeurs nulles avec case/isempty/isnull
Bikestream
| summarize ["Total Number of Bikes"] = sum(No_Bikes) by Neighbourhood
| project Neighbourhood = case(
    isempty(Neighbourhood) or isnull(Neighbourhood), "Unidentified",
    Neighbourhood),
  ["Total Number of Bikes"]
```

**Fonctions d'agrégation KQL courantes :**

| Fonction | Description |
|---|---|
| `sum(col)` | Somme des valeurs |
| `count()` | Nombre de lignes |
| `dcount(col)` | Nombre de valeurs distinctes (estimation) |
| `avg(col)` | Moyenne |
| `min(col)` | Valeur minimale |
| `max(col)` | Valeur maximale |
| `stdev(col)` | Écart-type |
| `percentile(col, 95)` | Percentile |
| `make_list(col)` | Liste de toutes les valeurs |
| `make_set(col)` | Ensemble de valeurs distinctes |

**`sort by` / `order by` : Trier les résultats**

```kql
// Trier par quartier par ordre alphabétique (asc = croissant)
Bikestream
| summarize ["Total Number of Bikes"] = sum(No_Bikes) by Neighbourhood
| project Neighbourhood = case(
    isempty(Neighbourhood) or isnull(Neighbourhood), "Unidentified",
    Neighbourhood),
  ["Total Number of Bikes"]
| sort by Neighbourhood asc
```

> `order by` et `sort by` sont identiques en KQL (deux syntaxes pour la même opération).

```kql
// Trier par total de vélos décroissant
Bikestream
| summarize TotalBikes = sum(No_Bikes) by Neighbourhood
| order by TotalBikes desc
| take 10
```

### Requêtes KQL avancées

**Requêtes temporelles** (particulièrement utiles pour les données streaming) :

```kql
// Données des 1 dernière heure
MyEvents
| where ingestion_time() > ago(1h)
| summarize count() by EventType
```

```kql
// Agrégation dans des fenêtres de temps (time bins)
MyEvents
| where timestamp > ago(24h)
| summarize EventCount = count() by bin(timestamp, 1h), EventType
| order by timestamp asc
```

```kql
// Tendance sur les 7 derniers jours
MyEvents
| where timestamp > ago(7d)
| summarize DailyCount = count() by Day = bin(timestamp, 1d)
| order by Day asc
```

**Jointures en KQL :**

```kql
// Joindre deux tables
Stations
| join kind=inner (
    Bikestream
    | summarize CurrentBikes = sum(No_Bikes) by StationId
) on StationId
| project StationName, Neighbourhood, CurrentBikes
```

### Comparaison KQL vs T-SQL

| Opération | KQL | T-SQL |
|---|---|---|
| Sélectionner colonnes | `project col1, col2` | `SELECT col1, col2` |
| Limiter les résultats | `take 100` | `SELECT TOP 100` |
| Filtrer | `where condition` | `WHERE condition` |
| Grouper | `summarize agg() by col` | `GROUP BY col` |
| Trier | `order by col asc` | `ORDER BY col ASC` |
| Compter distinct | `dcount(col)` | `COUNT(DISTINCT col)` |
| Données récentes | `where timestamp > ago(1h)` | `WHERE timestamp > DATEADD(hour,-1,GETDATE())` |
| Commentaires | `// commentaire` | `-- commentaire` |

## Vues matérialisées et fonctions stockées
*5 min* | 100 XP

### Vues matérialisées (Materialized Views)

Une **vue matérialisée** dans une base de données KQL est une requête pré-calculée dont les résultats sont stockés et mis à jour automatiquement au fur et à mesure que de nouvelles données arrivent. Contrairement aux vues SQL classiques (calculées à chaque requête), les vues matérialisées sont toujours à jour et les requêtes sur elles sont extrêmement rapides.

**Cas d'usage** : Agrégations fréquemment utilisées sur de grands volumes de données streaming.

**Créer une vue matérialisée :**

```kql
.create materialized-view with (backfill=true) BikesByNeighbourhood on table Bikestream
{
    Bikestream
    | summarize TotalBikes = sum(No_Bikes), AvgBikes = avg(No_Bikes)
      by Neighbourhood
}
```

Options importantes :
- `backfill=true` : Applique la vue aux données historiques déjà présentes dans la table
- Sans `backfill` : La vue ne s'applique qu'aux nouvelles données

**Interroger une vue matérialisée :**

```kql
// Interroger directement la vue matérialisée
BikesByNeighbourhood
| order by TotalBikes desc
```

**Supprimer une vue matérialisée :**

```kql
.drop materialized-view BikesByNeighbourhood
```

### Fonctions stockées (Stored Functions)

Les **fonctions stockées** en KQL permettent d'encapsuler des requêtes réutilisables avec des paramètres. Elles sont l'équivalent des procédures/fonctions stockées en SQL, mais pour KQL.

**Créer une fonction stockée :**

```kql
.create-or-alter function GetBikesByNeighbourhood(targetNeighbourhood: string)
{
    Bikestream
    | where Neighbourhood == targetNeighbourhood
    | summarize TotalBikes = sum(No_Bikes), Stations = count()
      by Neighbourhood, Street
    | order by TotalBikes desc
}
```

**Appeler une fonction stockée :**

```kql
// Appeler la fonction avec un paramètre
GetBikesByNeighbourhood("Chelsea")
```

**Fonction avec paramètre optionnel (valeur par défaut) :**

```kql
.create-or-alter function GetTopNeighbourhoods(topN: int = 10)
{
    Bikestream
    | summarize TotalBikes = sum(No_Bikes) by Neighbourhood
    | top topN by TotalBikes desc
}

// Appel sans argument (utilise la valeur par défaut 10)
GetTopNeighbourhoods()

// Appel avec argument personnalisé
GetTopNeighbourhoods(5)
```

**Avantages des fonctions stockées :**
- Réutilisation du code de requête
- Paramétrage pour des analyses flexibles
- Encapsulation de la logique métier complexe
- Standardisation des métriques clés (utiliser la même formule partout)

### Étape 5 : Requêtes T-SQL équivalentes

La base de données KQL supporte un sous-ensemble de T-SQL via un endpoint SQL compatible. Dans le queryset, vous pouvez switcher vers T-SQL :

```sql
-- Sélectionner les 100 premières lignes
SELECT TOP 100 * FROM Bikestream

-- Sélectionner des colonnes spécifiques avec alias
SELECT TOP 10 Street, No_Empty_Docks AS [Number of Empty Docks]
FROM Bikestream

-- Total de vélos disponibles
SELECT SUM(No_Bikes) AS [Total Number of Bikes]
FROM Bikestream

-- Grouper par quartier
SELECT Neighbourhood, SUM(No_Bikes) AS [Total Number of Bikes]
FROM Bikestream
GROUP BY Neighbourhood

-- Gérer les valeurs nulles avec CASE
SELECT
    CASE
        WHEN Neighbourhood IS NULL OR Neighbourhood = '' THEN 'Unidentified'
        ELSE Neighbourhood
    END AS Neighbourhood,
    SUM(No_Bikes) AS [Total Number of Bikes]
FROM Bikestream
GROUP BY CASE
    WHEN Neighbourhood IS NULL OR Neighbourhood = '' THEN 'Unidentified'
    ELSE Neighbourhood
END

-- Filtrer par quartier et trier
SELECT
    CASE
        WHEN Neighbourhood IS NULL OR Neighbourhood = '' THEN 'Unidentified'
        ELSE Neighbourhood
    END AS Neighbourhood,
    SUM(No_Bikes) AS [Total Number of Bikes]
FROM Bikestream
GROUP BY CASE
    WHEN Neighbourhood IS NULL OR Neighbourhood = '' THEN 'Unidentified'
    ELSE Neighbourhood
END
HAVING Neighbourhood = 'Chelsea'
ORDER BY Neighbourhood ASC;
```

> **Limitations T-SQL sur KQL Database** : Le endpoint T-SQL ne supporte pas `CREATE TABLE`, `INSERT`, `UPDATE`, `DELETE`, ni certaines fonctions avancées T-SQL. Il est recommandé d'utiliser KQL comme langage principal pour les bases de données KQL.

### Question 1

Quelle est la principale différence entre un Eventhouse et un Lakehouse dans Microsoft Fabric ?

A) Un Eventhouse supporte uniquement les données structurées ; un Lakehouse supporte tous les formats  
B) Un Eventhouse est optimisé pour l'ingestion et l'analyse de données en temps réel avec KQL ; un Lakehouse est optimisé pour le stockage batch et l'analyse avec Spark SQL  
C) Un Eventhouse est un conteneur pour les pipelines ; un Lakehouse est un conteneur pour les notebooks  
D) Un Eventhouse utilise le stockage OneLake ; un Lakehouse utilise Azure Blob Storage  

**Réponse correcte : B** — L'Eventhouse (avec ses bases de données KQL) est spécialisé pour les données streaming et temps réel avec ingestion haute fréquence et requêtes en millisecondes. Le Lakehouse est optimisé pour les données historiques avec traitement batch via Spark.

### Question 2

Quelle requête KQL retourne le nombre total de vélos (`No_Bikes`) groupé par quartier (`Neighbourhood`) ?

A) `Bikestream | GROUP BY Neighbourhood | SUM(No_Bikes)`  
B) `Bikestream | summarize Total = sum(No_Bikes) by Neighbourhood`  
C) `SELECT SUM(No_Bikes) FROM Bikestream GROUP BY Neighbourhood`  
D) `Bikestream | aggregate sum(No_Bikes) group by Neighbourhood`  

**Réponse correcte : B** — La syntaxe KQL correcte utilise `summarize` avec une fonction d'agrégation et `by` pour le groupement. Les options A, C et D utilisent des syntaxes SQL ou des opérateurs KQL inexistants.

---

### Question 3

Dans KQL, quelle est la différence entre `sort by` et `order by` ?

A) `sort by` trie en ordre croissant par défaut ; `order by` trie en ordre décroissant  
B) `sort by` fonctionne sur des colonnes numériques ; `order by` fonctionne sur des chaînes  
C) Il n'y a pas de différence — ce sont deux syntaxes pour le même opérateur  
D) `sort by` s'applique aux tables ; `order by` s'applique aux vues  

**Réponse correcte : C** — En KQL, `sort by` et `order by` sont strictement équivalents — deux aliases pour le même opérateur de tri. Par défaut, le tri est décroissant (desc). Pour l'ordre croissant, ajoutez `asc`.

### Question 4

Vous créez une vue matérialisée avec l'option `backfill=true`. Que signifie cette option ?

A) La vue est recalculée entièrement à chaque nouvelle donnée ingérée  
B) La vue s'applique également aux données historiques déjà présentes dans la table  
C) La vue est sauvegardée automatiquement chaque heure  
D) La vue est exportée vers OneLake en parallèle  

**Réponse correcte : B** — L'option `backfill=true` indique que la vue matérialisée doit être calculée sur les données déjà existantes dans la table (données historiques) en plus des nouvelles données. Sans cette option, la vue ne commence à se remplir qu'à partir des données ingérées après sa création.

### Question 5

Quelle commande KQL permet de créer ou mettre à jour une fonction stockée réutilisable ?

A) `CREATE FUNCTION GetBikes(n: string) { ... }`  
B) `.define function GetBikes(n: string) { ... }`  
C) `.create-or-alter function GetBikes(n: string) { ... }`  
D) `STORE PROCEDURE GetBikes @n NVARCHAR(100) AS ...`  

**Réponse correcte : C** — La commande KQL correcte est `.create-or-alter function`. Les commandes de gestion (management commands) en KQL commencent par un point (`.`). L'option A est syntaxe SQL, B et D sont des syntaxes inexistantes ou SQL.

## Résumé
*1 min*

Dans ce module, vous avez découvert les **Eventhouse et bases de données KQL** dans Microsoft Fabric pour analyser des données en temps réel.

**Points clés :**

- Un **Eventhouse** est un conteneur pour les bases de données KQL, optimisé pour l'ingestion et l'analyse de données en temps réel à haute fréquence.

- Les bases de données KQL utilisent le **Kusto Query Language (KQL)**, un langage tabulaire où les données "coulent" d'un opérateur à l'autre via le pipe `|`.

- Les opérateurs KQL fondamentaux sont : `take` (limiter), `project` (sélectionner/renommer colonnes), `where` (filtrer), `summarize` (agréger), `sort by` / `order by` (trier).

- KQL est particulièrement puissant pour les **requêtes temporelles** grâce à des fonctions comme `ago(1h)`, `bin(timestamp, 1h)`, `ingestion_time()`.

- Les **vues matérialisées** précalculent et stockent les résultats d'agrégations fréquentes, offrant des temps de requête extrêmement rapides sur de grands volumes.

- Les **fonctions stockées** encapsulent des requêtes KQL réutilisables avec des paramètres, permettant de standardiser les analyses.

- Un **sous-ensemble de T-SQL** est disponible via le endpoint SQL de la base de données KQL, mais KQL reste le langage recommandé pour ses performances et fonctionnalités supérieures.

- L'**Eventhouse s'intègre nativement** avec les Eventstreams de Fabric pour recevoir des données en streaming depuis Azure Event Hub, IoT Hub et d'autres sources.
