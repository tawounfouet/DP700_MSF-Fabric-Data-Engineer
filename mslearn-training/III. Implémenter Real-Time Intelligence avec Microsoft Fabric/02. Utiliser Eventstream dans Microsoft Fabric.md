# Utiliser Eventstream dans Microsoft Fabric

*57 min*
Module *(7 Unités)*
Intermédiaire
Ingénieur Data
Analyste de données
Microsoft Fabric

Le flux d'événements (Eventstream) dans Real-Time Intelligence (RTI) vous permet d'ingérer, de transformer et d'acheminer des données en temps réel depuis de nombreuses sources vers diverses destinations, sans écrire une seule ligne de code.

---

## Objectifs d'apprentissage

Dans ce module, vous allez apprendre à :

- Décrire l'architecture et les composants d'un Eventstream
- Connecter des sources de données variées (Event Hubs, IoT Hub, Kafka, CDC, données d'exemple)
- Configurer des destinations pour router les événements (Eventhouse, Lakehouse, Activator, Custom app)
- Appliquer des transformations sans code sur des flux d'événements (filtre, agrégation, Group by, Join)
- Comprendre les fenêtres temporelles (tumbling, hopping, session)
- Publier et monitorer un Eventstream en production

---

## Prérequis

- Connaissance des concepts de base du streaming de données
- Familiarité avec Microsoft Fabric (workspaces, items)
- Avoir complété le module "Bien démarrer avec Real-Time Intelligence dans Microsoft Fabric" (recommandé)
- Accès à un tenant Microsoft Fabric avec une capacité F4+ ou Trial

## Présentation

*2 min*
Effectué — 100 XP

Imaginez une ville intelligente qui collecte en temps réel les données de milliers de capteurs : des vélos en libre-service signalant leur position et leur disponibilité, des bus transmettant leur occupation et leur retard, des feux de circulation renvoyant leur état. Chaque seconde, des milliers d'événements arrivent simultanément depuis des sources hétérogènes.

Comment ingérer tout cela de manière fiable, le transformer à la volée (calculer le nombre total de vélos disponibles par quartier toutes les 5 secondes, par exemple) et le distribuer vers plusieurs systèmes — un entrepôt temps réel pour l'analytique, un système d'alerte pour les incidents, une application mobile pour les usagers ?

C'est exactement ce que **Eventstream** résout dans Microsoft Fabric. C'est le pipeline de streaming universel de Real-Time Intelligence : un composant visuel, sans code, capable de connecter n'importe quelle source de données en temps réel, d'appliquer des transformations sophistiquées et d'acheminer les événements vers de multiples destinations simultanément.

## Composants d'Eventstream

*3 min*
Effectué — 100 XP

### Architecture générale

Un Eventstream est composé de trois grandes catégories d'éléments organisés dans un éditeur visuel de type canvas (glisser-déposer) :

```
┌──────────────────────────────────────────────────────────────────┐
│                        EVENTSTREAM CANVAS                        │
│                                                                  │
│  ┌──────────┐    ┌───────────────────────┐    ┌──────────────┐  │
│  │  SOURCE  │───▶│  TRANSFORMATIONS      │───▶│ DESTINATION  │  │
│  │          │    │  (optionnel)          │    │              │  │
│  │ Event    │    │  Filter               │    │ Eventhouse   │  │
│  │  Hubs    │    │  Manage fields        │    │              │  │
│  │ IoT Hub  │    │  Aggregate            │    │ Lakehouse    │  │
│  │  Kafka   │    │  Group by             │    │              │  │
│  │   CDC    │    │  Join                 │    │ Activator    │  │
│  │  Sample  │    │  Union                │    │              │  │
│  └──────────┘    │  Expand               │    │ Custom app   │  │
│                  └───────────────────────┘    └──────────────┘  │
└──────────────────────────────────────────────────────────────────┘
```

### Le canvas de conception

L'interface principale d'Eventstream est un **canvas de conception** interactif où vous construisez visuellement votre pipeline de streaming. Chaque élément est représenté par un nœud, et vous créez des connexions entre les nœuds en les reliant graphiquement.

Le canvas offre plusieurs fonctionnalités :
- **Glisser-déposer** : faites glisser des sources, transformations et destinations sur le canvas
- **Connexions visuelles** : tirez des flèches pour relier les nœuds entre eux
- **Aperçu des données** : cliquez sur un nœud pour voir un aperçu des données qui le traversent en temps réel
- **Data insights** : onglet en bas du canvas montrant des métriques d'ingestion (événements par seconde, latence, etc.)
- **Mode Édition / Mode Visualisation** : basculez entre la conception et la vue opérationnelle

### Flux de données et streams dérivés

Un Eventstream possède toujours un **stream par défaut** qui représente le flux brut de données depuis la source. À partir de ce stream par défaut, vous pouvez créer des **streams dérivés (derived streams)** : des flux transformés qui peuvent être partagés dans le Real-Time Hub pour que d'autres équipes les consomment.

### Capacités avancées (Enhanced capabilities)

Lors de la création d'un Eventstream, vous pouvez activer les **Enhanced capabilities** pour débloquer un ensemble étendu de sources, de transformations et de destinations. En mode standard, seules les sources Azure Event Hubs, IoT Hub, Custom app et les données d'exemple sont disponibles.

## Sources et destinations Eventstream

*6 min*
Effectué — 100 XP

### Sources disponibles

Les sources sont les points d'entrée des données dans votre Eventstream. Voici les principales catégories :

#### Sources Azure natives

**Azure Event Hubs**
Azure Event Hubs est un service de streaming d'événements managé, capable d'ingérer des millions de messages par seconde. Il est couramment utilisé pour les télémétries d'applications, les logs d'activité et les données à haut débit.

Pour le connecter à Eventstream, vous fournissez :
- Le nom de l'Event Hub namespace
- Le nom de l'Event Hub spécifique
- La clé d'accès ou une identité managée

**Azure IoT Hub**
IoT Hub est le service Azure conçu spécifiquement pour les communications Device-to-Cloud. Il supporte les protocoles MQTT, AMQP et HTTPS pour la communication avec les appareils IoT.

Eventstream peut consommer le flux d'événements IoT Hub pour ingérer des données de capteurs, d'appareils industriels ou de systèmes embarqués directement dans Fabric.

**Azure Event Grid**
Event Grid prend en charge les événements MQTT et non-MQTT. Vous pouvez ingérer des messages depuis un namespace Azure Event Grid.

#### Sources de bases de données (CDC — Change Data Capture)

La CDC capture les changements (inserts, updates, deletes) dans des bases de données transactionnelles et les stream comme événements. Eventstream supporte CDC pour :

- **Azure SQL Database CDC** : capture les changements dans une base Azure SQL
- **Azure SQL Managed Instance CDC** : pour les instances SQL Managed
- **SQL Server sur VM CDC** : pour SQL Server hébergé sur une machine virtuelle
- **PostgreSQL Database CDC** : pour les bases PostgreSQL (Azure Database for PostgreSQL)
- **MySQL Database CDC** : pour Azure Database for MySQL
- **Azure Cosmos DB CDC** : pour Cosmos DB (API SQL/Core)
- **MongoDB CDC** : capture les changements dans des collections MongoDB

> **Note DeltaFlow** : Pour les sources CDC, la fonctionnalité **DeltaFlow (Preview)** transforme automatiquement les événements CDC bruts au format Debezium JSON en événements analytiques prêts à l'emploi, avec gestion automatique des schémas.

#### Sources cloud externes

- **Apache Kafka** (clusters Kafka auto-hébergés ou managés)
- **Confluent Cloud for Apache Kafka** (Kafka managé sur Confluent)
- **Amazon Kinesis Data Streams** (streaming AWS)
- **Google Cloud Pub/Sub** (messaging GCP)
- **Amazon MSK (Managed Streaming for Apache Kafka)**
- **MQTT** (broker MQTT générique, protocole IoT standard)
- **Cribl** (pipeline de données opérationnelles)
- **Solace PubSub+** (messaging enterprise)

#### Sources Fabric natives

- **Fabric workspace item events** : événements générés par les actions sur les items Fabric (création, modification, suppression)
- **Fabric OneLake events** : changements dans les fichiers et dossiers OneLake
- **Fabric job events** : événements de pipeline, notebooks, semantic model refresh
- **Azure Blob Storage events** : création/remplacement/suppression de blobs

#### Sources spécialisées

- **Real-time weather** : données météo en temps réel pour diverses localisations
- **HTTP (preview)** : ingestion depuis n'importe quelle API HTTP externe
- **Sample data** : données d'exemple intégrées pour les tests et développements
  - **Bicycles** : données de vélos en libre-service (rue, nombre de vélos, docks disponibles, coordonnées GPS)
  - **Yellow Taxi** : courses de taxi à New York
  - **Stock Market** : prix boursiers en temps réel (symbole, bid price, ask price)
  - **Buses** : données de transport en commun
  - **S&P 500 companies stocks** : actions du S&P 500

### Destinations disponibles

Les destinations sont les systèmes qui reçoivent les données transformées depuis votre Eventstream.

#### Eventhouse (KQL Database)

La destination **Eventhouse** est la plus courante pour les scénarios RTI. Elle permet d'ingérer les événements directement dans une table KQL Database.

Deux modes d'ingestion sont disponibles :
- **Direct ingestion** : les événements arrivent tels quels dans la table
- **Event processing before ingestion** : les événements passent d'abord par une transformation (agrégation, filtrage) avant d'être stockés

Paramètres à configurer :
- Workspace de destination
- Eventhouse cible
- KQL Database cible
- Table de destination (existante ou nouvelle)
- Format des données d'entrée (JSON, CSV, Avro, Parquet...)

#### Lakehouse

La destination **Lakehouse** convertit les événements en temps réel en format Delta Lake et les stocke dans les tables du Lakehouse. C'est utile pour les scénarios où vous souhaitez combiner des données temps réel avec des données historiques dans un environnement Spark.

#### Activator

La destination **Activator** connecte directement votre stream à un Activator Fabric. Cela permet de déclencher des règles et des alertes directement depuis les événements du stream, sans passer par une KQL Database intermédiaire.

#### Custom endpoint (Custom app)

La destination **Custom endpoint** expose un endpoint Kafka ou AMQP auquel vos applications externes peuvent se connecter pour consommer les événements. C'est utile pour intégrer Eventstream avec des systèmes existants hors de Fabric.

#### Derived stream

Un **Derived stream** est un flux intermédiaire créé après une ou plusieurs transformations. Il peut être partagé dans le Real-Time Hub et utilisé comme source par d'autres Eventstreams ou services. C'est un pattern puissant pour éviter la duplication de logique de transformation.

#### Spark Notebook (Preview)

La destination **Spark Notebook** permet de charger un notebook existant pour traiter les événements du stream via Spark Structured Streaming.

## Transformations Eventstream

*5 min*
Effectué — 100 XP

### L'éditeur de traitement d'événements

L'éditeur de traitement d'événements (event processor editor) est l'interface visuelle de transformation d'Eventstream. C'est un éditeur no-code basé sur le drag-and-drop qui vous permet de construire des pipelines de transformation complexes sans écrire de code.

Chaque nœud de transformation prend en entrée un stream (le stream par défaut ou le résultat d'une transformation précédente) et produit un stream transformé en sortie.

### Les transformations disponibles

#### Filter — Filtrage d'événements

Le **Filter** conserve uniquement les événements qui satisfont une condition sur la valeur d'un champ.

Exemple : conserver uniquement les événements où `Temperature > 80` pour ne surveiller que les capteurs en surchauffe.

Opérateurs disponibles selon le type de données :
- Texte : `is equal to`, `is not equal to`, `contains`, `does not contain`, `starts with`, `ends with`, `is null`, `is not null`
- Numérique : `=`, `!=`, `>`, `>=`, `<`, `<=`, `is null`, `is not null`

#### Manage fields — Gestion des colonnes

**Manage fields** permet de modifier la structure du stream en ajoutant, supprimant, renommant ou convertissant des colonnes.

Cas d'usage typiques :
- Supprimer des colonnes sensibles (PII) avant de stocker les données
- Renommer des colonnes pour correspondre au schéma d'une table existante
- Convertir un champ string en numérique ou datetime
- Ajouter une colonne calculée (ex : `TemperatureFahrenheit = Temperature * 1.8 + 32`)

#### Aggregate — Agrégation continue

**Aggregate** calcule des agrégations (somme, minimum, maximum, moyenne) en continu à chaque nouvel événement arrivant. À la différence de Group by, Aggregate émet un résultat à chaque événement entrant.

Exemple : calculer la moyenne mobile de température par appareil.

#### Group by — Agrégation par fenêtre temporelle

**Group by** est la transformation la plus puissante pour l'analytique temps réel. Elle calcule des agrégations sur des **fenêtres de temps**, regroupées par une ou plusieurs dimensions.

Paramètres clés :
- **Aggregate type** : Sum, Count, Average, Min, Max
- **Field** : le champ sur lequel appliquer l'agrégation
- **Group aggregations by** : dimensions de groupement (ex : par rue, par appareil, par région)
- **Time window** : type de fenêtre temporelle

**Types de fenêtres temporelles :**

| Type | Description | Cas d'usage |
|------|-------------|------------|
| **Tumbling** | Fenêtres non chevauchantes de durée fixe. La fenêtre 1 se termine et la fenêtre 2 commence immédiatement après. | Totaux par intervalle de 5 secondes |
| **Hopping** | Fenêtres se chevauchant. Une fenêtre de 10 secondes qui avance toutes les 5 secondes. | Moyennes glissantes |
| **Session** | Fenêtres dynamiques basées sur l'activité. La fenêtre s'ouvre à la 1ère activité et se ferme après un délai d'inactivité. | Sessions utilisateur |

Exemple de configuration Group by pour compter les vélos par rue toutes les 5 secondes :
- **Operation name** : GroupByStreet
- **Aggregate type** : Sum
- **Field** : No_Bikes
- **Group by** : Street
- **Time window** : Tumbling
- **Duration** : 5 seconds

Le résultat contient les colonnes : `Street`, `SUM_No_Bikes`, `Window_End_Time`

#### Union — Fusion de streams

**Union** combine deux ou plusieurs streams en un seul, à condition qu'ils partagent des colonnes avec le même nom et le même type de données. Les colonnes qui ne correspondent pas sont ignorées.

Utile pour fusionner des données provenant de sources différentes ayant le même schéma (ex : capteurs IoT de différents sites).

#### Expand — Expansion de tableaux

**Expand** crée une nouvelle ligne pour chaque valeur dans un champ de type tableau (array). Utile pour dénormaliser des données JSON imbriquées.

Exemple : un événement contenant un tableau de lectures de capteurs devient autant d'événements séparés, un par lecture.

#### Join — Jointure de streams

**Join** combine les données de deux streams sur un critère de correspondance, similaire à un JOIN SQL. Utile pour enrichir un stream avec des données de référence provenant d'un autre stream.

### Traitement via SQL (Preview)

En plus des transformations no-code, Eventstream supporte un **opérateur SQL** pour les utilisateurs qui préfèrent une approche code-first. Vous pouvez écrire des expressions SQL incluant des jointures, des fenêtres temporelles et des agrégations personnalisées.

## Exercice — Ingérer des données en temps réel avec Eventstream dans Microsoft Fabric

*30 min*
Effectué — 100 XP

### Objectif du lab

Dans cet exercice, vous allez créer un Eventstream complet qui ingère des données de vélos en libre-service, les stocke dans une KQL Database, puis applique une transformation d'agrégation pour calculer des statistiques par rue.

### Étape 1 : Créer un workspace et un Eventhouse

1. Connectez-vous à [https://app.fabric.microsoft.com](https://app.fabric.microsoft.com)
2. Créez un nouveau workspace avec une capacité Fabric
3. Dans le workspace, créez un **Eventhouse** (via **+ New item > Eventhouse**)
4. Notez que l'Eventhouse crée automatiquement une KQL Database du même nom

### Étape 2 : Créer l'Eventstream depuis la KQL Database

1. Ouvrez la KQL Database dans votre Eventhouse
2. Cliquez sur **Get data**
3. Sélectionnez **Eventstream > New eventstream**
4. Nommez l'Eventstream `Bicycle-data`

### Étape 3 : Ajouter la source de données d'exemple

1. Dans le canvas Eventstream, cliquez sur le nœud source et sélectionnez **Use sample data**
2. Nommez la source `Bicycles`
3. Sélectionnez le jeu de données **Bicycles**
4. Le canvas affiche maintenant la source **Bicycles** connectée au stream par défaut **Bicycle-data**

### Étape 4 : Configurer la destination Eventhouse

1. Cliquez sur le tile **Transform events or add destination**
2. Recherchez et sélectionnez **Eventhouse**
3. Configurez la destination :
   - **Data ingestion mode** : Event processing before ingestion
   - **Destination name** : `bikes-table`
   - **Workspace** : votre workspace
   - **Eventhouse** : votre Eventhouse
   - **KQL database** : votre KQL Database
   - **KQL Destination table** : créez une nouvelle table `bikes` (cliquez sur **Create new** sous la zone de texte)
   - **Input data format** : JSON
4. Cliquez **Save**, puis **Publish**

### Étape 5 : Vérifier l'ingestion des données

1. Attendez 1-2 minutes que les données commencent à arriver
2. Sélectionnez le nœud `bikes-table` dans le canvas
3. Observez l'aperçu des données dans le panneau **Data preview** en bas du canvas
4. Allez dans votre KQL Database et rafraîchissez — vous devriez voir la table `bikes`

### Étape 6 : Interroger les données ingérées avec KQL

1. Dans votre KQL Database, ouvrez le queryset associé
2. Exécutez cette requête pour voir les données récentes :

```kql
// Données ingérées dans les dernières 24 heures
bikes
| where ingestion_time() between (now(-1d) .. now())
```

3. Affichez un aperçu de la structure :

```kql
// Aperçu de la structure (rue, nombre de vélos)
bikes
| project Street, No_Bikes
| take 10
```

4. Calculez le total de vélos par quartier :

```kql
bikes
| summarize ["Total Number of Bikes"] = sum(No_Bikes) by Neighbourhood
| project Neighbourhood = case(
    isempty(Neighbourhood) or isnull(Neighbourhood), 
    "Unidentified", 
    Neighbourhood), 
  ["Total Number of Bikes"]
| sort by Neighbourhood asc
```

### Étape 7 : Ajouter une transformation Group by

1. Revenez dans votre Eventstream `Bicycle-data`
2. Cliquez sur **Edit** dans la toolbar
3. Dans le menu **Transform events**, sélectionnez **Group by**
4. Reliez la sortie du nœud **Bicycle-data** à l'entrée du nœud **Group by**
5. Éditez le nœud **Group by** (icône crayon) :
   - **Operation name** : GroupByStreet
   - **Aggregate type** : Sum
   - **Field** : No_Bikes → créez la fonction **SUM of No_Bikes**
   - **Group aggregations by** : Street
   - **Time window** : Tumbling
   - **Duration** : 5 seconds
   - **Offset** : 0 seconds
6. Sauvegardez la transformation

### Étape 8 : Ajouter une seconde destination pour les données agrégées

1. Cliquez sur le **+** à droite du nœud `GroupByStreet`
2. Ajoutez un nœud **Eventhouse**
3. Configurez :
   - **Data ingestion mode** : Event processing before ingestion
   - **Destination name** : `bikes-by-street-table`
   - **Destination table** : créez une nouvelle table `bikes-by-street`
   - **Input data format** : JSON
4. Sauvegardez, puis **Publish**

### Étape 9 : Interroger les données agrégées

Après 1-2 minutes, vérifiez les données transformées :

```kql
// Total de vélos par rue dans chaque fenêtre de 5 secondes
['bikes-by-street']
| summarize TotalBikes = sum(tolong(SUM_No_Bikes)) by Window_End_Time, Street
| sort by Window_End_Time desc, Street asc
```

Les résultats montrent le nombre de vélos par rue dans chaque fenêtre temporelle de 5 secondes. Notez les colonnes `Street`, `SUM_No_Bikes` et `Window_End_Time`.

## Évaluation du module

*10 min*

### Vérification des connaissances

**Question 1**
Vous devez capturer des changements (inserts, updates, deletes) dans une base de données Azure SQL et les ingérer dans Microsoft Fabric en temps réel. Quelle source Eventstream utilisez-vous ?

- A) Azure Event Hubs
- B) Azure SQL Database CDC ✓
- C) Custom endpoint
- D) Sample data

*Explication : CDC (Change Data Capture) est spécifiquement conçu pour capturer les changements dans des bases de données transactionnelles. Azure SQL Database CDC est le connecteur approprié pour Azure SQL.*

---

**Question 2**
Dans votre Eventstream, vous voulez calculer la moyenne des températures par appareil toutes les 10 secondes (chaque fenêtre ne se chevauche pas avec la suivante). Quel type de fenêtre temporelle choisissez-vous dans la transformation Group by ?

- A) Session
- B) Hopping
- C) Tumbling ✓
- D) Sliding

*Explication : Les fenêtres **Tumbling** sont non chevauchantes et de durée fixe. C'est le type adapté quand chaque intervalle de calcul doit être indépendant du suivant.*

---

**Question 3**
Vous avez deux Eventstreams provenant de deux sites de production différents. Les deux streams ont exactement le même schéma. Vous voulez les combiner en un seul stream pour les analyser ensemble. Quelle transformation utilisez-vous ?

- A) Join
- B) Expand
- C) Aggregate
- D) Union ✓

*Explication : **Union** fusionne plusieurs streams ayant des colonnes de même nom et type en un seul stream. **Join** est utilisé pour combiner deux streams sur un critère de correspondance, pas pour fusionner des sources similaires.*

---

**Question 4**
Quel est l'avantage du mode "Event processing before ingestion" par rapport à "Direct ingestion" lors de l'envoi de données vers un Eventhouse ?

- A) Les données arrivent plus vite dans l'Eventhouse
- B) Les données peuvent être transformées (filtrées, agrégées) avant d'être stockées, réduisant le volume stocké ✓
- C) Les données sont automatiquement indexées par l'Eventhouse
- D) Il n'y a pas de différence fonctionnelle, seulement une différence de performance

*Explication : "Event processing before ingestion" permet d'appliquer des transformations (agrégations, filtres, calculs) sur les données avant qu'elles ne soient stockées dans la KQL Database. Cela peut réduire significativement le volume de données stockées et faciliter les requêtes ultérieures.*

---

**Question 5**
Vous avez un Eventstream qui ingère des données de livraison de colis. Vous souhaitez déclencher automatiquement un email chaque fois qu'un colis médical dépasse 20°C pendant le transport. Quelle destination Eventstream utilisez-vous pour cela ?

- A) Eventhouse
- B) Lakehouse
- C) Activator ✓
- D) Custom endpoint

*Explication : La destination **Activator** permet de connecter directement l'Eventstream à un Activator Fabric, qui peut surveiller des conditions (température > 20°C) et déclencher des actions (email) sans passer par un intermédiaire.*

## Résumé

*1 min*

Dans ce module, vous avez exploré en profondeur **Eventstream**, le composant central d'ingestion et de transformation de Real-Time Intelligence dans Microsoft Fabric.

Les points clés à retenir :

- **Eventstream** est un pipeline de streaming no-code, configuré via un éditeur visuel glisser-déposer
- Il supporte une **large variété de sources** : Azure Event Hubs, IoT Hub, Apache Kafka, CDC databases (SQL, PostgreSQL, MySQL, Cosmos DB), sources cloud (AWS Kinesis, GCP Pub/Sub, Confluent), MQTT, données Fabric natives et données d'exemple
- Les **destinations supportées** incluent Eventhouse, Lakehouse, Activator, Custom endpoint et Derived streams
- Les **transformations disponibles** sont : Filter, Manage fields, Aggregate, Group by, Union, Expand, Join (+ SQL pour les cas avancés)
- Les **fenêtres temporelles** (Tumbling, Hopping, Session) permettent de calculer des agrégations sur des intervalles de temps spécifiques
- La fonctionnalité **DeltaFlow** transforme automatiquement les événements CDC en données analytiques prêtes à l'emploi
- Il est possible d'attacher **plusieurs destinations simultanément** à un même Eventstream sans interférence
- Les **Derived streams** permettent de partager des flux transformés dans le Real-Time Hub pour une consommation par d'autres services
