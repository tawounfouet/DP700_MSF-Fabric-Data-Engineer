Un Eventhouse dans Microsoft Fabric est un conteneur qui héberge une ou plusieurs bases de données KQL pour stocker et analyser des données en temps réel. Basé sur la technologie Azure Data Explorer (ADX), il permet d'interroger des milliards d'événements en quelques secondes grâce au Kusto Query Language (KQL).

Dans un monde où les décisions doivent être prises en secondes, pas en heures, les systèmes d'analytique traditionnels montrent leurs limites. Un entrepôt de données typique peut prendre des minutes pour ingérer et rendre disponibles de nouvelles données. Mais que se passe-t-il si vous devez détecter une fraude bancaire en millisecondes, surveiller des équipements industriels en temps réel, ou réagir à des événements météorologiques critiques dès qu'ils surviennent ?

C'est le problème que l'**Eventhouse** résout dans Microsoft Fabric. C'est le moteur de stockage et d'interrogation de Real-Time Intelligence, spécialement conçu et optimisé pour les **données d'événements en temps réel** : télémétrie, logs, données IoT, séries temporelles, données financières.

L'Eventhouse est basé sur la technologie **Azure Data Explorer (ADX)**, un service éprouvé en production chez Microsoft pour l'analyse de téraoctets de logs et de télémétries à l'échelle planétaire. Il combine une ingestion ultra-rapide avec des requêtes sub-secondes sur des milliards de lignes.

Dans ce module, vous allez apprendre à maîtriser l'Eventhouse et le Kusto Query Language (KQL) — l'outil analytique le plus puissant de l'arsenal RTI de Microsoft Fabric.

### Architecture de l'Eventhouse

Un Eventhouse est organisé en couches :

```
┌─────────────────────────────────────────────────────────────┐
│                        EVENTHOUSE                           │
│   Conteneur de niveau projet (partage capacité/ressources)  │
│                                                             │
│  ┌─────────────────────────────────────────────────────┐   │
│  │              KQL DATABASE 1 (principale)            │   │
│  │                                                     │   │
│  │  ┌───────────┐  ┌──────────────┐  ┌────────────┐   │   │
│  │  │  Tables   │  │  Materialized│  │ Stored     │   │   │
│  │  │           │  │    Views     │  │ Functions  │   │   │
│  │  │ stock     │  │              │  │            │   │   │
│  │  │ telemetry │  │              │  │            │   │   │
│  │  └───────────┘  └──────────────┘  └────────────┘   │   │
│  │                                                     │   │
│  │  ┌─────────────────────────────────────────────┐   │   │
│  │  │   KQL Queryset (fichier de requêtes)        │   │   │
│  │  └─────────────────────────────────────────────┘   │   │
│  └─────────────────────────────────────────────────────┘   │
│                                                             │
│  ┌─────────────────────────────────────────────────────┐   │
│  │              KQL DATABASE 2 (optionnel)             │   │
│  └─────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────┘
```

Un **Eventhouse** est le conteneur de plus haut niveau. Il peut contenir plusieurs **KQL Databases**. Chaque KQL Database contient des tables, des vues matérialisées, des fonctions stockées et un queryset associé.

Cette organisation en conteneur permet à un Eventhouse de **partager la capacité et les ressources** entre plusieurs databases d'un même projet, optimisant ainsi les coûts.

### Caractéristiques clés d'un Eventhouse

**Optimisation temporelle**
Les données dans un Eventhouse sont **automatiquement organisées par ordre chronologique d'arrivée**. Cela permet des requêtes ultra-rapides sur des plages de temps : interroger "les événements des dernières 5 minutes" est extrêmement efficace car le moteur sait exactement où chercher dans le stockage.

**Support de multiples formats de données**
L'Eventhouse accepte des données structurées (tables avec schéma fixe), semi-structurées (JSON, XML avec schéma variable) et non-structurées (texte libre, logs). Il peut donc gérer aussi bien des événements IoT bien définis que des logs applicatifs libres.

**Scalabilité automatique**
L'Eventhouse scale automatiquement selon la charge d'ingestion et de requêtes, sans configuration manuelle. Vous n'avez pas à prévoir la capacité à l'avance.

**Intégration OneLake**
Les données stockées dans un Eventhouse peuvent être exposées dans **OneLake** comme une copie logique unique, sans duplication physique. Cela permet à d'autres expériences Fabric (notebooks Spark, Power BI, Data Factory) d'accéder aux mêmes données.

**Monitoring et observabilité**
L'Eventhouse fournit un tableau de bord système intégré avec :
- Taux d'ingestion (events/seconde)
- Top databases les plus interrogées
- Top databases les plus ingérées
- Utilisation des ressources (CPU, mémoire)
- Activité des utilisateurs

### Créer un Eventhouse

Pour créer un Eventhouse dans Microsoft Fabric :
1. Naviguez vers votre workspace
2. Cliquez sur **+ New item**
3. Sous la section **Real-Time Intelligence**, sélectionnez **Eventhouse**
4. Donnez-lui un nom unique

À la création, un Eventhouse inclut automatiquement :
- Une **KQL Database** du même nom
- Un **KQL Queryset** associé à la database (fichier de requêtes d'exploration)

### Modes d'accès aux données

Une fois les données dans l'Eventhouse, vous pouvez les interroger via plusieurs interfaces :

1. **KQL Queryset** : éditeur de requêtes intégré supportant KQL et T-SQL
2. **Real-Time Dashboard** : visualisation directe depuis les requêtes KQL
3. **Power BI** : via le connecteur Fabric ou le SQL analytics endpoint
4. **Notebooks Fabric** : accès direct depuis Python, PySpark ou Spark SQL
5. **SQL analytics endpoint** (managé) : surface T-SQL complète pour les outils BI
6. **APIs REST** : pour les intégrations programmatiques

## Utiliser KQL efficacement

*5 min*
Effectué — 100 XP

### Syntaxe et structure de KQL

Le Kusto Query Language (KQL) est un langage de requête basé sur des **opérateurs en pipeline**. La structure de base est :

```kql
NomDeTable
| Operateur1 [arguments]
| Operateur2 [arguments]
| ...
```

La lecture se fait de haut en bas : chaque ligne prend en entrée le résultat de la ligne précédente. Le `|` (pipe) est l'opérateur de composition.

### Les opérateurs fondamentaux

#### `take` — Récupérer un nombre limité de lignes

```kql
// Afficher les 100 premières lignes
Bikestream
| take 100
```

Équivalent SQL : `SELECT TOP 100 *`

#### `project` — Sélectionner et renommer des colonnes

```kql
// Sélectionner des colonnes spécifiques
Bikestream
| project Street, No_Bikes
| take 10

// Renommer une colonne
Bikestream
| project Street, ["Number of Empty Docks"] = No_Empty_Docks
| take 10
```

Équivalent SQL : `SELECT Street, No_Empty_Docks AS [Number of Empty Docks]`

#### `where` — Filtrer les lignes

```kql
// Filtrer par quartier
Bikestream
| where Neighbourhood == "Chelsea"

// Filtrer par plage de temps (très courant en RTI)
Bikestream
| where ingestion_time() > ago(1h)

// Combiner plusieurs conditions
Bikestream
| where Neighbourhood == "Chelsea" and No_Bikes > 5
```

Équivalent SQL : `WHERE Neighbourhood = 'Chelsea'`

La fonction `ago()` est spécifique à KQL et très utile : `ago(5m)` signifie "il y a 5 minutes", `ago(24h)` = "il y a 24 heures", `ago(7d)` = "il y a 7 jours".

#### `summarize` — Agréger des données

```kql
// Compter le total de vélos
Bikestream
| summarize ["Total Number of Bikes"] = sum(No_Bikes)

// Agréger par dimension
Bikestream
| summarize ["Total Number of Bikes"] = sum(No_Bikes) by Neighbourhood

// Agréger avec gestion des valeurs nulles
Bikestream
| summarize ["Total Number of Bikes"] = sum(No_Bikes) by Neighbourhood
| project Neighbourhood = case(
    isempty(Neighbourhood) or isnull(Neighbourhood), 
    "Unidentified", 
    Neighbourhood), 
  ["Total Number of Bikes"]
```

Fonctions d'agrégation disponibles : `sum()`, `count()`, `avg()`, `min()`, `max()`, `stdev()`, `dcount()` (distinct count), `countif()`, `sumif()`, `arg_max()`, `arg_min()`

#### `order by` / `sort by` — Trier les résultats

```kql
// Tri croissant par quartier
Bikestream
| summarize ["Total Number of Bikes"] = sum(No_Bikes) by Neighbourhood
| order by Neighbourhood asc

// Tri décroissant par nombre de vélos
Bikestream
| summarize total = sum(No_Bikes) by Neighbourhood
| sort by total desc
```

`order by` et `sort by` sont synonymes en KQL.

#### `extend` — Ajouter des colonnes calculées

```kql
// Ajouter une colonne de statut
Bikestream
| extend Status = iff(No_Bikes > 5, "Available", "Low")
| project Street, No_Bikes, Status

// Calcul de différence de temps
stock
| extend TimeSinceEvent = now() - ["time"]
| project symbol, bidPrice, TimeSinceEvent
```

#### `join` — Joindre deux tables

```kql
// Inner join entre deux tables
Bikestream
| join kind=inner (
    StationInfo
    | project StationId, StationName, Capacity
) on $left.StationId == $right.StationId
| project Street, Neighbourhood, StationName, No_Bikes, Capacity
```

#### `render` — Visualiser les résultats

KQL inclut un opérateur de visualisation intégré :

```kql
// Graphique en courbes
stock
| where ["time"] > ago(1h)
| summarize avgPrice = avg(todecimal(bidPrice)) by bin(["time"], 5m), symbol
| render timechart

// Graphique en barres
Bikestream
| summarize total = sum(No_Bikes) by Neighbourhood
| render barchart

// Graphique circulaire
Bikestream
| summarize count() by Neighbourhood
| render piechart
```

### Requêtes sur des séries temporelles

L'Eventhouse excelle pour les requêtes sur des séries temporelles. La fonction `bin()` permet de regrouper les événements dans des intervalles réguliers :

```kql
// Agrégation par fenêtres de 5 minutes
stock
| where ["time"] > ago(1h)
| summarize avgPrice = avg(todecimal(bidPrice)) by bin(["time"], 5m), symbol
| order by ["time"] asc
| render timechart

// Détecter les périodes creuses (faible activité)
Bikestream
| where ingestion_time() > ago(24h)
| summarize count() by bin(ingestion_time(), 30m)
| render timechart
```

### Requêtes analytiques avancées

```kql
// Top N par catégorie
Bikestream
| summarize TotalBikes = sum(No_Bikes) by Street
| top 10 by TotalBikes desc

// Détecter des anomalies dans une série temporelle
stock
| where ["time"] > ago(24h)
| summarize avgPrice = avg(todecimal(bidPrice)) by bin(["time"], 5m), symbol
| where symbol == "AAPL"
| extend anomaly = series_decompose_anomalies(pack_array(avgPrice), 1.5)

// Analyse de corrélation entre deux colonnes
Bikestream
| summarize correlation = pearsonCorrelation(No_Bikes, No_Empty_Docks)
    by Neighbourhood

// Calcul percentile (p50, p95, p99)
stock
| where ["time"] > ago(7d)
| summarize p50 = percentile(todecimal(bidPrice), 50),
             p95 = percentile(todecimal(bidPrice), 95),
             p99 = percentile(todecimal(bidPrice), 99) by symbol
```

### Requêtes KQL depuis la page d'interrogation avec données d'exemple (RTISample)

Quand vous utilisez l'échantillon RTISample de Microsoft, les requêtes s'appliquent à la table `Bikestream` :

```kql
// Filtrer par quartier Chelsea
Bikestream
| where Neighbourhood == "Chelsea"
| summarize ["Total Number of Bikes"] = sum(No_Bikes) by Neighbourhood
| project Neighbourhood = case(
    isempty(Neighbourhood) or isnull(Neighbourhood), 
    "Unidentified", 
    Neighbourhood), 
  ["Total Number of Bikes"]
| sort by Neighbourhood asc
```

### T-SQL dans un Eventhouse

L'Eventhouse fournit un **endpoint T-SQL managé** qui émule Microsoft SQL Server, permettant aux équipes familières avec SQL de requêter les données sans apprendre KQL. Cependant, cet endpoint a des limitations : il ne supporte pas CREATE/ALTER/DROP TABLE, INSERT/UPDATE/DELETE, ni toutes les fonctions T-SQL avancées.

```sql
-- Equivalent en T-SQL des requêtes KQL précédentes

-- Récupérer 100 lignes
SELECT TOP 100 * FROM Bikestream

-- Sélectionner des colonnes spécifiques avec alias
SELECT TOP 10 Street, No_Empty_Docks AS [Number of Empty Docks]
FROM Bikestream

-- Agréger par quartier
SELECT 
    CASE 
        WHEN Neighbourhood IS NULL OR Neighbourhood = '' THEN 'Unidentified'
        ELSE Neighbourhood
    END AS Neighbourhood,
    SUM(No_Bikes) AS [Total Number of Bikes]
FROM Bikestream
GROUP BY CASE 
    WHEN Neighbourhood IS NULL OR Neighbourhood = '' THEN 'Unidentified'
    ELSE Neighbourhood
END
ORDER BY Neighbourhood ASC

-- Filtrer par quartier Chelsea
SELECT 
    CASE 
        WHEN Neighbourhood IS NULL OR Neighbourhood = '' THEN 'Unidentified'
        ELSE Neighbourhood
    END AS Neighbourhood,
    SUM(No_Bikes) AS [Total Number of Bikes]
FROM Bikestream
GROUP BY CASE 
    WHEN Neighbourhood IS NULL OR Neighbourhood = '' THEN 'Unidentified'
    ELSE Neighbourhood
END
HAVING Neighbourhood = 'Chelsea'
ORDER BY Neighbourhood ASC
```

**Recommandation** : Privilégiez KQL pour les performances et les capacités analytiques avancées. Utilisez T-SQL uniquement si vous devez intégrer avec des outils ou des équipes qui ne maîtrisent pas KQL.

### Vues matérialisées (Materialized Views)

Une **vue matérialisée** est une requête d'agrégation pré-calculée dont le résultat est mis à jour automatiquement en continu. Contrairement à une vue ordinaire (qui recalcule à chaque requête), une vue matérialisée stocke physiquement les résultats agrégés, permettant des requêtes instantanées sur des datasets très volumineux.

#### Quand utiliser une vue matérialisée ?

Les vues matérialisées sont idéales pour :
- Des agrégations fréquemment utilisées (comptages, sommes, moyennes)
- Des requêtes sur des données de déduplication (dernier état connu par entité)
- Des résumés de tables à très haut volume où les requêtes directes seraient trop lentes

#### Créer une vue matérialisée

```kql
// Créer une vue matérialisée : dernier état de chaque vélo
.create materialized-view BikeLatestState on table Bikestream
{
    Bikestream
    | summarize arg_max(ingestion_time(), *) by StationId
}

// Créer une vue matérialisée : total de vélos par quartier (mise à jour continue)
.create materialized-view BikesByNeighbourhood on table Bikestream
{
    Bikestream
    | summarize TotalBikes = sum(No_Bikes), 
                AvgBikes = avg(No_Bikes),
                LastUpdated = max(ingestion_time())
      by Neighbourhood
}
```

#### Interroger une vue matérialisée

Les vues matérialisées s'interrogent comme des tables ordinaires :

```kql
// Requête sur la vue matérialisée (résultat quasi-instantané)
BikesByNeighbourhood
| order by TotalBikes desc
| take 10

// La vue retourne toujours les données les plus récentes
BikeLatestState
| where Neighbourhood == "Chelsea"
| project StationId, Street, No_Bikes, No_Empty_Docks
```

#### Propriétés des vues matérialisées

- Elles sont **persistantes** : elles survivent aux redémarrages du service
- Elles sont **maintenues automatiquement** : le moteur met à jour les résultats en arrière-plan au fil des nouvelles ingestions
- Elles supportent les fonctions d'agrégation : `sum`, `count`, `avg`, `min`, `max`, `dcount`, `arg_max`, `arg_min`
- Elles peuvent inclure un **filtre where** pour ne matérialiser que les données pertinentes

### Fonctions stockées (Stored Functions)

Les **fonctions stockées** sont des requêtes KQL nommées et réutilisables. Elles permettent d'encapsuler de la logique de requête complexe que vous souhaitez réutiliser ou partager.

#### Créer une fonction stockée

```kql
// Créer une fonction pour obtenir les stats d'un quartier
.create-or-alter function GetNeighbourhoodStats(neighbourhood: string) {
    Bikestream
    | where Neighbourhood == neighbourhood
    | summarize 
        TotalBikes = sum(No_Bikes),
        TotalEmptyDocks = sum(No_Empty_Docks),
        AvgBikes = avg(No_Bikes),
        StationCount = dcount(StationId)
}

// Créer une fonction pour les données des N dernières minutes
.create-or-alter function GetRecentEvents(minutesBack: int) {
    Bikestream
    | where ingestion_time() > ago(minutesBack * 1m)
    | project Street, Neighbourhood, No_Bikes, No_Empty_Docks
}

// Créer une fonction pour calculer le taux d'occupation
.create-or-alter function GetOccupancyRate() {
    Bikestream
    | summarize arg_max(ingestion_time(), *) by StationId
    | extend OccupancyRate = toreal(No_Bikes) / toreal(No_Bikes + No_Empty_Docks) * 100
    | project Street, Neighbourhood, No_Bikes, No_Empty_Docks, OccupancyRate
}
```

#### Utiliser une fonction stockée

```kql
// Appeler la fonction avec un argument
GetNeighbourhoodStats("Chelsea")

// Appeler la fonction sans argument
GetOccupancyRate()
| where OccupancyRate > 80  // stations quasi-pleines
| order by OccupancyRate desc

// Combiner avec d'autres opérateurs
GetRecentEvents(30)
| summarize count() by Neighbourhood
| order by count_ desc
```

#### Avantages des fonctions stockées

1. **Réutilisabilité** : écrivez la logique une fois, appelez-la partout
2. **Maintenabilité** : modifiez la logique à un seul endroit
3. **Lisibilité** : les requêtes complexes deviennent plus lisibles
4. **Partage** : partagez des fonctions avec votre équipe via le queryset
5. **Encapsulation** : masquez la complexité des requêtes aux utilisateurs finaux

## Évaluation du module

*10 min*

### Vérification des connaissances

**Question 1**
Dans KQL, quel opérateur utilisez-vous pour calculer la somme des vélos disponibles groupée par quartier ?

- A) `project`
- B) `where`
- C) `summarize` ✓
- D) `order by`

*Explication : `summarize` est l'équivalent KQL de `GROUP BY` en SQL. Il permet de calculer des agrégations (sum, count, avg, min, max...) sur des groupes de lignes.*

---

**Question 2**
Vous voulez interroger les événements des 2 dernières heures dans une table KQL. Quelle est la syntaxe correcte ?

- A) `| where timestamp > now() - 2h`
- B) `| where ingestion_time() > ago(2h)` ✓
- C) `| where time > last(2h)`
- D) `| where datetime > recent(2h)`

*Explication : `ago(2h)` est la fonction KQL qui retourne le moment qui était il y a 2 heures. Combinée avec `ingestion_time()` (le timestamp d'ingestion) ou un champ datetime de la table, elle permet de filtrer sur une fenêtre temporelle glissante.*

**Question 3**
Quelle est la principale différence entre une vue matérialisée et une vue ordinaire dans un Eventhouse ?

- A) Une vue matérialisée ne peut pas être interrogée comme une table normale
- B) Une vue ordinaire stocke physiquement les résultats ; une vue matérialisée les recalcule à chaque requête
- C) Une vue matérialisée stocke physiquement les résultats agrégés et les met à jour automatiquement ; une vue ordinaire recalcule à chaque requête ✓
- D) Il n'y a pas de différence fonctionnelle, seulement une différence de syntaxe

*Explication : Une vue matérialisée pré-calcule et stocke les résultats agrégés de manière persistante. Elle est mise à jour en arrière-plan à chaque nouvelle ingestion. Cela la rend idéale pour des agrégations coûteuses (ex : sum par groupe) sur des tables très volumineuses.*

---

**Question 4**
Quel opérateur KQL permet de combiner deux tables en faisant correspondre des lignes selon un critère de correspondance (clé commune) ?

- A) `union`
- B) `extend`
- C) `summarize`
- D) `join` ✓

*Explication : `join` en KQL fonctionne comme un JOIN SQL. Il combine deux tables sur un critère de correspondance (clé commune). `union` fusionne des tables verticalement (ajouter des lignes), tandis que `join` les combine horizontalement (ajouter des colonnes).*

**Question 5**
Vous avez une requête KQL complexe de calcul d'occupation des stations vélo que vous utilisez dans 5 dashboards différents. Comment pouvez-vous centraliser cette logique pour la maintenir à un seul endroit ?

- A) Copier-coller la requête dans chaque dashboard
- B) Créer une vue matérialisée
- C) Créer une fonction stockée ✓
- D) Créer une table de résultats mise à jour manuellement

*Explication : Les **fonctions stockées** permettent d'encapsuler de la logique de requête complexe sous un nom réutilisable. En modifiant la définition de la fonction, tous les dashboards qui l'utilisent sont mis à jour automatiquement, sans modification individuelle.*

## Résumé

*1 min*

Dans ce module, vous avez maîtrisé l'**Eventhouse** et le **Kusto Query Language (KQL)** pour analyser des données en temps réel dans Microsoft Fabric.

Points clés à retenir :

- Un **Eventhouse** est un conteneur qui héberge une ou plusieurs **KQL Databases**, optimisé pour les données de séries temporelles et d'événements. Il se base sur la technologie Azure Data Explorer.
- Les données sont **automatiquement organisées par ordre chronologique**, permettant des requêtes ultra-rapides sur des plages temporelles
- **KQL** est un langage de requête basé sur des opérateurs en pipeline (`|`). Ses opérateurs fondamentaux sont : `take`, `project`, `where`, `summarize`, `order by`, `extend`, `join`, `render`
- La fonction **`ago()`** est clé pour filtrer sur des fenêtres temporelles glissantes (ex : `ago(1h)`, `ago(7d)`)
- Le **T-SQL** est supporté via un endpoint managé, mais KQL offre des performances et des capacités analytiques supérieures
- Les **vues matérialisées** pré-calculent et stockent des agrégations en continu, idéales pour les requêtes fréquentes sur des datasets volumineux
- Les **fonctions stockées** encapsulent de la logique KQL réutilisable, améliorant la maintenabilité des solutions analytiques
- Les données Eventhouse sont **accessibles depuis OneLake**, Power BI, notebooks Fabric et le SQL analytics endpoint managé
