Dans un monde où les décisions d'affaires doivent être prises en quelques secondes, pas en quelques heures, les architectures analytiques traditionnelles atteignent leurs limites. Un pipeline de données classique — ingest, transform, load, query — peut introduire des latences de plusieurs minutes, voire plusieurs heures. Mais dans certains domaines, chaque seconde compte.

Imaginez un système de surveillance industrielle qui doit détecter une surchauffe critique avant qu'elle n'endommage une ligne de production. Ou une plateforme de trading qui doit réagir à un signal de marché en millisecondes. Ou encore un système de détection de fraude bancaire qui doit valider une transaction avant qu'elle ne soit approuvée. Ces scénarios ne peuvent pas attendre un traitement par lots nocturne.

**Real-Time Intelligence (RTI)** est la réponse de Microsoft Fabric à ce besoin. C'est une suite intégrée de services conçus pour capturer, transformer, stocker, analyser et agir sur des données en mouvement — le tout avec une latence minimale et sans nécessiter de compétences avancées en infrastructure.

Ce module vous donne une vue d'ensemble complète de l'écosystème RTI dans Microsoft Fabric, de ses composants et de la façon dont ils s'articulent pour créer des solutions analytiques temps réel de bout en bout.

## Qu'est-ce que l'analytique de données en temps réel ?

*5 min*
Effectué — 100 XP

### De l'analytique par lots à l'analytique en temps réel

L'analytique traditionnelle fonctionne sur le modèle **"collect-then-analyze"** : les données sont collectées pendant un certain temps (une nuit, une heure, quelques minutes), puis traitées en bloc. Ce modèle, dit de **traitement par lots (batch processing)**, est adapté aux rapports périodiques, aux analyses historiques et aux tableaux de bord mis à jour toutes les heures.

L'analytique en temps réel, aussi appelée **streaming analytics**, adopte une approche radicalement différente : les données sont traitées **au fur et à mesure de leur arrivée**, sans accumulation préalable. On parle d'un modèle **"process-as-it-arrives"**.

La distinction entre les deux se traduit par une différence de **latence** :

| Mode | Latence typique | Cas d'usage |
|------|----------------|-------------|
| Batch processing | Minutes à heures | Rapports quotidiens, ETL nocturnes, BI classique |
| Micro-batch | 1 à 30 secondes | Agrégations quasi-temps-réel, streaming SQL |
| Streaming pur | Millisecondes à 1 seconde | Détection de fraude, alertes IoT, trading |

### Quand utiliser l'analytique temps réel ?

Real-Time Intelligence n'impose pas que vos données arrivent à haute fréquence. Ce qui le distingue, c'est sa capacité à **réagir aux événements dès qu'ils se produisent**, plutôt que d'attendre un cycle de traitement planifié.

Voici des exemples concrets de cas d'usage :

- **Industrie manufacturière** : surveillance de capteurs IoT pour détecter des anomalies de température ou de pression avant une panne machine
- **Finance** : détection de transactions frauduleuses en millisecondes, alertes sur des variations de cours
- **Logistique** : suivi en temps réel de véhicules et de livraisons, alertes sur des retards
- **Retail** : analyse du comportement client en temps réel, personnalisation instantanée d'offres
- **Santé** : monitoring de patients en soins intensifs, alertes sur des constantes anormales
- **Applications IA** : surveillance de la sécurité du contenu dans des applications LLM (détection de toxicité, violations de politique)
- **Gaming** : détection de comportements de triche en temps réel, gestion d'événements en jeu

### Les défis du streaming de données

Travailler avec des données en temps réel introduit des défis techniques spécifiques :

1. **Volume et vélocité** : les streams peuvent générer des millions d'événements par seconde
2. **Désordre des événements** : les événements peuvent arriver dans le désordre (late arriving data)
3. **Exactement-une-fois vs. au-moins-une-fois** : garanties de traitement
4. **Fenêtres temporelles** : comment agréger des données sur des intervalles glissants ?
5. **State management** : comment maintenir un état entre les événements ?
6. **Scalabilité** : comment gérer des pics de charge ?

Real-Time Intelligence dans Microsoft Fabric gère tous ces défis de manière transparente grâce à son architecture basée sur des services managés.

### Les 6 composants fondamentaux

#### 1. Real-Time Hub — Le point d'entrée universel

Le **Real-Time Hub** est le catalogue centralisé de toutes les données en mouvement de votre organisation. Il joue le rôle de **"place de marché" pour les streams de données** : un endroit unique où vous pouvez découvrir, vous connecter et partager des flux de données temps réel.

Le Real-Time Hub contient trois catégories de données :

- **Data streams** : tous les flux de données actifs dans Fabric auxquels vous avez accès
- **Microsoft sources** : sources Azure facilement connectables (Azure Event Hubs, IoT Hub, Azure SQL DB CDC, Azure Cosmos DB CDC, PostgreSQL CDC...)
- **Fabric events** : événements générés par Fabric lui-même (création/modification d'items dans un workspace, événements Azure Blob Storage, etc.)

Le Real-Time Hub permet également de partager des streams dérivés — des flux transformés que d'autres équipes peuvent consommer directement, sans dupliquer la logique d'ingestion.

#### 2. Eventstream — L'ingestion et la transformation sans code

**Eventstream** est le composant d'ingestion et de transformation de Real-Time Intelligence. Il vous permet de **capturer, transformer et router des événements en temps réel** vers différentes destinations, **sans écrire une ligne de code**.

Eventstream fonctionne comme un pipeline de streaming visuel. Vous ajoutez des sources (où les données viennent), des transformations (comment les traiter) et des destinations (où les envoyer). Tout se configure via une interface de glisser-déposer.

Parmi les sources supportées : Azure Event Hubs, Azure IoT Hub, Apache Kafka, CDC databases (Azure SQL, PostgreSQL, MySQL, Cosmos DB), AWS Kinesis, Google Cloud Pub/Sub, MQTT, et des données d'exemple intégrées.

#### 3. Eventhouse — Le moteur de stockage et d'analyse

L'**Eventhouse** est le moteur de stockage et d'interrogation optimisé pour les données en temps réel. C'est un conteneur qui héberge une ou plusieurs **bases de données KQL (KQL Databases)**.

Basé sur la technologie **Azure Data Explorer (ADX)**, l'Eventhouse permet d'ingérer des milliards d'événements et de les interroger en quelques secondes grâce au langage **KQL (Kusto Query Language)**, spécialement conçu pour les requêtes sur des données de séries temporelles.

L'Eventhouse est particulièrement adapté pour : les données de télémétrie et de logs, les données IoT et de séries temporelles, les enregistrements financiers, les logs de sécurité et de conformité.

#### 4. KQL (Kusto Query Language) — La puissance analytique

**KQL** est le langage de requête utilisé pour interroger les données dans un Eventhouse. Syntaxiquement proche de SQL mais optimisé pour les requêtes sur des séries temporelles et des logs, KQL offre des capacités analytiques avancées : détection d'anomalies, analyse de séries temporelles, prévisions, et visualisations intégrées.

#### 5. Real-Time Dashboards — La visualisation instantanée

Les **tableaux de bord en temps réel (Real-Time Dashboards)** permettent de visualiser des données directement depuis un Eventhouse avec une latence de quelques secondes. Ils supportent l'auto-refresh, les paramètres interactifs, les cartes géospatiales et diverses visualisations.

#### 6. Activator — L'automatisation intelligente

**Activator** est le moteur de déclenchement d'actions de Real-Time Intelligence. Il surveille en permanence des flux de données ou des résultats de requêtes KQL, et déclenche automatiquement des actions (envoi d'emails, messages Teams, déclenchement de Power Automate workflows, exécution de jobs Fabric) lorsque certaines conditions ou patterns sont détectés.

### Intégration avec le reste de Fabric

Real-Time Intelligence s'intègre nativement avec les autres expériences Fabric :

- Les données stockées dans un Eventhouse sont **automatiquement disponibles dans OneLake** (une copie logique unique)
- Les données OneLake peuvent être **interrogées depuis un Eventhouse comme raccourci** (shortcut), sans les dupliquer
- Les insights RTI peuvent alimenter des **rapports Power BI**
- Les **notebooks Fabric** peuvent travailler directement sur des données Eventhouse (KQL, T-SQL, Python, Spark)

## Ingérer et transformer des données en temps réel

*6 min*
Effectué — 100 XP

### Le rôle d'Eventstream dans l'ingestion

L'ingestion de données en temps réel commence toujours par une source. Dans Microsoft Fabric, **Eventstream** est le composant central pour connecter n'importe quelle source de streaming à l'écosystème RTI.

Le processus d'ingestion avec Eventstream se déroule en trois étapes :

**Étape 1 — Connexion à une source**

Vous choisissez d'où viennent vos données. Parmi les sources disponibles :

- **Azure Event Hubs** : service de streaming managé d'Azure, idéal pour les applications à haut débit
- **Azure IoT Hub** : conçu spécifiquement pour les données IoT (telemetry, device-to-cloud)
- **Apache Kafka** : plate-forme open-source de streaming distribuée
- **Données CDC (Change Data Capture)** : capture des changements dans des bases de données (Azure SQL, PostgreSQL, MySQL, Cosmos DB...)
- **Sources cloud externes** : AWS Kinesis, Google Cloud Pub/Sub, Confluent Kafka
- **Données d'exemple** : données simulées intégrées (vélos, taxis, marchés boursiers) pour les tests

**Étape 2 — Transformation (optionnelle)**

Entre la source et la destination, vous pouvez appliquer des transformations sans code via l'éditeur visuel :

- **Filter** : filtrer les événements selon des critères (ex : conserver uniquement les capteurs avec température > 80°C)
- **Manage fields** : ajouter, supprimer, renommer ou convertir des colonnes
- **Aggregate** : calculer des sommes, moyennes, min/max sur des fenêtres temporelles
- **Group by** : agréger par dimension avec des fenêtres de temps (tumbling, hopping, session)
- **Join** : combiner deux streams sur un critère de correspondance
- **Union** : fusionner plusieurs streams ayant la même structure

**Étape 3 — Envoi vers une destination**

Les données transformées sont routées vers une ou plusieurs destinations simultanées :
- **Eventhouse** (KQL Database) : pour l'analyse et le requêtage KQL
- **Lakehouse** : pour le stockage Delta Lake et l'analyse Spark
- **Activator** : pour déclencher des alertes et des actions
- **Custom endpoint** : pour envoyer les données à des applications externes

### Modes d'ingestion dans l'Eventhouse

Lorsqu'une Eventstream envoie des données vers un Eventhouse, deux modes sont disponibles :

1. **Direct ingestion** : les événements bruts sont insérés directement dans la table KQL, sans transformation supplémentaire
2. **Event processing before ingestion** : les événements sont d'abord transformés (agrégés, filtrés, joints) avant d'être stockés — utile pour réduire le volume de données stockées

## Stocker et interroger des données en temps réel

*5 min*
Effectué — 100 XP

### L'Eventhouse : le cœur du stockage RTI

Une fois les données ingérées via Eventstream, elles sont stockées dans l'**Eventhouse** dans des tables de **bases de données KQL**. L'Eventhouse organise automatiquement les données par ordre chronologique d'arrivée, ce qui permet des requêtes ultra-rapides sur des plages temporelles.

Voici les principales caractéristiques du stockage dans un Eventhouse :

- **Compression automatique** : les données sont compressées pour réduire les coûts de stockage
- **Indexation temporelle** : chaque événement est indexé par son timestamp d'ingestion
- **Support de formats variés** : JSON, CSV, Parquet, Avro, données structurées, semi-structurées (JSON/XML) et non-structurées (texte libre)
- **OneLake integration** : les données peuvent être exposées dans OneLake comme une copie logique unique (sans duplication physique)

### Introduction à KQL

Le **Kusto Query Language (KQL)** est le langage natif pour interroger un Eventhouse. Sa syntaxe est basée sur des **opérateurs en pipeline** : chaque opération prend en entrée le résultat de l'opération précédente.

Structure d'une requête KQL :

```kql
// Syntaxe de base : Table | Opérateur1 | Opérateur2 | ...
stock
| where ["time"] > ago(5m)
| summarize avgPrice = avg(todecimal(bidPrice)) by symbol
| project symbol, avgPrice
| order by avgPrice desc
```

Les opérateurs KQL les plus utilisés :

| Opérateur | Rôle | Équivalent SQL |
|-----------|------|---------------|
| `where` | Filtrer les lignes | `WHERE` |
| `project` | Sélectionner/renommer des colonnes | `SELECT` |
| `summarize` | Agréger des données | `GROUP BY` |
| `order by` | Trier les résultats | `ORDER BY` |
| `take` | Limiter le nombre de lignes | `TOP` / `LIMIT` |
| `extend` | Ajouter une colonne calculée | Colonnes calculées |
| `join` | Joindre deux tables | `JOIN` |
| `render` | Visualiser les résultats | (non-SQL) |

KQL supporte également le **T-SQL** via un endpoint managé, permettant aux équipes BI de se connecter à des outils existants comme Power BI Desktop ou SQL Server Management Studio.

## Visualiser des données en temps réel

*2 min*
Effectué — 100 XP

### Real-Time Dashboards

Les **tableaux de bord en temps réel** permettent de créer des visualisations interactives directement alimentées par des requêtes KQL sur un Eventhouse, avec des délais de mise à jour de quelques secondes.

Les principales fonctionnalités des Real-Time Dashboards :

- **Tuiles multiples** : chaque tuile est alimentée par une requête KQL indépendante
- **Types de visualisation** : graphiques en courbes, barres, colonnes, secteurs, tables, cartes géospatiales, jauges
- **Auto-refresh** : actualisation automatique configurable (30 secondes, 1 minute, etc.)
- **Paramètres** : filtres interactifs permettant aux utilisateurs de sélectionner des plages de temps, des catégories, des régions
- **Requêtes de base (Base queries)** : requêtes partagées entre plusieurs tuiles pour éviter la duplication et faciliter la maintenance
- **Pages** : organisation du dashboard en plusieurs pages thématiques

Exemple de requête pour un tableau de bord de prix boursiers :

```kql
stock
| where ["time"] > ago(5m)
| summarize avgPrice = avg(todecimal(bidPrice)) by symbol
| project symbol, avgPrice
```

### KQL Querysets

En dehors des dashboards, les **KQL Querysets** sont des fichiers associés à une base de données KQL permettant d'écrire, sauvegarder et exécuter des requêtes KQL ad-hoc. Ils supportent également T-SQL pour les utilisateurs non familiers avec KQL.

## Automatiser les actions

*4 min*
Effectué — 100 XP

### Activator : de la donnée à l'action

L'analytique temps réel n'a de valeur que si elle peut déclencher des **actions concrètes**. C'est le rôle d'**Activator** dans l'écosystème RTI.

Activator surveille en continu des sources de données (Real-Time Hub, résultats de requêtes KQL, tableaux de bord Real-Time, rapports Power BI) et déclenche des actions lorsque des conditions ou des patterns spécifiques sont détectés.

**Les éléments d'une règle Activator :**

1. **Source** : d'où viennent les données surveillées (eventstream, KQL query, dashboard)
2. **Objet** : l'entité surveillée (ex : un package de livraison, un appareil IoT, un symbole boursier)
3. **Propriété** : l'attribut de l'objet à surveiller (ex : température, prix, statut)
4. **Condition** : le critère de déclenchement (ex : température > 20°C, prix augmente de plus de 100)
5. **Filtre de propriété** : conditions supplémentaires pour affiner le déclenchement (ex : uniquement pour les packages contenant des médicaments)
6. **Action** : ce qui se déclenche (email, message Teams, Power Automate workflow, job Fabric)

**Types d'actions disponibles :**

- Envoi d'email (avec sujet, corps et données contextuelles)
- Message Microsoft Teams
- Déclenchement de workflows Power Automate
- Exécution de pipelines Fabric, Spark jobs, Dataflows
- Exécution de User Data Functions

Exemple de scénario Activator : dans un système de surveillance de prix boursiers, une règle déclenche un email chaque fois que le prix moyen d'une action augmente de plus de 100 unités sur une période de 5 minutes. Cette règle s'applique séparément à chaque symbole boursier (groupé par `symbol`).

## Exercice — Prise en main de l'intelligence en temps réel dans Microsoft Fabric

*30 min*
Effectué — 100 XP

### Objectif du lab

Dans ce lab pratique, vous allez créer une solution RTI complète de bout en bout pour analyser des données de marché boursier en temps réel.

### Ce que vous allez faire

**1. Créer un workspace Fabric**
- Connectez-vous à [https://app.fabric.microsoft.com](https://app.fabric.microsoft.com)
- Créez un nouveau workspace avec une licence Fabric (Trial ou Premium)

**2. Créer un Eventstream depuis le Real-Time Hub**
- Ouvrez le **Real-Time Hub** dans le menu de navigation
- Cliquez sur **Add data**
- Sélectionnez **Stock market** comme source de données exemple
- Configurez la source :
  - **Source name** : `stock`
  - **Eventstream name** : `stock-data`
- Cliquez sur **Next** puis **Connect**

**3. Créer un Eventhouse**
- Créez un **Eventhouse** depuis le menu Create > Real-Time Intelligence
- Nommez-le de manière unique
- Dans l'Eventhouse, sélectionnez la KQL Database créée automatiquement

**4. Connecter l'Eventstream à l'Eventhouse**
- Dans la KQL Database, cliquez sur **Get data**
- Sélectionnez **Eventstream > Existing eventstream**
- Créez une table `stock` comme destination
- Nommez la connexion `stock-table`

**5. Interroger les données avec KQL**

Une fois les données qui commencent à arriver, exécutez ces requêtes dans le KQL Queryset :

```kql
// Afficher les 100 derniers événements
stock
| take 100
```

```kql
// Prix moyen par symbole sur les 5 dernières minutes
stock
| where ["time"] > ago(5m)
| summarize avgPrice = avg(todecimal(bidPrice)) by symbol
| project symbol, avgPrice
```

Attendez quelques secondes et relancez la requête — les prix changent au fil des nouveaux événements !

**6. Créer un tableau de bord temps réel**
- Depuis l'éditeur KQL, sélectionnez la requête de prix moyens
- Cliquez sur **Save to dashboard** > dans un nouveau dashboard
- Nommez le dashboard `Stock Dashboard` et la tuile `Average Prices`
- Dans le dashboard, passez en mode **Editing**
- Modifiez la tuile pour changer le visuel de *Table* en *Column chart*
- Sauvegardez

**7. Créer une alerte avec Activator**
- Dans le dashboard, cliquez sur **Set alert** dans la toolbar
- Configurez l'alerte :
  - **Run query every** : 5 minutes
  - **Grouping field** : symbol
  - **When** : avgPrice **Increases by** 100
  - **Action** : Send me an email
- Créez l'alerte

**8. Explorer l'Activator créé**
- Retournez dans votre workspace
- Ouvrez l'item Activator créé
- Observez la structure : objet `avgPrice`, règle d'alerte, onglet **History**

### Résultat attendu

À la fin du lab, vous avez créé une mini-solution RTI complète :
- Un **Eventstream** qui ingère des données boursières en temps réel depuis un sample data source
- Un **Eventhouse** qui stocke ces données dans une table KQL
- Des **requêtes KQL** qui analysent les prix moyens
- Un **Real-Time Dashboard** avec un graphique en colonnes mis à jour en temps réel
- Un **Activator** qui surveille les variations de prix et envoie des alertes email

- Le **Real-Time Hub** est le catalogue centralisé pour découvrir et partager des flux de données dans une organisation
- **Eventstream** permet d'ingérer des données depuis de nombreuses sources (Event Hubs, IoT Hub, Kafka, CDC databases, sources cloud...) et de les transformer sans code via un éditeur visuel
- L'**Eventhouse** stocke les données dans des bases de données **KQL**, optimisées pour les requêtes ultra-rapides sur des séries temporelles
- **KQL (Kusto Query Language)** est le langage de requête natif, puissant et expressif pour interroger et analyser des données d'événements
- Les **Real-Time Dashboards** offrent des visualisations interactives avec auto-refresh, paramètres et types de graphiques variés
- **Activator** ferme la boucle en déclenchant des actions automatiques (emails, Teams, Power Automate) lorsque des conditions sont détectées dans les données

Ces composants s'intègrent seamlessly entre eux et avec le reste de l'écosystème Fabric (OneLake, Power BI, notebooks, pipelines).
