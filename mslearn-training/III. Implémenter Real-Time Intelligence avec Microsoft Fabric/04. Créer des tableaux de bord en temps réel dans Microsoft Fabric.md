# Créer des tableaux de bord en temps réel dans Microsoft Fabric

*1 h 13 min*
Module *(7 Unités)*
Intermédiaire
Ingénieur Data
Analyste de données
Microsoft Fabric

Les tableaux de bord en temps réel (Real-Time Dashboards) sont une fonctionnalité de Microsoft Fabric qui permet de créer des visualisations interactives de données en mouvement, directement alimentées par des requêtes KQL sur un Eventhouse. Ils supportent l'auto-refresh, les paramètres dynamiques et diverses visualisations incluant des cartes géospatiales.

---

## Objectifs d'apprentissage

Dans ce module, vous allez apprendre à :

- Créer un tableau de bord en temps réel et y ajouter une source de données Eventhouse
- Ajouter et configurer des tuiles (tiles) avec différents types de visualisation
- Créer des requêtes de base (base queries) pour factoriser la logique partagée
- Ajouter des paramètres pour rendre le dashboard interactif
- Configurer l'auto-refresh pour maintenir les visualisations à jour
- Organiser le tableau de bord en plusieurs pages
- Partager le tableau de bord avec d'autres utilisateurs

---

## Prérequis

- Avoir complété le module "Utiliser des données en temps réel dans un Eventhouse" (recommandé)
- Connaissances de base en KQL (opérateurs `where`, `summarize`, `project`)
- Un Eventhouse avec des données dans une KQL Database
- Accès à un tenant Microsoft Fabric avec une capacité F4+ ou Trial

## Présentation

*1 min*
Effectué — 100 XP

Les données en temps réel n'ont de valeur que si les bonnes personnes peuvent les voir au bon moment. Un opérateur de salle de contrôle qui surveille 500 capteurs industriels ne peut pas lire des lignes de données brutes dans un fichier CSV — il lui faut une visualisation claire, qui se met à jour automatiquement, et qui lui permette d'identifier instantanément les anomalies.

C'est le rôle des **tableaux de bord en temps réel (Real-Time Dashboards)** dans Microsoft Fabric. Contrairement aux rapports Power BI conçus pour l'analytique historique, les Real-Time Dashboards sont spécialement optimisés pour les données en mouvement : ils interrogent directement l'Eventhouse, se rafraîchissent automatiquement à intervalles configurable et affichent des résultats avec une latence de quelques secondes seulement.

Dans ce module, vous allez apprendre à concevoir et déployer des tableaux de bord temps réel professionnels, en maîtrisant toutes leurs fonctionnalités : tuiles, base queries, paramètres, auto-refresh et partage.

## Prise en main des tableaux de bord en temps réel

*6 min*
Effectué — 100 XP

### Qu'est-ce qu'un Real-Time Dashboard ?

Un **tableau de bord en temps réel** est un artifact Fabric qui contient un ensemble de **tuiles (tiles)**, chacune alimentée par une requête KQL exécutée directement sur un Eventhouse. La différence fondamentale avec un rapport Power BI classique :

| Caractéristique | Real-Time Dashboard | Rapport Power BI |
|-----------------|---------------------|------------------|
| Source de données | KQL Database (Eventhouse) directement | Semantic model (dataset) |
| Latence typique | Quelques secondes | Minutes (selon refresh) |
| Langage de requête | KQL | DAX + M (Power Query) |
| Auto-refresh | Configurable (30s minimum) | Planifié (30 min minimum en service) |
| Cas d'usage | Monitoring temps réel, opérations | Analytique, reporting business |
| Interactivité | Paramètres KQL | Slicers, filtres, drillthrough |

### Interface du dashboard

L'interface d'un Real-Time Dashboard comprend :

- **Canvas principal** : zone d'affichage des tuiles, organisable librement
- **Toolbar** : boutons pour ajouter des tuiles, des sources de données, gérer les base queries, les paramètres et l'auto-refresh
- **Panneau Pages** : navigation entre les différentes pages du dashboard
- **Mode Viewing / Editing** : basculez entre la consultation et la modification
- **Onglet Manage** : accès aux paramètres et à l'auto-refresh

### Créer un Real-Time Dashboard

Pour créer un nouveau tableau de bord :

1. Dans votre workspace, cliquez sur **+ New item**
2. Sous **Real-Time Intelligence**, sélectionnez **Real-Time Dashboard**
3. Donnez-lui un nom descriptif

Un dashboard vide est créé. La première étape est d'y ajouter une **source de données**.

### Configurer une source de données

Une source de données dans un Real-Time Dashboard est la connexion à une KQL Database dans un Eventhouse. Sans source de données configurée, les tuiles n'ont pas de données à afficher.

1. Dans la toolbar, cliquez sur **New data source**
2. Sélectionnez **Eventhouse / KQL Database**
3. Choisissez votre Eventhouse
4. Configurez la source :
   - **Display name** : nom d'affichage (ex : `Bike Rental Data`)
   - **Database** : la KQL Database cible dans l'Eventhouse
   - **Passthrough identity** : si activé, la requête s'exécute avec l'identité de l'utilisateur qui consulte le dashboard (recommandé pour la sécurité)
5. Cliquez **Add**

Un dashboard peut avoir **plusieurs sources de données** provenant de différents Eventhouses ou KQL Databases.

## Organiser et filtrer les données du tableau de bord

*10 min*
Effectué — 100 XP

### Ajouter et configurer des tuiles

Une **tuile (tile)** est la brique fondamentale d'un Real-Time Dashboard. Chaque tuile affiche les résultats d'une requête KQL sous forme de visualisation.

#### Ajouter une tuile

1. Cliquez sur **Add tile** dans le dashboard
2. L'éditeur de tuile s'ouvre : en haut, un éditeur KQL ; en bas, un aperçu de la visualisation
3. Sélectionnez la source de données appropriée
4. Écrivez ou collez votre requête KQL
5. Cliquez **Run** pour tester la requête
6. Cliquez **Apply changes** pour ajouter la tuile au canvas

Exemple de requête pour une tuile montrant les vélos et docks disponibles par quartier :

```kql
bikes
    | where ingestion_time() between (ago(30min) .. now())
    | summarize latest_observation = arg_max(ingestion_time(), *) by Neighbourhood
    | project Neighbourhood, latest_observation, No_Bikes, No_Empty_Docks
    | order by Neighbourhood asc
```

#### Configurer la visualisation

Après avoir appliqué la requête, vous pouvez personnaliser l'apparence de la tuile via le panneau **Visual Formatting** :

**Paramètres communs à tous les visuels :**
- **Tile name** : titre affiché en haut de la tuile
- **Visual type** : type de visualisation (table, graphique, carte...)

**Types de visualisation disponibles :**

| Type | Description | Cas d'usage typique |
|------|-------------|---------------------|
| **Table** | Tableau classique avec lignes et colonnes | Données brutes, listes détaillées |
| **Bar chart** | Barres horizontales | Comparaison de catégories |
| **Column chart** | Barres verticales | Évolution par catégorie |
| **Line chart** | Courbes | Séries temporelles, tendances |
| **Area chart** | Courbes remplies | Volumes dans le temps |
| **Pie chart** | Secteurs | Distribution proportionnelle |
| **Donut chart** | Anneau | Distribution avec valeur centrale |
| **Scatter chart** | Nuage de points | Corrélations |
| **Map** | Carte géospatiale | Données avec latitude/longitude |
| **Gauge** | Jauge | Indicateur de performance (KPI) |
| **Stat** | Chiffre unique mis en évidence | KPIs, valeurs critiques |
| **Funnel** | Entonnoir | Conversion, pipeline |
| **Heatmap** | Carte de chaleur | Densité, intensité par catégorie |

#### Configuration d'un graphique en barres empilées

Pour transformer une table en graphique en barres empilées (exemple : vélos et docks par quartier) :

Dans le panneau **Visual Formatting** :
- **Tile name** : `Bikes and Docks`
- **Visual type** : Bar chart
- **Visual format** : Stacked bar chart
- **Y columns** : `No_Bikes`, `No_Empty_Docks` (deux colonnes = deux séries)
- **X column** : `Neighbourhood`
- **Legend location** : Bottom

#### Configuration d'une carte géospatiale

Pour visualiser des données avec des coordonnées GPS :

Requête :
```kql
bikes
    | where ingestion_time() between (ago(30min) .. now())
    | summarize latest_observation = arg_max(ingestion_time(), *) by Neighbourhood
    | project Neighbourhood, latest_observation, Latitude, Longitude, No_Bikes
    | order by Neighbourhood asc
```

Dans le panneau **Visual Formatting** :
- **Tile name** : `Bike Locations`
- **Visual type** : Map
- **Define location by** : Latitude and longitude
- **Latitude column** : `Latitude`
- **Longitude column** : `Longitude`
- **Label column** : `Neighbourhood`
- **Size** : Show
- **Size column** : `No_Bikes` (les stations avec plus de vélos apparaissent plus grandes)

#### Redimensionner et repositionner les tuiles

Les tuiles sont redimensionnables par glisser-déposer sur leurs bords ou coins. Vous pouvez les repositionner librement sur le canvas. Il est recommandé d'organiser les tuiles les plus importantes en haut à gauche (sens de lecture naturel).

### Requêtes de base (Base queries)

Lorsque plusieurs tuiles partagent des filtres ou des transformations similaires, les **requêtes de base (base queries)** permettent de centraliser cette logique commune, évitant la duplication et facilitant la maintenance.

#### Créer une base query

1. Dans la toolbar, cliquez sur **Base queries**
2. Cliquez sur **+ Add**
3. Définissez :
   - **Variable name** : nom de la variable KQL (ex : `base_bike_data`)
   - **Source** : la source de données à utiliser
   - La requête KQL qui définit le dataset de base

Exemple :
```kql
bikes
    | where ingestion_time() between (ago(30min) .. now())
    | summarize latest_observation = arg_max(ingestion_time(), *) by Neighbourhood
```

4. Cliquez **Run** pour vérifier la requête, puis **Done**

#### Utiliser une base query dans les tuiles

Une fois la base query définie, les tuiles peuvent la référencer directement comme si c'était une table :

**Tuile "Bikes and Docks" (après base query) :**
```kql
base_bike_data
| project Neighbourhood, latest_observation, No_Bikes, No_Empty_Docks
| order by Neighbourhood asc
```

**Tuile "Bike Locations" (après base query) :**
```kql
base_bike_data
| project Neighbourhood, latest_observation, No_Bikes, Latitude, Longitude
| order by Neighbourhood asc
```

Les avantages des base queries :
- **Maintenabilité** : modifiez la logique de filtrage en un seul endroit
- **Cohérence** : toutes les tuiles utilisent exactement les mêmes données de base
- **Performance** : le moteur peut optimiser l'exécution si plusieurs tuiles utilisent la même base query
- **Lisibilité** : les requêtes des tuiles deviennent plus courtes et plus claires

### Paramètres du dashboard

Les **paramètres** permettent aux utilisateurs du dashboard de filtrer interactivement les données affichées, sans modifier les requêtes sous-jacentes.

#### Créer un paramètre

1. Dans la toolbar, sous l'onglet **Manage**, cliquez sur **Parameters**
2. Cliquez sur **+ Add**
3. Configurez le paramètre :

| Champ | Valeur exemple | Description |
|-------|---------------|-------------|
| **Label** | `Neighbourhood` | Texte affiché à l'utilisateur |
| **Parameter type** | Multiple selection | Simple, Multiple, ou Text |
| **Description** | `Choose neighbourhoods` | Aide contextuelle |
| **Variable name** | `selected_neighbourhoods` | Nom utilisé dans les requêtes KQL |
| **Data type** | string | Type de données |
| **Show on pages** | All | Sur quelles pages afficher le paramètre |
| **Source** | Query | La liste de valeurs vient d'une requête |
| **Data source** | Bike Rental Data | Source de données pour la requête |
| **Edit query** | (voir ci-dessous) | Requête pour alimenter la liste |
| **Value column** | Neighbourhood | Colonne utilisée comme valeur |
| **Add "Select all" value** | Coché | Ajoute l'option "Tout sélectionner" |

Requête pour alimenter la liste des quartiers :
```kql
bikes
| distinct Neighbourhood
| order by Neighbourhood asc
```

4. Cliquez **Done**

#### Utiliser le paramètre dans les requêtes

Pour que les tuiles et la base query respectent le paramètre sélectionné, modifiez la base query :

```kql
bikes
    | where ingestion_time() between (ago(30min) .. now())
      and (isempty(['selected_neighbourhoods']) or Neighbourhood in (['selected_neighbourhoods']))
    | summarize latest_observation = arg_max(ingestion_time(), *) by Neighbourhood
```

La condition `isempty(['selected_neighbourhoods'])` garantit que si aucun quartier n'est sélectionné (valeur "Select all"), toutes les données sont affichées.

Le paramètre apparaît maintenant en haut du dashboard. Les utilisateurs peuvent sélectionner un ou plusieurs quartiers pour filtrer toutes les tuiles simultanément.

## Gestion et optimisation du tableau de bord

*10 min*
Effectué — 100 XP

### Organisation en pages

Les dashboards complexes peuvent nécessiter plusieurs pages pour organiser l'information par thématique ou par audience.

#### Ajouter une page

1. Dans le panneau **Pages** à gauche du dashboard, cliquez sur **+ Add page**
2. Nommez la nouvelle page (ex : `Page 2`, `Détails par station`, `Alertes`)
3. Sélectionnez la page pour la modifier

Chaque page peut avoir ses propres tuiles, mais partage les mêmes paramètres et base queries définis pour le dashboard.

Exemple de requête pour une page "Dernières observations" :
```kql
base_bike_data
| project Neighbourhood, latest_observation
| order by latest_observation desc
```

#### Bonnes pratiques d'organisation

- **Page 1** (Vue d'ensemble) : KPIs globaux, cartes, graphiques de synthèse
- **Page 2** (Détails) : tables détaillées, requêtes plus granulaires
- **Page 3** (Alertes) : tuiles mettant en évidence les situations critiques

### Auto-refresh

L'auto-refresh est l'une des fonctionnalités les plus importantes d'un Real-Time Dashboard. Il permet au dashboard de **se rafraîchir automatiquement** à intervalles réguliers, maintenant les visualisations à jour sans intervention manuelle.

#### Configurer l'auto-refresh

1. Dans la toolbar, sous l'onglet **Manage**, cliquez sur **Auto refresh**
2. Configurez :
   - **Enabled** : cochez pour activer l'auto-refresh
   - **Minimum time interval** : définissez la durée minimale entre deux refreshs autorisés (ex : Allow all refresh intervals)
   - **Default refresh rate** : fréquence de rafraîchissement par défaut (ex : 30 minutes)
3. Cliquez **Apply**

**Intervalles de refresh disponibles :**
- 30 secondes, 1 minute, 5 minutes, 10 minutes, 15 minutes, 30 minutes, 1 heure

Le **minimum time interval** permet aux administrateurs de contrôler la charge sur l'Eventhouse en empêchant des refreshs trop fréquents. Le **default refresh rate** est la valeur qui s'applique au chargement du dashboard par un utilisateur.

#### Impact sur les performances

Chaque auto-refresh réexécute toutes les requêtes KQL du dashboard sur l'Eventhouse. Des refreshs très fréquents (toutes les 30 secondes) avec des requêtes complexes sur de gros volumes peuvent impacter les performances et les coûts. Il est recommandé de :
- Utiliser des **base queries** pour partager les calculs coûteux
- Créer des **vues matérialisées** dans l'Eventhouse pour les agrégations fréquentes
- Calibrer le **minimum time interval** selon la tolérance à la charge

### Sauvegarder et partager le dashboard

#### Sauvegarder

Cliquez sur **Save** dans la toolbar. Les modifications non sauvegardées sont indiquées par un indicateur dans l'interface.

#### Partager le dashboard

1. Après sauvegarde, cliquez sur **Share** dans la toolbar
2. Dans la boîte de dialogue, vous pouvez :
   - **Copier un lien direct** vers le dashboard
   - **Gérer les permissions** pour donner accès à d'autres utilisateurs
3. Les destinataires doivent avoir accès au workspace Fabric pour voir le dashboard
4. Avec le lien, les utilisateurs peuvent voir les données en utilisant leur propre identité (si "Passthrough identity" est activé dans la source de données)

#### Modes d'accès

- **Viewing mode** : mode consultation, les utilisateurs peuvent interagir avec les paramètres et filtres mais pas modifier les tuiles
- **Editing mode** : mode édition, pour modifier les tuiles, requêtes, paramètres (nécessite des droits d'édition sur le workspace)

## Exercice — Prise en main des tableaux de bord en temps réel

*35 min*
Effectué — 100 XP

### Objectif du lab

Créer un tableau de bord en temps réel complet pour visualiser des données de location de vélos, avec carte géospatiale, graphique en barres, base query, paramètre de filtrage et auto-refresh.

### Étape 1 : Créer l'infrastructure (workspace, Eventhouse, Eventstream)

1. Créez un workspace Fabric
2. Créez un **Eventhouse** depuis le menu Create > Real-Time Intelligence
3. Ouvrez la KQL Database et cliquez sur **Get data > Eventstream > New eventstream**
4. Nommez l'Eventstream `Bicycle-data`
5. Ajoutez la source **Sample data > Bicycles** nommée `Bicycles`
6. Ajoutez la destination **Eventhouse** avec les paramètres :
   - Mode : Event processing before ingestion
   - Destination name : `bikes-table`
   - Table : créez `bikes`
   - Format : JSON
7. Publiez l'Eventstream et attendez 1-2 minutes

### Étape 2 : Créer le tableau de bord

1. Depuis le workspace, créez un **Real-Time Dashboard** nommé `bikes-dashboard`
2. Dans la toolbar, cliquez **New data source > Eventhouse / KQL Database**
3. Sélectionnez votre Eventhouse et créez une source :
   - **Display name** : `Bike Rental Data`
   - **Database** : votre KQL Database
   - **Passthrough identity** : Activé
4. Cliquez **Add**

### Étape 3 : Ajouter la première tuile (graphique en barres)

1. Cliquez **Add tile**
2. Vérifiez que la source **Bike Rental Data** est sélectionnée
3. Entrez la requête :

```kql
bikes
    | where ingestion_time() between (ago(30min) .. now())
    | summarize latest_observation = arg_max(ingestion_time(), *) by Neighbourhood
    | project Neighbourhood, latest_observation, No_Bikes, No_Empty_Docks
    | order by Neighbourhood asc
```

4. Cliquez **Run**, puis **Apply changes**
5. Éditez la tuile (icône crayon) et configurez :
   - **Tile name** : `Bikes and Docks`
   - **Visual type** : Bar chart
   - **Visual format** : Stacked bar chart
   - **Y columns** : `No_Bikes`, `No_Empty_Docks`
   - **X column** : `Neighbourhood`
   - **Legend location** : Bottom
6. Appliquez et redimensionnez la tuile pour occuper le côté gauche du canvas

### Étape 4 : Ajouter la deuxième tuile (carte géospatiale)

1. Cliquez **New tile** dans la toolbar
2. Entrez la requête :

```kql
bikes
    | where ingestion_time() between (ago(30min) .. now())
    | summarize latest_observation = arg_max(ingestion_time(), *) by Neighbourhood
    | project Neighbourhood, latest_observation, Latitude, Longitude, No_Bikes
    | order by Neighbourhood asc
```

3. Appliquez et configurez la visualisation :
   - **Tile name** : `Bike Locations`
   - **Visual type** : Map
   - **Define location by** : Latitude and longitude
   - **Latitude column** : `Latitude`
   - **Longitude column** : `Longitude`
   - **Label column** : `Neighbourhood`
   - **Size** : Show, **Size column** : `No_Bikes`
4. Redimensionnez la carte pour occuper le côté droit du canvas

### Étape 5 : Créer une base query

1. Dans la toolbar, cliquez sur **Base queries > + Add**
2. **Variable name** : `base_bike_data`
3. **Source** : Bike Rental Data
4. Entrez la requête :

```kql
bikes
    | where ingestion_time() between (ago(30min) .. now())
    | summarize latest_observation = arg_max(ingestion_time(), *) by Neighbourhood
```

5. Cliquez **Run** pour vérifier, puis **Done**

6. Éditez la tuile **Bikes and Docks** et remplacez la requête par :

```kql
base_bike_data
| project Neighbourhood, latest_observation, No_Bikes, No_Empty_Docks
| order by Neighbourhood asc
```

7. Éditez la tuile **Bike Locations** et remplacez par :

```kql
base_bike_data
| project Neighbourhood, latest_observation, No_Bikes, Latitude, Longitude
| order by Neighbourhood asc
```

Vérifiez que les deux tuiles affichent toujours les données correctement.

### Étape 6 : Ajouter un paramètre de filtrage

1. Dans l'onglet **Manage**, cliquez sur **Parameters**
2. Supprimez les paramètres existants s'il y en a
3. Cliquez **+ Add** et configurez :
   - **Label** : `Neighbourhood`
   - **Parameter type** : Multiple selection
   - **Variable name** : `selected_neighbourhoods`
   - **Data type** : string
   - **Show on pages** : All
   - **Source** : Query
   - **Data source** : Bike Rental Data
   - **Edit query** :
   ```kql
   bikes
   | distinct Neighbourhood
   | order by Neighbourhood asc
   ```
   - **Value column** : Neighbourhood
   - **Add "Select all" value** : Coché
   - **"Select all" sends empty string** : Coché
   - **Default value** : Select all
4. Cliquez **Done**

5. Mettez à jour la **base query** pour intégrer le filtre :

```kql
bikes
    | where ingestion_time() between (ago(30min) .. now())
      and (isempty(['selected_neighbourhoods']) or Neighbourhood in (['selected_neighbourhoods']))
    | summarize latest_observation = arg_max(ingestion_time(), *) by Neighbourhood
```

6. Testez le paramètre en sélectionnant un ou deux quartiers — les deux tuiles doivent se filtrer simultanément

### Étape 7 : Ajouter une page

1. Dans le panneau **Pages**, cliquez sur **+ Add page**
2. Nommez-la `Dernières observations`
3. Sélectionnez cette page et ajoutez une tuile avec la requête :

```kql
base_bike_data
| project Neighbourhood, latest_observation
| order by latest_observation desc
```

4. Configurez en **Table** et redimensionnez pour occuper toute la hauteur du dashboard

### Étape 8 : Configurer l'auto-refresh

1. Dans l'onglet **Manage**, cliquez sur **Auto refresh**
2. Configurez :
   - **Enabled** : Activé
   - **Minimum time interval** : Allow all refresh intervals
   - **Default refresh rate** : 30 minutes
3. Appliquez

### Étape 9 : Sauvegarder et partager

1. Cliquez **Save**
2. Cliquez **Share** et copiez le lien
3. Ouvrez le lien dans un nouvel onglet pour vérifier l'affichage du dashboard en mode consultation

### Vérification des connaissances

**Question 1**
Quelle est la principale différence entre un Real-Time Dashboard et un rapport Power BI dans Microsoft Fabric ?

- A) Un Real-Time Dashboard supporte plus de types de visualisations qu'un rapport Power BI
- B) Un Real-Time Dashboard interroge directement une KQL Database et se rafraîchit avec une latence de quelques secondes, tandis que Power BI est optimisé pour l'analytique historique via des semantic models ✓
- C) Un Real-Time Dashboard ne peut pas être partagé avec d'autres utilisateurs
- D) Un rapport Power BI supporte KQL, un Real-Time Dashboard supporte uniquement DAX

*Explication : La différence fondamentale est l'optimisation pour des données en mouvement. Les Real-Time Dashboards interrogent directement l'Eventhouse via KQL avec une latence de secondes. Power BI utilise des semantic models (datasets) avec des cycles de refresh en minutes.*

---

**Question 2**
Vous avez un dashboard avec 5 tuiles qui filtrent toutes les données sur les 30 dernières minutes et récupèrent le dernier état de chaque quartier. Comment optimiser ce dashboard pour éviter de dupliquer cette logique ?

- A) Créer 5 copies du même Eventstream
- B) Créer une vue matérialisée dans l'Eventhouse
- C) Créer une requête de base (base query) qui encapsule ce filtre commun, puis référencer cette base query dans chaque tuile ✓
- D) Augmenter la fréquence d'auto-refresh

*Explication : Les **base queries** sont exactement conçues pour ce cas d'usage : centraliser la logique de filtrage commune à plusieurs tuiles. En modifiant la base query, toutes les tuiles qui l'utilisent sont mises à jour automatiquement.*

---

**Question 3**
Un utilisateur souhaite voir uniquement les données du quartier "Chelsea" dans votre dashboard. Quelle fonctionnalité devez-vous configurer ?

- A) Créer une nouvelle base query spécifique à Chelsea
- B) Créer un paramètre dans le dashboard permettant de sélectionner un quartier ✓
- C) Créer une page séparée pour Chelsea
- D) Modifier toutes les requêtes des tuiles pour ajouter `where Neighbourhood == "Chelsea"`

*Explication : Les **paramètres** permettent aux utilisateurs de filtrer interactivement les données du dashboard sans modifier les requêtes. Le paramètre est configuré avec une liste de valeurs (ici les quartiers distincts) et référencé dans la base query ou les requêtes des tuiles.*

---

**Question 4**
Vous configurez l'auto-refresh de votre dashboard avec un "Minimum time interval" de 5 minutes. Qu'est-ce que cela signifie ?

- A) Le dashboard se rafraîchit automatiquement toutes les 5 minutes exactement
- B) Les utilisateurs ne peuvent pas rafraîchir le dashboard plus souvent que toutes les 5 minutes ✓
- C) Les données affichées ont au maximum 5 minutes de retard
- D) Le dashboard se rafraîchit après 5 minutes d'inactivité

*Explication : Le "Minimum time interval" définit la fréquence minimale de refresh que les utilisateurs peuvent sélectionner. En mettant 5 minutes, vous empêchez les utilisateurs de configurer un refresh à 30 secondes qui pourrait surcharger l'Eventhouse.*

**Question 5**
Pour afficher des stations de vélos sur une carte avec des points de taille proportionnelle au nombre de vélos disponibles, quel type de visualisation et quels paramètres choisissez-vous ?

## Résumé

*1 min*

Dans ce module, vous avez maîtrisé la création de **tableaux de bord en temps réel** dans Microsoft Fabric pour visualiser des données en mouvement.

Points clés à retenir :

- Les **Real-Time Dashboards** sont alimentés directement par des requêtes KQL sur un Eventhouse, avec une latence de quelques secondes et un auto-refresh configurable
- Chaque dashboard se connecte à une ou plusieurs **sources de données** (KQL Databases dans un Eventhouse)
- Les **tuiles** sont les briques visuelles du dashboard, chacune alimentée par une requête KQL. Elles supportent de nombreux types : table, graphiques, carte géospatiale, jauge, stat...
- Les **requêtes de base (base queries)** centralisent la logique partagée entre plusieurs tuiles, améliorant la maintenabilité et la cohérence
- Les **paramètres** permettent une interactivité dynamique : les utilisateurs peuvent filtrer les données affichées sans modifier le dashboard
- L'**auto-refresh** maintient les visualisations à jour automatiquement, avec un minimum de 30 secondes
- L'organisation en **pages** permet de structurer un dashboard complexe par thématique
- Le dashboard peut être **partagé** via un lien direct, avec gestion fine des permissions
