## 1. Comprendre les entrepôts de données

### Définition et rôle d'un data warehouse

Un **entrepôt de données (data warehouse)** est une base de données relationnelle conçue spécifiquement pour l'analytique et le reporting, par opposition aux bases de données OLTP (Online Transaction Processing) optimisées pour les opérations transactionnelles à haute fréquence.

Les caractéristiques fondamentales d'un data warehouse :

| Caractéristique | Base OLTP | Data Warehouse |
|----------------|-----------|----------------|
| **Objectif** | Transactions (INSERT/UPDATE) | Analyse et reporting |
| **Schéma** | Normalisé (3NF) | Dénormalisé (étoile, flocon) |
| **Volume de données** | Faible à moyen | Large à très large |
| **Requêtes** | Simples, nombreuses, courtes | Complexes, agrégations, JOIN |
| **Utilisateurs** | Systèmes applicatifs | Analystes, Data Scientists |
| **Fréquence de mise à jour** | Temps réel | Périodique (batch) |
| **Historique** | Limité | Long terme (3 à 10+ ans) |

### La modélisation dimensionnelle

La modélisation dimensionnelle est la méthodologie de conception d'un data warehouse, popularisée par Ralph Kimball. Elle organise les données selon deux types de tables :

**Tables de faits (Fact Tables)** : contiennent les mesures numériques d'un processus métier (chiffres d'affaires, quantités, durées). Chaque ligne représente un événement ou une transaction. Les tables de faits sont généralement volumineuses et contiennent principalement des clés étrangères et des mesures.

**Tables de dimensions (Dimension Tables)** : contiennent les attributs descriptifs permettant d'analyser les faits selon différentes perspectives (client, produit, temps, géographie). Les dimensions sont généralement plus petites et contiennent des données textuelles riches.

### Le schéma en étoile

Le schéma en étoile (Star Schema) est le modèle le plus courant dans un data warehouse. La table de faits est au centre, entourée de tables de dimensions connectées via des clés de substitution (surrogate keys).

```
                    DimDate
                   ┌─────────┐
                   │ DateKey │
                   │ Year    │
                   │ Month   │
                   │ Day     │
                   └────┬────┘
                        │
DimCustomer    ──── FactSalesOrder ──── DimProduct
┌──────────┐  │   ┌──────────────┐  │  ┌──────────┐
│CustomerKey│◄─┘   │OrderKey (PK) │  └─►│ProductKey│
│Name       │      │CustomerKey   │     │Name      │
│Region     │      │ProductKey    │     │Category  │
│Email      │      │DateKey       │     │Price     │
└──────────┘      │Quantity      │     └──────────┘
                   │SalesTotal    │
                   └──────────────┘
```

Avantages du schéma en étoile :
- **Performance des requêtes** : les JOINs sont simples (une table de faits joint plusieurs dimensions)
- **Facilité de compréhension** : structure intuitive pour les analystes
- **Compatibilité Power BI** : le mode DirectLake fonctionne optimalement avec ce schéma

### Schéma en flocon (Snowflake Schema)

Variante du schéma en étoile où les dimensions sont normalisées en plusieurs tables. Par exemple, une dimension Produit peut être décomposée en tables Produit, Catégorie et Sous-catégorie. Moins courant car il complexifie les requêtes sans gain de performance significatif.

## 2. L'entrepôt de données dans Microsoft Fabric

### Différences avec un Lakehouse

Dans Fabric, il existe deux types de magasins de données analytiques. Comprendre leurs différences est essentiel pour choisir le bon outil :

| Critère | Lakehouse (SQL Endpoint) | Data Warehouse Fabric |
|---------|--------------------------|----------------------|
| **Langage** | SQL (lecture seule) + Spark | T-SQL complet (lecture/écriture) |
| **DML** | Non supporté via SQL | INSERT, UPDATE, DELETE, MERGE |
| **Transactions ACID** | Via Spark uniquement | Natives T-SQL |
| **Schéma** | Flexible (Delta Parquet) | Défini (CREATE TABLE) |
| **Contraintes** | Non enforced | PK, FK (NOT ENFORCED) |
| **Cas d'usage** | Exploration, Spark ETL | DW traditionnel, rapports SQL |
| **Performances analytiques** | Bonnes avec Spark | Excellentes avec T-SQL |

### Architecture d'un Data Warehouse Fabric

Un Data Warehouse Fabric est un moteur T-SQL complet stockant ses données physiquement dans OneLake au format Delta Parquet. Il combine :

1. **Moteur de requête SQL** : compatible avec la plupart des syntaxes T-SQL de SQL Server / Synapse Analytics
2. **Stockage OneLake** : les données sont stockées en Delta Parquet dans OneLake, accessibles également via Spark
3. **Endpoint TDS** : connexion via SQL Server Management Studio, Azure Data Studio, ou d'autres outils ODBC/JDBC
4. **Modèle sémantique par défaut** : un modèle Power BI DirectLake est automatiquement généré pour chaque warehouse

### Fonctionnalités T-SQL supportées

Le Data Warehouse Fabric supporte un sous-ensemble riche du T-SQL :

- DDL : `CREATE TABLE`, `ALTER TABLE`, `DROP TABLE`, `CREATE VIEW`, `CREATE PROCEDURE`, `CREATE FUNCTION`
- DML : `INSERT`, `UPDATE`, `DELETE`, `MERGE`, `TRUNCATE`
- Requêtes : `SELECT`, `JOIN`, `GROUP BY`, `HAVING`, `ORDER BY`, `UNION`, `CTE`, fenêtrage
- Sécurité : `GRANT`, `DENY`, `REVOKE`, Row-Level Security, Column-Level Security
- Statistiques : `CREATE STATISTICS`, `UPDATE STATISTICS`

Fonctionnalités **non supportées** dans la version actuelle :
- Identités (IDENTITY avec auto-incrément géré automatiquement à la création)
- Curseurs T-SQL
- Certains types de données spécialisés (geography, geometry, hierarchyid)
- Triggers

## 3. Créer un Data Warehouse dans Fabric

### Étapes de création

1. Dans votre espace de travail Fabric, cliquer sur **+ Nouvel élément** ou **Créer**
2. Sélectionner **Entrepôt** dans la section Data Warehouse
3. Donner un nom unique à l'entrepôt (ex: `AdventureWorksDW`)
4. Patienter 1 à 2 minutes le temps du provisionnement

Une fois créé, l'interface du warehouse affiche :

- **Éditeur de requêtes SQL** (centre) : zone d'édition T-SQL avec IntelliSense
- **Barre d'outils** : boutons Run, New SQL Query, New Visual Query, Nouveau modèle sémantique

### Créer les tables du schéma dimensionnel

Voici comment créer un schéma en étoile complet pour un entrepôt de ventes :

```sql
-- Créer la table de dimension Date
CREATE TABLE dbo.DimDate
(
    DateKey         INT         NOT NULL,   -- Clé de substitution (YYYYMMDD)
    FullDate        DATE        NOT NULL,
    Year            SMALLINT    NOT NULL,
    Quarter         TINYINT     NOT NULL,
    Month           TINYINT     NOT NULL,
    MonthName       VARCHAR(10) NOT NULL,
    DayOfMonth      TINYINT     NOT NULL,
    DayOfWeek       TINYINT     NOT NULL,
    DayName         VARCHAR(10) NOT NULL,
    IsWeekend       BIT         NOT NULL DEFAULT 0,
    FiscalYear      SMALLINT    NOT NULL,
    FiscalQuarter   TINYINT     NOT NULL
);
GO

-- Créer la table de dimension Client
CREATE TABLE dbo.DimCustomer
(
    CustomerKey     INT             NOT NULL,   -- Clé de substitution
    CustomerAltKey  VARCHAR(25)     NULL,        -- Clé métier (ID source)
    CustomerName    NVARCHAR(100)   NOT NULL,
    EmailAddress    VARCHAR(150)    NULL,
    Phone           VARCHAR(25)     NULL,
    CountryRegion   NVARCHAR(50)    NULL,
    City            NVARCHAR(50)    NULL,
    PostalCode      VARCHAR(20)     NULL,
    -- Attributs SCD Type 2 (Slowly Changing Dimension)
    EffectiveDate   DATE            NOT NULL DEFAULT GETDATE(),
    ExpirationDate  DATE            NULL,
    IsCurrent       BIT             NOT NULL DEFAULT 1
);
GO

-- Créer la table de dimension Produit
CREATE TABLE dbo.DimProduct
(
    ProductKey      INT             NOT NULL,
    ProductAltKey   VARCHAR(25)     NULL,
    ProductName     NVARCHAR(100)   NOT NULL,
    Category        NVARCHAR(50)    NULL,
    SubCategory     NVARCHAR(50)    NULL,
    ListPrice       DECIMAL(10,2)   NULL,
    StandardCost    DECIMAL(10,2)   NULL,
    Color           NVARCHAR(20)    NULL,
    Size            NVARCHAR(20)    NULL
);
GO

-- Créer la table de faits Commandes de ventes
CREATE TABLE dbo.FactSalesOrder
(
    SalesOrderKey       INT             NOT NULL,   -- Clé de substitution
    SalesOrderNumber    VARCHAR(30)     NOT NULL,   -- Clé métier
    SalesOrderLineNumber TINYINT        NOT NULL,
    -- Clés étrangères vers les dimensions
    CustomerKey         INT             NOT NULL,
    ProductKey          INT             NOT NULL,
    SalesOrderDateKey   INT             NOT NULL,
    ShipDateKey         INT             NULL,
    -- Mesures numériques
    OrderQuantity       SMALLINT        NOT NULL,
    UnitPrice           DECIMAL(10,2)   NOT NULL,
    UnitPriceDiscount   DECIMAL(5,2)    NOT NULL DEFAULT 0,
    UnitCost            DECIMAL(10,2)   NULL,
    SalesAmount         DECIMAL(10,2)   NOT NULL,
    TaxAmount           DECIMAL(10,2)   NOT NULL DEFAULT 0,
    FreightAmount       DECIMAL(10,2)   NOT NULL DEFAULT 0,
    TotalDue            DECIMAL(10,2)   NOT NULL
);
GO
```

## 4. Interroger et transformer des données avec T-SQL

### Requêtes analytiques fondamentales

La puissance d'un data warehouse réside dans sa capacité à répondre à des questions analytiques complexes :

```sql
-- Chiffre d'affaires par mois et par région
SELECT
    d.Year                          AS Année,
    d.Month                         AS Mois,
    d.MonthName                     AS NomMois,
    c.CountryRegion                 AS Région,
    SUM(f.SalesAmount)              AS ChiffreAffaires,
    SUM(f.TaxAmount)                AS TVA,
    SUM(f.TotalDue)                 AS TotalTTC,
    COUNT(DISTINCT f.SalesOrderNumber) AS NombreCommandes,
    SUM(f.OrderQuantity)            AS QuantitéVendue
FROM dbo.FactSalesOrder AS f
JOIN dbo.DimDate AS d        ON f.SalesOrderDateKey = d.DateKey
JOIN dbo.DimCustomer AS c    ON f.CustomerKey = c.CustomerKey
GROUP BY
    d.Year, d.Month, d.MonthName, c.CountryRegion
ORDER BY
    d.Year, d.Month, c.CountryRegion;
```

### Fonctions de fenêtrage (Window Functions)

Les fonctions de fenêtrage permettent des analyses comparatives sans GROUP BY traditionnel :

```sql
-- Top 3 produits par catégorie avec classement
SELECT
    p.Category,
    p.ProductName,
    SUM(f.SalesAmount)          AS TotalVentes,
    RANK() OVER (
        PARTITION BY p.Category
        ORDER BY SUM(f.SalesAmount) DESC
    )                           AS ClassementDansCategorie,
    SUM(SUM(f.SalesAmount)) OVER (
        PARTITION BY p.Category
    )                           AS TotalCategorie,
    ROUND(
        100.0 * SUM(f.SalesAmount) /
        SUM(SUM(f.SalesAmount)) OVER (PARTITION BY p.Category),
        1
    )                           AS PourcentageCategorie
FROM dbo.FactSalesOrder AS f
JOIN dbo.DimProduct AS p ON f.ProductKey = p.ProductKey
GROUP BY p.Category, p.ProductName
ORDER BY p.Category, TotalVentes DESC;
```

### CTE (Common Table Expressions)

Les CTE améliorent la lisibilité des requêtes complexes :

```sql
-- Analyse des performances mensuelles avec comparaison N-1
WITH VentesParMois AS (
    SELECT
        d.Year,
        d.Month,
        d.MonthName,
        SUM(f.SalesAmount) AS ChiffreAffaires
    FROM dbo.FactSalesOrder f
    JOIN dbo.DimDate d ON f.SalesOrderDateKey = d.DateKey
    GROUP BY d.Year, d.Month, d.MonthName
),
VentesAvecComparaison AS (
    SELECT
        v.Year,
        v.Month,
        v.MonthName,
        v.ChiffreAffaires,
        LAG(v.ChiffreAffaires, 12) OVER (ORDER BY v.Year, v.Month) AS CA_N_Moins_1,
        v.ChiffreAffaires - LAG(v.ChiffreAffaires, 12) OVER (ORDER BY v.Year, v.Month) AS Variation
    FROM VentesParMois v
)
SELECT
    Year,
    Month,
    MonthName,
    ChiffreAffaires,
    CA_N_Moins_1,
    Variation,
    CASE
        WHEN CA_N_Moins_1 IS NULL THEN NULL
        ELSE ROUND(100.0 * Variation / CA_N_Moins_1, 1)
    END AS TauxCroissance_Pct
FROM VentesAvecComparaison
ORDER BY Year, Month;
```


### Procédures stockées pour les chargements

```sql
-- Procédure de chargement incrémental des faits
CREATE OR ALTER PROCEDURE dbo.sp_ChargerFactVentes
    @AnneeChargement INT,
    @MoisChargement  TINYINT
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @NbLignesChargees INT = 0;
    DECLARE @DateDebut DATE = DATEFROMPARTS(@AnneeChargement, @MoisChargement, 1);
    DECLARE @DateFin   DATE = EOMONTH(@DateDebut);

    -- Supprimer les doublons si re-exécution
    DELETE FROM dbo.FactSalesOrder
    WHERE SalesOrderDateKey IN (
        SELECT DateKey FROM dbo.DimDate
        WHERE FullDate BETWEEN @DateDebut AND @DateFin
    );

    -- Insérer les nouvelles données depuis la zone staging
    INSERT INTO dbo.FactSalesOrder (
        SalesOrderKey, SalesOrderNumber, SalesOrderLineNumber,
        CustomerKey, ProductKey, SalesOrderDateKey,
        OrderQuantity, UnitPrice, SalesAmount, TaxAmount, TotalDue
    )
    SELECT
        NEXT VALUE FOR dbo.seq_SalesOrderKey,  -- Séquence pour la clé de substitution
        s.OrderNumber,
        s.LineNumber,
        c.CustomerKey,
        p.ProductKey,
        d.DateKey,
        s.Quantity,
        s.UnitPrice,
        s.Quantity * s.UnitPrice * (1 - s.Discount),
        s.Quantity * s.UnitPrice * s.TaxRate,
        s.Quantity * s.UnitPrice * (1 - s.Discount + s.TaxRate)
    FROM dbo.staging_SalesOrder s
    JOIN dbo.DimCustomer c  ON s.CustomerID = c.CustomerAltKey AND c.IsCurrent = 1
    JOIN dbo.DimProduct p   ON s.ProductID = p.ProductAltKey
    JOIN dbo.DimDate d      ON s.OrderDate = d.FullDate
    WHERE s.OrderDate BETWEEN @DateDebut AND @DateFin;

    SET @NbLignesChargees = @@ROWCOUNT;
    PRINT CONCAT('Chargement terminé : ', @NbLignesChargees, ' lignes insérées.');
END;
GO

-- Exécuter la procédure pour le mois de janvier 2024
EXEC dbo.sp_ChargerFactVentes @AnneeChargement = 2024, @MoisChargement = 1;
```

## 5. Modéliser les données pour Power BI

### Modèle sémantique par défaut

Quand vous créez un Data Warehouse dans Fabric, un **modèle sémantique (semantic model) par défaut** est automatiquement créé et maintenu. Ce modèle Power BI en mode DirectLake reflète les tables et vues du warehouse en temps réel, sans nécessiter de publication manuelle.

Pour créer manuellement un modèle sémantique avec des relations définies :

1. Dans la barre d'outils du warehouse, cliquer sur **Nouveau modèle sémantique**
2. Sélectionner les tables à inclure (DimDate, DimCustomer, DimProduct, FactSalesOrder)
3. Dans le concepteur de modèle, créer les relations en faisant glisser les clés :
   - `FactSalesOrder.CustomerKey` → `DimCustomer.CustomerKey` (Plusieurs-à-un)
   - `FactSalesOrder.ProductKey` → `DimProduct.ProductKey` (Plusieurs-à-un)
   - `FactSalesOrder.SalesOrderDateKey` → `DimDate.DateKey` (Plusieurs-à-un)

### Bonnes pratiques de modélisation

Pour optimiser les performances Power BI DirectLake :

- **Clés entières** : utiliser des entiers (INT) comme clés de substitution plutôt que des VARCHAR
- **Tables de dimensions petites** : les dimensions doivent être aussi compactes que possible
- **Éviter les relations bidirectionnelles** : utiliser des relations unidirectionnelles sauf si absolument nécessaire
- **Hiérarchies de dates** : définir les hiérarchies Année > Trimestre > Mois > Jour dans la dimension Date
- **Mesures vs colonnes calculées** : préférer les mesures DAX aux colonnes calculées pour réduire la taille du modèle

## 6. Éditeur de requêtes visuel

L'éditeur de requêtes visuel (Visual Query Editor) permet de créer des requêtes sans écrire de T-SQL, via une interface graphique de type Power Query.

### Utilisation pratique

1. Dans la barre d'outils, cliquer sur **Nouvelle requête visuelle**
2. Faire glisser la table `FactSalesOrder` dans le canvas
3. Faire glisser `DimProduct` dans le canvas
4. Cliquer sur le bouton **(+)** de FactSalesOrder et choisir **Fusionner les requêtes**
5. Sélectionner DimProduct comme table de droite, choisir ProductKey comme clé de jointure
6. Dans l'aperçu, développer la colonne DimProduct et sélectionner ProductName, Category
7. Appliquer des filtres, des agrégations ou des transformations via le menu contextuel
8. Utiliser **Visualiser les résultats** ou **Télécharger en Excel** pour explorer les résultats

L'éditeur visuel est particulièrement utile pour les analystes non développeurs qui souhaitent explorer les données sans connaître T-SQL.

## Vérification des connaissances

**Question 1.** Quelle est la principale différence entre un endpoint SQL d'un Lakehouse et un Data Warehouse Fabric ?

A) Le Lakehouse ne supporte pas SQL du tout  
B) L'endpoint SQL d'un Lakehouse est en lecture seule ; le Data Warehouse Fabric supporte T-SQL complet avec INSERT, UPDATE, DELETE  
C) Le Data Warehouse Fabric est plus lent que le Lakehouse pour les requêtes analytiques  
D) Le Lakehouse et le Data Warehouse Fabric sont identiques, seul le nom change  

**Réponse correcte : B** — L'endpoint SQL d'un Lakehouse est automatiquement généré et ne supporte que les opérations de lecture. Le Data Warehouse Fabric offre un T-SQL transactionnel complet.

---

**Question 2.** Dans un schéma en étoile, quel type de table contient les mesures numériques comme les chiffres d'affaires et les quantités ?

A) Table de dimension  
B) Table de faits  
C) Table de staging  
D) Table de référence  

**Réponse correcte : B** — Les tables de faits contiennent les mesures numériques (chiffres d'affaires, quantités, coûts) et les clés étrangères vers les tables de dimensions.

**Question 3.** Vous souhaitez analyser les ventes par produit et par région sans écrire de T-SQL. Quel outil Fabric utilisez-vous ?

A) L'éditeur de requêtes SQL avec l'option IntelliSense  
B) L'éditeur de requêtes visuel (Visual Query Editor)  
C) Power BI Desktop en mode Import  
D) Azure Data Studio  

**Réponse correcte : B** — L'éditeur de requêtes visuel permet de créer des requêtes analytiques de manière graphique, sans code T-SQL.

---

**Question 4.** Quelle est l'utilité principale d'une clé de substitution (surrogate key) dans un data warehouse ?

A) Accélérer les requêtes de recherche full-text  
B) Remplacer les clés métier changeantes par des identifiants stables et entiers pour les jointures  
C) Permettre le chiffrement des données sensibles  
D) Réduire le volume de stockage des tables de faits  

**Réponse correcte : B** — Les clés de substitution sont des entiers générés par le DW, indépendants des clés métier sources. Elles restent stables même si les clés sources changent (SCD Type 2) et optimisent les performances des JOIN.

**Question 5.** Quelle instruction T-SQL permet de modifier une ligne existante si elle correspond à une condition ou d'en insérer une nouvelle si elle n'existe pas ?

A) `INSERT OR UPDATE`  
B) `UPSERT INTO`  
C) `MERGE`  
D) `REPLACE INTO`  

**Réponse correcte : C** — L'instruction MERGE (aussi appelée UPSERT) permet de fusionner des données sources avec une table cible : UPDATE si la ligne existe, INSERT si elle n'existe pas.

## Résumé

Dans ce module, vous avez appris les fondamentaux du Data Warehouse dans Microsoft Fabric :

- Un **data warehouse** est une base de données relationnelle optimisée pour l'analytique, utilisant le schéma en étoile avec des tables de faits et de dimensions
- Le **Data Warehouse Fabric** supporte T-SQL complet (INSERT, UPDATE, DELETE, MERGE) contrairement à l'endpoint SQL d'un Lakehouse
- Les données sont physiquement stockées dans **OneLake** au format Delta Parquet, accessibles aussi bien via T-SQL que via Spark
- L'éditeur de **requêtes visuel** permet l'exploration des données sans code pour les analystes non-développeurs
- Un **modèle sémantique** Power BI DirectLake est automatiquement créé et maintenu pour les rapports en aval
