## 1. Stratégies de chargement de données

### Vue d'ensemble des approches ELT vs ETL

Dans un Data Warehouse Fabric, le paradigme dominant est **ELT (Extract, Load, Transform)** plutôt qu'ETL traditionnel :

- **ETL traditionnel** : Extraire → Transformer (hors du DW) → Charger les données transformées
- **ELT moderne** : Extraire → Charger (dans une zone staging) → Transformer (dans le DW avec T-SQL/Spark)

L'ELT tire parti de la puissance de calcul du moteur Fabric plutôt que de dépendre d'un serveur ETL intermédiaire. Cela simplifie l'architecture et améliore les performances de chargement.

### Comparaison des méthodes de chargement

| Méthode | Cas d'usage | Avantages | Inconvénients |
|---------|-------------|-----------|---------------|
| **T-SQL direct** (INSERT, MERGE) | Transformations complexes, logique métier | Contrôle total, performance | Nécessite expertise SQL |
| **COPY INTO** | Ingestion massive depuis stockage externe | Très rapide, parallèle | Peu de transformation |
| **Pipelines de données** | Orchestration ETL complexe | Visuel, planification, monitoring | Plus de configuration |
| **Dataflows Gen2** | Transformation sans code | Accessible aux analystes | Limites sur volumes très larges |
| **Requêtes inter-bases** | Accès Lakehouse depuis Warehouse | Aucun déplacement de données | Latence légèrement supérieure |
| **Spark Notebooks** | Transformations complexes à grande échelle | Puissance Spark, Python/Scala | Nécessite expertise Spark |

## 2. Chargement avec T-SQL

### INSERT direct

La méthode la plus simple pour charger des données est l'instruction INSERT. Elle convient aux petits volumes et aux chargements manuels :

```sql
-- Insertion simple de lignes individuelles
INSERT INTO dbo.DimProduct (ProductKey, ProductAltKey, ProductName, Category, ListPrice)
VALUES
(10, 'BIKE-001', 'Mountain Bike Pro 300', 'Vélos', 2299.99),
(11, 'BIKE-002', 'Road Bike Elite 500', 'Vélos', 3499.99),
(12, 'ACC-001', 'Pompe de vélo portable', 'Accessoires', 24.99);

-- Insertion depuis une autre table (INSERT INTO ... SELECT)
INSERT INTO dbo.DimProduct (ProductKey, ProductAltKey, ProductName, Category, ListPrice)
SELECT
    ROW_NUMBER() OVER (ORDER BY p.ProductID) + 100  AS ProductKey,
    CONCAT('PROD-', p.ProductID)                     AS ProductAltKey,
    p.ProductName,
    p.CategoryName,
    p.ListPrice
FROM dbo.staging_Products AS p
WHERE p.IsActive = 1
    AND p.ProductName NOT IN (SELECT ProductName FROM dbo.DimProduct);
```

### COPY INTO pour l'ingestion massive

`COPY INTO` est l'instruction optimisée pour l'ingestion de grands volumes de données depuis des fichiers stockés dans Azure Blob Storage, ADLS Gen2 ou OneLake :

```sql
-- Ingestion de fichiers Parquet depuis Azure Blob Storage
COPY INTO dbo.FactSalesOrder
FROM 'https://moncompte.blob.core.windows.net/sales-data/2024/'
WITH (
    FILE_TYPE = 'PARQUET',
    COMPRESSION = 'SNAPPY',
    CREDENTIAL = (IDENTITY = 'Managed Identity')
);

-- Ingestion de fichiers CSV avec options de formatage
COPY INTO dbo.staging_RawSales
FROM 'https://moncompte.blob.core.windows.net/imports/sales-*.csv'
WITH (
    FILE_TYPE = 'CSV',
    FIELDTERMINATOR = ',',
    ROWTERMINATOR = '\n',
    FIRSTROW = 2,               -- Ignorer la ligne d'en-tête
    ENCODING = 'UTF8',
    MAXERRORS = 100,            -- Tolérer jusqu'à 100 erreurs avant abandon
    ERRORFILE = 'https://moncompte.blob.core.windows.net/errors/'
);

-- Ingestion de fichiers JSON depuis OneLake
COPY INTO dbo.staging_Events
FROM 'https://onelake.dfs.fabric.microsoft.com/workspace-id/lakehouse-id/Files/events/'
WITH (
    FILE_TYPE = 'JSON',
    CREDENTIAL = (IDENTITY = 'Managed Identity')
);
```

### Pattern avec tables de staging

Le pattern staging est fondamental dans l'architecture d'un data warehouse. Les données brutes sont d'abord chargées dans une zone tampon (staging) avant d'être transformées et chargées dans les tables finales.

```sql
-- Étape 1 : Créer le schéma de staging
CREATE SCHEMA staging;
GO

-- Étape 2 : Créer la table de staging (structure identique à la source)
CREATE TABLE staging.SalesStage
(
    RawID           INT,
    OrderDate       NVARCHAR(20),   -- Données brutes en texte
    CustomerName    NVARCHAR(100),
    CustomerEmail   NVARCHAR(150),
    ProductCode     NVARCHAR(25),
    ProductName     NVARCHAR(100),
    Quantity        NVARCHAR(10),   -- Texte, à convertir
    UnitPrice       NVARCHAR(15),   -- Texte, à convertir
    Discount        NVARCHAR(10),
    TaxRate         NVARCHAR(10),
    Region          NVARCHAR(50),
    LoadDate        DATETIME DEFAULT GETDATE(),
    IsProcessed     BIT DEFAULT 0
);
GO

-- Étape 3 : Charger les données brutes dans le staging
COPY INTO staging.SalesStage (RawID, OrderDate, CustomerName, CustomerEmail,
    ProductCode, ProductName, Quantity, UnitPrice, Discount, TaxRate, Region)
FROM 'https://moncompte.blob.core.windows.net/raw/sales-2024-01.csv'
WITH (FILE_TYPE = 'CSV', FIRSTROW = 2, FIELDTERMINATOR = ';');

-- Étape 4 : Valider les données dans le staging
SELECT
    COUNT(*)                                                    AS TotalLignes,
    SUM(CASE WHEN OrderDate IS NULL THEN 1 ELSE 0 END)         AS LignesSansDate,
    SUM(CASE WHEN CustomerEmail IS NULL THEN 1 ELSE 0 END)     AS LignesSansEmail,
    SUM(CASE WHEN TRY_CAST(Quantity AS INT) IS NULL THEN 1 ELSE 0 END) AS QuantitésInvalides,
    SUM(CASE WHEN TRY_CAST(UnitPrice AS DECIMAL(10,2)) IS NULL THEN 1 ELSE 0 END) AS PrixInvalides
FROM staging.SalesStage
WHERE IsProcessed = 0;

-- Étape 5 : Transformer et charger dans les dimensions (exemple Client)
INSERT INTO dbo.DimCustomer (CustomerKey, CustomerAltKey, CustomerName, EmailAddress, CountryRegion)
SELECT DISTINCT
    ABS(CHECKSUM(s.CustomerEmail))  AS CustomerKey,   -- Clé de substitution déterministe
    s.CustomerEmail                 AS CustomerAltKey,
    s.CustomerName,
    s.CustomerEmail,
    s.Region
FROM staging.SalesStage s
WHERE s.IsProcessed = 0
    AND s.CustomerEmail IS NOT NULL
    AND NOT EXISTS (
        SELECT 1 FROM dbo.DimCustomer dc
        WHERE dc.CustomerAltKey = s.CustomerEmail
    );
```

### MERGE pour les chargements incrémentiels (UPSERT)

L'instruction MERGE est idéale pour les chargements incrémentiels qui doivent mettre à jour les enregistrements existants et en insérer de nouveaux :

```sql
-- MERGE pour maintenir la dimension Client à jour
MERGE dbo.DimCustomer AS cible
USING (
    SELECT DISTINCT
        CustomerEmail                   AS CustomerAltKey,
        CustomerName,
        CustomerEmail                   AS EmailAddress,
        Region                          AS CountryRegion
    FROM staging.SalesStage
    WHERE IsProcessed = 0
        AND CustomerEmail IS NOT NULL
) AS source
ON cible.CustomerAltKey = source.CustomerAltKey

-- Si le client existe : mettre à jour les attributs modifiables
WHEN MATCHED AND (
    cible.CustomerName  <> source.CustomerName OR
    cible.CountryRegion <> source.CountryRegion
) THEN
    UPDATE SET
        cible.CustomerName  = source.CustomerName,
        cible.CountryRegion = source.CountryRegion

-- Si le client n'existe pas : l'insérer
WHEN NOT MATCHED BY TARGET THEN
    INSERT (CustomerKey, CustomerAltKey, CustomerName, EmailAddress, CountryRegion)
    VALUES (
        ABS(CHECKSUM(source.CustomerAltKey)),
        source.CustomerAltKey,
        source.CustomerName,
        source.EmailAddress,
        source.CountryRegion
    );

-- Afficher le résultat
SELECT @@ROWCOUNT AS LignesAffectees;
```

### Chargement de la table de faits avec MERGE complet

```sql
-- MERGE complet pour la table de faits (INSERT seulement, UPDATE et DELETE optionnels)
MERGE dbo.FactSalesOrder AS cible
USING (
    SELECT
        s.RawID,
        CONCAT(s.RawID, '-01')      AS SalesOrderNumber,
        1                           AS SalesOrderLineNumber,
        dc.CustomerKey,
        dp.ProductKey,
        dd.DateKey                  AS SalesOrderDateKey,
        TRY_CAST(s.Quantity AS SMALLINT) AS OrderQuantity,
        TRY_CAST(s.UnitPrice AS DECIMAL(10,2)) AS UnitPrice,
        TRY_CAST(s.Discount AS DECIMAL(5,2)) AS UnitPriceDiscount,
        TRY_CAST(s.Quantity AS SMALLINT)
            * TRY_CAST(s.UnitPrice AS DECIMAL(10,2))
            * (1 - ISNULL(TRY_CAST(s.Discount AS DECIMAL(5,2)), 0))  AS SalesAmount,
        TRY_CAST(s.Quantity AS SMALLINT)
            * TRY_CAST(s.UnitPrice AS DECIMAL(10,2))
            * ISNULL(TRY_CAST(s.TaxRate AS DECIMAL(5,2)), 0)         AS TaxAmount
    FROM staging.SalesStage s
    JOIN dbo.DimCustomer dc ON s.CustomerEmail = dc.CustomerAltKey AND dc.IsCurrent = 1
    JOIN dbo.DimProduct  dp ON s.ProductCode  = dp.ProductAltKey
    JOIN dbo.DimDate     dd ON TRY_CAST(s.OrderDate AS DATE) = dd.FullDate
    WHERE s.IsProcessed = 0
        AND TRY_CAST(s.Quantity AS SMALLINT) IS NOT NULL
        AND TRY_CAST(s.UnitPrice AS DECIMAL(10,2)) IS NOT NULL
) AS source
ON cible.SalesOrderNumber = source.SalesOrderNumber
    AND cible.SalesOrderLineNumber = source.SalesOrderLineNumber

WHEN NOT MATCHED BY TARGET THEN
    INSERT (SalesOrderKey, SalesOrderNumber, SalesOrderLineNumber,
            CustomerKey, ProductKey, SalesOrderDateKey,
            OrderQuantity, UnitPrice, UnitPriceDiscount,
            SalesAmount, TaxAmount, TotalDue)
    VALUES (
        source.RawID,
        source.SalesOrderNumber,
        source.SalesOrderLineNumber,
        source.CustomerKey,
        source.ProductKey,
        source.SalesOrderDateKey,
        source.OrderQuantity,
        source.UnitPrice,
        source.UnitPriceDiscount,
        source.SalesAmount,
        source.TaxAmount,
        source.SalesAmount + source.TaxAmount
    );

-- Marquer les lignes comme traitées dans le staging
UPDATE staging.SalesStage
SET IsProcessed = 1
WHERE IsProcessed = 0;
```

## 3. Requêtes inter-bases (Cross-database Queries)

### Accéder aux données d'un Lakehouse depuis un Warehouse

L'une des fonctionnalités les plus puissantes de Fabric est la possibilité d'interroger directement les données d'un Lakehouse depuis un Warehouse, sans copier les données. Le Lakehouse expose automatiquement un endpoint SQL, accessible via une syntaxe en trois parties : `[NomLakehouse].[schema].[table]`.

```sql
-- Créer une vue dans le Warehouse qui pointe vers le Lakehouse
-- (remplacer 'MonLakehouse' par le nom réel du lakehouse)
CREATE VIEW staging.vw_SalesFromLakehouse
AS
SELECT *
FROM [MonLakehouse].[dbo].[staging_sales];
GO

-- Utiliser la vue pour charger les données
INSERT INTO dbo.FactSalesOrder (
    SalesOrderKey, SalesOrderNumber, SalesOrderLineNumber,
    CustomerKey, ProductKey, SalesOrderDateKey,
    OrderQuantity, UnitPrice, SalesAmount, TaxAmount, TotalDue
)
SELECT
    ROW_NUMBER() OVER (ORDER BY s.SalesOrderNumber, CAST(s.SalesOrderLineNumber AS INT)) + 10000,
    s.SalesOrderNumber,
    CAST(s.SalesOrderLineNumber AS INT),
    dc.CustomerKey,
    di.ItemID,
    dd.DateKey,
    CAST(s.Quantity AS INT),
    CAST(s.UnitPrice AS FLOAT),
    CAST(s.Quantity AS INT) * CAST(s.UnitPrice AS FLOAT),
    CAST(s.TaxAmount AS FLOAT),
    CAST(s.Quantity AS INT) * CAST(s.UnitPrice AS FLOAT) + CAST(s.TaxAmount AS FLOAT)
FROM staging.vw_SalesFromLakehouse s
JOIN dbo.DimCustomer dc ON s.CustomerName = dc.CustomerName
JOIN dbo.DimProduct  di ON s.Item = di.ProductName
JOIN dbo.DimDate     dd ON CAST(s.OrderDate AS DATE) = dd.FullDate
WHERE YEAR(CAST(s.OrderDate AS DATE)) = 2024;
```

### Procédure stockée de chargement avec requête inter-bases

```sql
-- Procédure complète utilisant une requête inter-bases vers un lakehouse
CREATE OR ALTER PROCEDURE dbo.usp_LoadSalesFromLakehouse
    @AnneeCible INT,
    @MoisCible  TINYINT = NULL  -- NULL = toute l'année
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @DateDebut DATE;
    DECLARE @DateFin   DATE;

    IF @MoisCible IS NULL
    BEGIN
        SET @DateDebut = DATEFROMPARTS(@AnneeCible, 1, 1);
        SET @DateFin   = DATEFROMPARTS(@AnneeCible, 12, 31);
    END
    ELSE
    BEGIN
        SET @DateDebut = DATEFROMPARTS(@AnneeCible, @MoisCible, 1);
        SET @DateFin   = EOMONTH(@DateDebut);
    END

    -- Charger les clients manquants
    INSERT INTO dbo.DimCustomer (CustomerKey, CustomerAltKey, CustomerName, EmailAddress)
    SELECT DISTINCT
        ABS(CHECKSUM(s.CustomerName)),
        s.CustomerName,
        s.CustomerName,
        s.EmailAddress
    FROM [MonLakehouse].[dbo].[staging_sales] s
    WHERE CAST(s.OrderDate AS DATE) BETWEEN @DateDebut AND @DateFin
        AND NOT EXISTS (
            SELECT 1 FROM dbo.DimCustomer dc WHERE dc.CustomerName = s.CustomerName
        );

    -- Charger les produits manquants
    INSERT INTO dbo.DimProduct (ProductKey, ProductAltKey, ProductName)
    SELECT DISTINCT
        ABS(CHECKSUM(s.Item)),
        s.Item,
        s.Item
    FROM [MonLakehouse].[dbo].[staging_sales] s
    WHERE CAST(s.OrderDate AS DATE) BETWEEN @DateDebut AND @DateFin
        AND NOT EXISTS (
            SELECT 1 FROM dbo.DimProduct dp WHERE dp.ProductName = s.Item
        );

    -- Charger les faits
    INSERT INTO dbo.FactSalesOrder (
        SalesOrderKey, SalesOrderNumber, SalesOrderLineNumber,
        CustomerKey, ProductKey, SalesOrderDateKey,
        OrderQuantity, UnitPrice, SalesAmount, TaxAmount, TotalDue
    )
    SELECT
        ABS(CHECKSUM(s.SalesOrderNumber, s.SalesOrderLineNumber)),
        s.SalesOrderNumber,
        CAST(s.SalesOrderLineNumber AS INT),
        dc.CustomerKey,
        dp.ProductKey,
        dd.DateKey,
        CAST(s.Quantity AS INT),
        CAST(s.UnitPrice AS FLOAT),
        CAST(s.Quantity AS INT) * CAST(s.UnitPrice AS FLOAT),
        CAST(s.TaxAmount AS FLOAT),
        CAST(s.Quantity AS INT) * CAST(s.UnitPrice AS FLOAT) + CAST(s.TaxAmount AS FLOAT)
    FROM [MonLakehouse].[dbo].[staging_sales] s
    JOIN dbo.DimCustomer dc ON s.CustomerName = dc.CustomerName
    JOIN dbo.DimProduct  dp ON s.Item = dp.ProductName
    JOIN dbo.DimDate     dd ON CAST(s.OrderDate AS DATE) = dd.FullDate
    WHERE CAST(s.OrderDate AS DATE) BETWEEN @DateDebut AND @DateFin;

    PRINT CONCAT('Chargement terminé : ', @@ROWCOUNT, ' lignes de faits insérées pour ',
                 @DateDebut, ' à ', @DateFin);
END;
GO

-- Exécuter pour l'année 2024
EXEC dbo.usp_LoadSalesFromLakehouse @AnneeCible = 2024;

-- Exécuter pour janvier 2024 seulement
EXEC dbo.usp_LoadSalesFromLakehouse @AnneeCible = 2024, @MoisCible = 1;
```

## 4. Pipelines de données pour le chargement

### Créer un pipeline dans Data Factory Fabric

Les pipelines de données (Data Factory) permettent d'orchestrer visuellement les flux de chargement, de planifier leur exécution et de gérer les erreurs de manière centralisée.

**Étapes de création d'un pipeline de chargement :**

1. Dans l'espace de travail, créer un nouveau **Pipeline de données**
2. Ajouter une activité **Copier les données** (Copy Data)
3. Configurer la **source** :
   - Type : Stockage Azure Blob / ADLS Gen2 / HTTP
   - Fichier : `sales-data/*.parquet`
   - Format : Parquet
4. Configurer le **récepteur (sink)** :
   - Type : Entrepôt de données Microsoft Fabric
   - Table de destination : `dbo.staging_SalesStage`
   - Mode d'écriture : Append (ajouter) ou Overwrite (écraser)
5. Ajouter une activité **Script SQL** après la copie pour déclencher le traitement :
   ```sql
   EXEC dbo.usp_ProcessStagingData;
   ```
6. Configurer un **déclencheur** :
   - Planifié : quotidien à 02:00
   - Événementiel : à l'arrivée d'un nouveau fichier dans le blob storage

### Architecture de pipeline ELT typique

```
[Source Blob Storage]
        │
        ▼ Activité "Copy Data"
[staging.RawSalesStage]  ← Chargement brut, sans transformation
        │
        ▼ Activité "Script SQL" : EXEC usp_ValidateStaging
[Validation des données]
        │
        ├── Erreurs → [staging.SalesErrors] + Notification email
        │
        ▼ Activité "Script SQL" : EXEC usp_LoadDimensions
[dbo.DimCustomer, DimProduct, DimDate]  ← Dimensions d'abord
        │
        ▼ Activité "Script SQL" : EXEC usp_LoadFacts
[dbo.FactSalesOrder]  ← Faits ensuite (référencent les dimensions)
        │
        ▼ Activité "Script SQL" : UPDATE staging.IsProcessed = 1
[Marquage des données traitées]
```

### Paramétrer un pipeline pour les chargements incrémentiels

Les pipelines peuvent être paramétrés pour des chargements flexibles :

- Paramètre `@AnneeCible` (INT) : année à charger
- Paramètre `@MoisCible` (INT) : mois à charger (optionnel)
- Variable `@DernierChargement` : date du dernier chargement réussi, stockée dans une table de contrôle

```sql
-- Table de contrôle des chargements (dans le Warehouse)
CREATE TABLE dbo.ControlChargement
(
    NomPipeline         VARCHAR(100)    NOT NULL,
    DernierChargement   DATETIME        NULL,
    StatutDernier       VARCHAR(20)     NULL,  -- 'SUCCESS', 'FAILED', 'RUNNING'
    NombreLignes        INT             NULL,
    DureeSecondes       INT             NULL,
    MessageErreur       NVARCHAR(MAX)   NULL
);
```

## 5. Dataflows Gen2 pour la transformation sans code

### Présentation de Dataflows Gen2

Les Dataflows Gen2 sont l'interface graphique basée sur **Power Query** pour la transformation de données. Ils permettent aux analystes non-développeurs de créer des flux de transformation complexes sans écrire de code, en utilisant plus de 300 transformations disponibles.

**Fonctionnalités clés :**
- Interface visuelle drag-and-drop
- Prévisualisation des données à chaque étape
- Connexion à 150+ sources de données (fichiers, bases de données, API, services cloud)
- Transformations avancées : pivot/unpivot, fusion, agrégation, enrichissement par ML
- Publication dans : OneLake, Data Warehouse, Azure SQL, Lakehouse

### Créer un Dataflow Gen2

1. Dans l'espace de travail Fabric, créer un nouveau **Dataflow Gen2**
2. Cliquer sur **Obtenir des données** et choisir la source
3. Appliquer les transformations dans l'éditeur Power Query :
   - **Nettoyer les données** : supprimer les colonnes inutiles, gérer les valeurs nulles
   - **Transformer les types** : convertir les textes en dates/nombres
   - **Fusionner des tables** : JOIN entre différentes sources
   - **Pivoter/dépivoter** : restructurer les données
4. Configurer la **destination** : sélectionner le Warehouse et la table cible
5. Publier et planifier l'exécution

### Exemples de transformations Power Query M

```m
// Exemple de transformation Power Query M pour un Dataflow Gen2
let
    // Étape 1 : Connexion à la source CSV
    Source = Csv.Document(
        File.Contents("C:\data\sales.csv"),
        [Delimiter=",", Columns=9, Encoding=65001, QuoteStyle=QuoteStyle.None]
    ),
    
    // Étape 2 : Promouvoir la première ligne comme en-tête
    PromotedHeaders = Table.PromoteHeaders(Source, [PromoteAllScalars=true]),
    
    // Étape 3 : Typer les colonnes
    TypedColumns = Table.TransformColumnTypes(PromotedHeaders, {
        {"OrderDate", type date},
        {"Quantity", Int64.Type},
        {"UnitPrice", type number},
        {"TaxAmount", type number}
    }),
    
    // Étape 4 : Supprimer les lignes avec des valeurs nulles dans les colonnes clés
    FilteredRows = Table.SelectRows(TypedColumns, each
        [CustomerName] <> null and [CustomerName] <> "" and
        [UnitPrice] <> null and [UnitPrice] > 0
    ),
    
    // Étape 5 : Ajouter une colonne calculée
    AddedSalesAmount = Table.AddColumn(FilteredRows, "SalesAmount",
        each [Quantity] * [UnitPrice] * (1 - [Discount]),
        type number
    ),
    
    // Étape 6 : Renommer les colonnes pour correspondre au schéma cible
    RenamedColumns = Table.RenameColumns(AddedSalesAmount, {
        {"CustomerName", "CustomerFullName"},
        {"UnitPrice",    "ListPrice"}
    })
in
    RenamedColumns
```

## 6. Bonnes pratiques pour le chargement de données

### Performance et optimisation

**Chargements en masse (Bulk Load)**
- Préférer `COPY INTO` ou les pipelines avec mode batch pour les grands volumes
- Désactiver temporairement les statistiques automatiques pendant le chargement initial (`ALTER DATABASE SET AUTO_UPDATE_STATISTICS OFF`)
- Utiliser `TRUNCATE TABLE` plutôt que `DELETE FROM` pour vider les tables de staging (plus rapide, non journalisé)

**Gestion des transactions**
```sql
-- Utiliser des transactions explicites pour garantir la cohérence
BEGIN TRANSACTION;
    BEGIN TRY
        -- Charger les dimensions
        EXEC dbo.usp_LoadDimensions;
        
        -- Charger les faits
        EXEC dbo.usp_LoadFacts;
        
        -- Mettre à jour la table de contrôle
        UPDATE dbo.ControlChargement
        SET DernierChargement = GETDATE(), StatutDernier = 'SUCCESS'
        WHERE NomPipeline = 'PipelineSalesDaily';
        
        COMMIT TRANSACTION;
    END TRY
    BEGIN CATCH
        ROLLBACK TRANSACTION;
        
        -- Enregistrer l'erreur
        INSERT INTO dbo.ControlChargement (NomPipeline, DernierChargement, StatutDernier, MessageErreur)
        VALUES ('PipelineSalesDaily', GETDATE(), 'FAILED', ERROR_MESSAGE());
        
        -- Re-propager l'erreur
        THROW;
    END CATCH;
```

**Chargement partitionné par date**
```sql
-- Supprimer uniquement les données du mois en cours (DELETE ciblé)
DELETE FROM dbo.FactSalesOrder
WHERE SalesOrderDateKey IN (
    SELECT DateKey
    FROM dbo.DimDate
    WHERE Year = YEAR(GETDATE()) AND Month = MONTH(GETDATE())
);

-- Re-charger les données du mois
INSERT INTO dbo.FactSalesOrder ...
```

### Gestion de la qualité des données

```sql
-- Rapport de qualité des données de staging avant chargement
SELECT
    'TotalLignes'           AS Metrique, COUNT(*) AS Valeur FROM staging.SalesStage
UNION ALL
SELECT 'LignesDoublons',        COUNT(*) - COUNT(DISTINCT CONCAT(OrderNumber, LineNumber, OrderDate))
    FROM staging.SalesStage
UNION ALL
SELECT 'DateInvalides',         COUNT(*) FROM staging.SalesStage
    WHERE TRY_CAST(OrderDate AS DATE) IS NULL AND OrderDate IS NOT NULL
UNION ALL
SELECT 'PrixNegatifs',          COUNT(*) FROM staging.SalesStage
    WHERE TRY_CAST(UnitPrice AS DECIMAL(10,2)) < 0
UNION ALL
SELECT 'QuantitésNulles',       COUNT(*) FROM staging.SalesStage
    WHERE TRY_CAST(Quantity AS INT) <= 0
UNION ALL
SELECT 'ClientsSansEmail',      COUNT(*) FROM staging.SalesStage
    WHERE CustomerEmail IS NULL OR CustomerEmail = '';
```

## 7. Lab pratique : Charger des données dans un entrepôt

Le lab associé à ce module (06a) couvre le scénario complet de chargement via T-SQL avec requête inter-bases.

**Scénario :** Vous disposez d'un Lakehouse avec une table `staging_sales` contenant des données de ventes CSV. Vous devez créer un Data Warehouse avec le schéma dimensionnel et charger les données via une procédure stockée.

**Étapes clés du lab :**

1. Créer un Lakehouse et uploader le fichier `sales.csv`
2. Charger le CSV comme table `staging_sales` dans le Lakehouse
3. Créer un Warehouse avec les tables `Sales.Fact_Sales`, `Sales.Dim_Customer`, `Sales.Dim_Item`
4. Créer une vue dans le Warehouse pointant vers le Lakehouse :
   ```sql
   CREATE VIEW Sales.Staging_Sales
   AS
   SELECT * FROM [NomDuLakehouse].[dbo].[staging_sales];
   ```
5. Créer et exécuter la procédure `Sales.LoadDataFromStaging`
6. Valider les données avec des requêtes analytiques :
   ```sql
   -- Top clients par chiffre d'affaires 2021
   SELECT c.CustomerName, SUM(s.UnitPrice * s.Quantity) AS TotalVentes
   FROM Sales.Fact_Sales s
   JOIN Sales.Dim_Customer c ON s.CustomerID = c.CustomerID
   WHERE YEAR(s.OrderDate) = 2021
   GROUP BY c.CustomerName
   ORDER BY TotalVentes DESC;
   ```

## Vérification des connaissances

**Question 1.** Quelle est la différence principale entre ETL et ELT dans le contexte d'un Data Warehouse Fabric ?

A) ETL est plus rapide qu'ELT pour les grands volumes de données  
B) Dans ELT, les données sont d'abord chargées dans le DW (ou zone staging), puis transformées avec T-SQL/Spark en tirant parti de la puissance du moteur Fabric  
C) ELT ne nécessite pas de zone de staging  
D) ETL est la seule approche supportée par Microsoft Fabric  

**Réponse correcte : B** — ELT (Extract-Load-Transform) charge d'abord les données brutes, puis les transforme dans le DW grâce à la puissance de calcul du moteur Fabric, ce qui est plus efficace que de transformer les données hors du DW.

**Question 2.** Quelle instruction T-SQL est optimisée pour l'ingestion massive de fichiers Parquet ou CSV depuis Azure Blob Storage vers un Data Warehouse Fabric ?

A) `BULK INSERT`  
B) `INSERT INTO ... SELECT`  
C) `COPY INTO`  
D) `OPENROWSET`  

**Réponse correcte : C** — `COPY INTO` est l'instruction spécialisée pour l'ingestion massive et parallèle de fichiers depuis le stockage externe (Blob Storage, ADLS Gen2, OneLake) dans un Data Warehouse Fabric.

**Question 3.** Dans un pattern de chargement avec table de staging, quelle est la bonne séquence d'opérations ?

A) Charger les faits → Charger les dimensions → Valider le staging  
B) Valider le staging → Charger les faits → Charger les dimensions  
C) Charger les données brutes dans le staging → Valider → Charger les dimensions → Charger les faits  
D) Charger les dimensions et les faits en même temps sans staging  

**Réponse correcte : C** — Le pattern correct est : staging (brut) → validation → dimensions (d'abord car les faits en dépendent) → faits (qui référencent les dimensions).

**Question 4.** Quelle fonctionnalité Fabric permet d'accéder aux données d'un Lakehouse depuis un Warehouse sans copier les données ?

A) Les raccourcis OneLake (Shortcuts)  
B) Les requêtes inter-bases (Cross-database queries) via la syntaxe `[NomLakehouse].[schema].[table]`  
C) Azure Data Factory Copy Activity  
D) Power BI Dataflows  

**Réponse correcte : B** — Les requêtes inter-bases permettent d'utiliser la syntaxe en trois parties `[NomLakehouse].[schema].[table]` pour accéder directement aux tables d'un Lakehouse depuis un Warehouse, sans déplacement de données.

**Question 5.** Quel outil Fabric est le plus adapté pour un analyste non-développeur qui doit transformer des données depuis plusieurs sources et les charger dans un Warehouse ?

A) Un notebook PySpark  
B) Un script T-SQL MERGE manuel  
C) Dataflows Gen2 avec l'interface Power Query

## Résumé

Dans ce module, vous avez découvert les stratégies de chargement de données dans un Data Warehouse Fabric :

- Le pattern **ELT** (Extract-Load-Transform) est privilégié dans Fabric pour tirer parti de la puissance du moteur de calcul natif
- **T-SQL** (INSERT, COPY INTO, MERGE) offre le contrôle maximum pour les transformations complexes et les chargements incrémentiels
- Les **tables de staging** servent de zone tampon pour la validation et la transformation des données brutes avant chargement dans les tables finales
- Les **requêtes inter-bases** permettent d'accéder aux données d'un Lakehouse depuis un Warehouse sans duplication
- Les **pipelines Data Factory** orchestrent et planifient les flux de chargement complexes
- **Dataflows Gen2** (Power Query) démocratise la transformation de données pour les utilisateurs non-développeurs
