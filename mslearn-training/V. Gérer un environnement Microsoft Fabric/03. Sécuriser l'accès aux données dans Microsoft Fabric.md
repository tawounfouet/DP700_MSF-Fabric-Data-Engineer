## 1. Le modèle de sécurité multicouche de Microsoft Fabric

### Pourquoi une sécurité multicouche ?

Microsoft Fabric héberge des données potentiellement sensibles — données financières, données personnelles (PII), données confidentielles de l'entreprise. Un modèle de sécurité robuste ne repose pas sur une seule couche de protection, mais sur plusieurs couches qui se combinent pour garantir que chaque utilisateur accède uniquement aux données auxquelles il a droit.

Le modèle de sécurité Fabric s'articule autour de trois niveaux :

```
Ordre d'évaluation de la sécurité dans Microsoft Fabric

1. Authentification Microsoft Entra ID
   └── L'utilisateur est-il authentifié dans le tenant ?
       └── NON → Accès refusé
       └── OUI →

2. Accès à Microsoft Fabric
   └── L'utilisateur a-t-il une licence Fabric active ?
       └── NON → Accès refusé
       └── OUI →

3. Sécurité des données
   ├── Rôles d'espace de travail (Workspace Roles)
   │   └── L'utilisateur a-t-il un rôle dans le workspace ?
   ├── Permissions d'élément (Item Permissions)
   │   └── L'utilisateur a-t-il des permissions sur cet élément ?
   ├── Sécurité OneLake
   │   └── L'utilisateur a-t-il accès à cette table/dossier OneLake ?
   └── Sécurité de calcul (SQL / Modèle sémantique)
       └── RLS, CLS, OLS définies dans le moteur de calcul
```

Chaque couche est évaluée successivement. Un utilisateur doit satisfaire à **tous les niveaux** pour accéder aux données.

### Hiérarchie complète des permissions

```
Tenant Level (Paramètres tenant)
├── Administrateur Fabric
│   ├── Portail d'administration
│   ├── Paramètres du tenant
│   └── Gestion des capacités
│
Capacity Level (Niveau capacité)
├── Administrateur de capacité
│   ├── Attribution des workspaces à la capacité
│   └── Paramètres de la capacité
│
Workspace Level (Niveau workspace)
├── Admin  → Contrôle total + gestion des permissions
├── Member → Créer, modifier, partager tous les éléments
├── Contributor → Créer et modifier les éléments
└── Viewer → Lire uniquement
│
Item Level (Niveau élément)
├── Owner
├── Read (métadonnées + rapports associés)
├── ReadData (données SQL / modèle sémantique)
└── ReadAll (accès OneLake direct)
│
OneLake Security (Niveau tables/dossiers)
├── Rôles OneLake personnalisés
│   ├── Accès à des tables spécifiques
│   └── Accès à des dossiers spécifiques
│
Compute Security (Moteur de calcul)
├── Point de terminaison SQL
│   ├── Row-Level Security (RLS)
│   ├── Column-Level Security (CLS)
│   └── Object-Level Security (OLS)
└── Modèle sémantique
    ├── RLS via DAX
    └── OLS via DAX
```

## 2. Les rôles d'espace de travail (Workspace Roles)

### Les quatre rôles disponibles

Les rôles d'espace de travail définissent les permissions pour **toutes les ressources** d'un workspace. Ils sont applicables à l'ensemble des éléments Fabric dans ce workspace.

| Rôle | Français | Permissions principales |
|------|----------|------------------------|
| **Admin** | Administrateur | Contrôle total : modifier, partager, gérer les accès, supprimer le workspace |
| **Member** | Membre | Modifier, partager tous les contenus + ajouter des membres |
| **Contributor** | Contributeur | Créer et modifier les éléments, mais ne peut pas gérer les accès |
| **Viewer** | Lecteur | Lire uniquement — ne peut pas créer ou modifier |

**Tableau détaillé des permissions par rôle :**

| Capacité | Admin | Member | Contributor | Viewer |
|----------|-------|--------|-------------|--------|
| Supprimer le workspace | ✅ | ❌ | ❌ | ❌ |
| Ajouter des Admins | ✅ | ❌ | ❌ | ❌ |
| Ajouter des Members | ✅ | ✅ | ❌ | ❌ |
| Écrire des données | ✅ | ✅ | ✅ | ❌ |
| Créer des éléments | ✅ | ✅ | ✅ | ❌ |
| Lire les données | ✅ | ✅ | ✅ | ✅ |
| Partager des éléments | ✅ | ✅ | ❌ | ❌ |
| Gérer les connexions | ✅ | ✅ | ❌ | ❌ |
| Intégration Git | ✅ | ✅ | ✅ | ❌ |

### Assigner des rôles de workspace

**Via l'interface Fabric :**

1. Dans le workspace, cliquez sur **Gérer l'accès** (en haut à droite)
2. Cliquez sur **Ajouter des personnes ou des groupes**
3. Saisissez l'email de l'utilisateur ou le nom du groupe de sécurité
4. Sélectionnez le rôle : Admin, Member, Contributor ou Viewer
5. Cliquez sur **Ajouter**

**Bonne pratique : utiliser des groupes de sécurité**

Plutôt que d'assigner des rôles à des individus, utilisez des **groupes de sécurité Microsoft Entra ID** :

```
Groupe Entra ID : FabricDataEngineers
└── Membres : alice@company.com, bob@company.com
└── Rôle dans workspace : Contributor

Groupe Entra ID : FabricDataViewers
└── Membres : carol@company.com, reportingteam@company.com
└── Rôle dans workspace : Viewer
```

Cela simplifie la gestion : pour donner accès à un nouvel ingénieur, ajoutez-le simplement au groupe Entra ID.

### Comportement du rôle Viewer sur les éléments Fabric

Le rôle **Viewer** accorde un accès en lecture à tous les éléments du workspace. Selon le type d'élément, cela implique :

**Sur un Data Warehouse :**
- Permission `CONNECT` sur le warehouse
- Permission `ReadData` sur toutes les tables (via le point de terminaison SQL)

**Sur un Lakehouse :**
- Accès aux données via le **point de terminaison SQL Analytics** (interface SQL)
- **Pas** d'accès direct aux fichiers OneLake (nécessite des permissions OneLake supplémentaires)

**Sur un Rapport Power BI :**
- Lecture du rapport et des visuels
- Pas d'accès aux données brutes sous-jacentes

## 3. Les permissions au niveau des éléments (Item Permissions)

### Quand utiliser les permissions d'élément ?

Les permissions d'élément permettent de partager **un élément spécifique** avec un utilisateur sans lui donner accès à l'ensemble du workspace. C'est utile pour :

- Partager un rapport avec un utilisateur externe sans lui montrer tous les éléments du workspace
- Donner accès à un seul lakehouse pour des partenaires
- Accorder un accès en lecture seule à un entrepôt de données pour un analyste externe

**Relation entre permissions workspace et permissions d'élément :**

```
Scénario : Alice a le rôle Viewer dans le workspace
          Alice a aussi une permission d'élément "Read" sur le rapport X

Résultat : Alice peut voir le rapport X
           (via son rôle Viewer ET via la permission d'élément)

Scénario : Bob n'a aucun rôle dans le workspace
          Bob a une permission d'élément "Read" sur le rapport X

Résultat : Bob peut voir le rapport X via un lien partagé
           mais ne voit pas les autres éléments du workspace
```

> **Important :** Si un utilisateur a un rôle Viewer dans le workspace ET une permission d'élément, supprimer la permission d'élément ne suffira pas à lui retirer l'accès au rapport — il peut toujours y accéder via son rôle Viewer. Il faut aussi retirer le rôle Viewer.

### Types de permissions d'élément

Selon le type d'élément, différentes permissions peuvent être accordées :

**Pour un Lakehouse :**

| Permission | Description |
|------------|-------------|
| **Read** | Accès aux métadonnées du lakehouse, pas aux données |
| **ReadData** | Accès aux données via le point de terminaison SQL (toutes les tables) |
| **ReadAll** | Accès direct à OneLake (toutes les tables et tous les dossiers) |

**Pour un Data Warehouse :**

| Permission | Description |
|------------|-------------|
| **Read** | Accès en lecture via SQL (point de terminaison) |
| **ReadData** | Lecture de toutes les tables |
| **Write** | Écriture dans les tables |

**Pour un Modèle sémantique (Semantic Model) :**

| Permission | Description |
|------------|-------------|
| **Read** | Lire les rapports basés sur ce modèle |
| **Build** | Créer de nouveaux rapports à partir de ce modèle |
| **Write** | Modifier le modèle |
| **Reshare** | Partager le modèle avec d'autres |

### Configurer les permissions d'un élément

1. Dans le workspace, survolez l'élément (ex : un lakehouse)
2. Cliquez sur **...** → **Gérer les permissions**
3. Cliquez sur **Ajouter un utilisateur**
4. Saisissez l'email de l'utilisateur
5. Cochez les permissions souhaitées (**Read**, **ReadData**, **ReadAll**)
6. Cliquez sur **Accorder**

## 4. La sécurité OneLake

### Qu'est-ce que la sécurité OneLake ?

**OneLake** est le lac de données unifié de Microsoft Fabric, basé sur Azure Data Lake Storage Gen2. Tous les éléments Fabric (lakehouses, warehouses, Eventhouses) stockent leurs données dans OneLake.

La **sécurité OneLake** permet de créer des rôles de sécurité personnalisés au sein d'un lakehouse et d'accorder des permissions granulaires à des **tables spécifiques** et des **dossiers spécifiques**. C'est le niveau de contrôle le plus fin disponible dans Fabric.

### Fonctionnement de la sécurité OneLake

**Sans sécurité OneLake :**

```
Lakehouse: SalesLakehouse
├── Tables/
│   ├── customers       ← accessible à tous les users avec ReadAll
│   ├── orders          ← accessible à tous les users avec ReadAll
│   ├── employees       ← accessible à tous les users avec ReadAll (données sensibles !)
│   └── salaries        ← accessible à tous les users avec ReadAll (données très sensibles !)
└── Files/
    └── raw/            ← accessible à tous les users avec ReadAll
```

**Avec la sécurité OneLake :**

```
Lakehouse: SalesLakehouse
Rôle OneLake: "AnalystRole"
  └── Tables autorisées: customers, orders
  └── Membres: analysts-group@company.com

Rôle OneLake: "HRRole"
  └── Tables autorisées: employees, salaries
  └── Membres: hr-team@company.com

Résultat:
- Les analystes voient SEULEMENT customers et orders
- L'équipe RH voit SEULEMENT employees et salaries
```

### Créer un rôle de sécurité OneLake

1. Dans le lakehouse, cliquez sur **Gérer la sécurité OneLake**
2. Sur l'écran OneLake Security, cliquez sur **+ Nouveau**
3. Nommez le rôle (ex : `analysts_role`)
4. Sous **Accorder des permissions** :
   - Si la case est décochée : le rôle ne donne pas accès par défaut à tout (recommandé pour des rôles restrictifs)
   - Si la case est cochée : le rôle donne accès à toutes les données (pour des rôles larges)
5. Cliquez sur **Suivant**

**Sélectionner les données accessibles :**

6. Sous **Ajouter des données à votre rôle**, sélectionnez **Données sélectionnées**
7. Dans le navigateur de données, développez **Tables** et **dbo**
8. Cochez les tables auxquelles ce rôle doit avoir accès (ex : `customers`, `orders`)
9. Cliquez sur **Ajouter les données**, puis **Suivant**

**Ajouter des membres au rôle :**

10. Saisissez les emails des utilisateurs ou groupes à ajouter au rôle
11. Cochez leur checkbox et cliquez sur **Créer**

### Schéma de la sécurité OneLake par couches

```
Accès à un lakehouse : exemple de Alice

Couche 1: Alice a la permission "Read" sur le lakehouse
  → Alice voit les métadonnées (nom des tables)
  → Alice ne voit PAS les données

Couche 2: Alice est membre du rôle OneLake "analysts_role"
  → analysts_role donne accès aux tables: customers, orders
  → Alice peut maintenant lire les données de customers et orders
  → Alice ne peut PAS lire employees ou salaries

Couche 3: Sécurité SQL (optionnelle)
  → Une RLS est définie sur customers pour filtrer par region
  → Alice voit uniquement les clients de sa région
```

### Contraintes importantes de la sécurité OneLake

- La sécurité OneLake s'applique uniquement lors d'un **accès direct à OneLake** (API OneLake, Azure Storage Explorer, accès programmatique)
- Elle s'applique également lors d'un accès via le **point de terminaison SQL Analytics** du lakehouse
- Elle ne remplace **pas** les permissions au niveau du workspace ou de l'élément
- Pour qu'un utilisateur puisse accéder à OneLake, il doit d'abord avoir au minimum la permission **Read** sur le lakehouse (niveau élément)

## 5. Microsoft Purview et la gouvernance des données

### Le rôle de Microsoft Purview avec Fabric

**Microsoft Purview** est la plateforme de gouvernance de données de Microsoft. Son intégration avec Microsoft Fabric permet de :

- Appliquer des **étiquettes de confidentialité** (Sensitivity Labels) aux éléments Fabric
- Découvrir et cataloguer les données sensibles à travers tout le tenant Fabric
- Appliquer des **politiques de protection des données** automatiquement
- Auditer les accès aux données sensibles

### Étiquettes de confidentialité (Sensitivity Labels)

Les étiquettes de confidentialité permettent de classer les données selon leur niveau de sensibilité. Elles héritent les protections définies dans Microsoft Purview.

**Niveaux d'étiquettes typiques :**

```
Public          → Données accessibles au grand public
Interne         → Données pour les employés de l'entreprise
Confidentiel    → Données sensibles, accès restreint
Hautement Confidentiel → Données très sensibles (données financières, PII)
Secret          → Données critiques (utilisé dans certaines industries réglementées)
```

**Comment les étiquettes protègent les données :**

Une étiquette "Confidentiel" peut inclure des actions automatiques :
- Chiffrement des fichiers exportés
- Restriction du partage externe
- Filigrane sur les rapports Power BI exportés
- Journalisation de tous les accès dans Microsoft Purview

### Appliquer une étiquette de confidentialité dans Fabric

1. Dans le workspace, survolez un élément (ex : un rapport ou un lakehouse)
2. Cliquez sur **...** → **Paramètres**
3. Dans le panneau de paramètres, trouvez **Étiquette de confidentialité**
4. Sélectionnez l'étiquette appropriée dans la liste déroulante
5. Sauvegardez

> **Note :** Pour que les étiquettes de confidentialité soient disponibles, l'administrateur Fabric doit activer l'intégration Microsoft Purview dans les paramètres du tenant.

### Héritage des étiquettes

Les étiquettes de confidentialité se propagent automatiquement dans certains scénarios :

```
Lakehouse étiqueté "Confidentiel"
  └── Rapport Power BI créé depuis ce lakehouse
      → hérite automatiquement de "Confidentiel"
      
Fichier Excel exporté depuis un rapport "Confidentiel"
  → hérite de "Confidentiel" + chiffrement appliqué
```

### Intégration Purview pour la découverte des données

Microsoft Purview peut scanner les lakehouses et warehouses Fabric pour :
- Identifier automatiquement les colonnes contenant des **données personnelles** (noms, emails, numéros de carte bancaire)
- Classer automatiquement les données selon des schémas prédéfinis
- Générer une carte des données (Data Map) montrant où se trouvent les données sensibles

## 6. Scénarios pratiques de configuration de la sécurité

### Scénario 1 : Équipe de ventes avec accès par région

**Contexte :** Une entreprise a des analystes de ventes qui ne doivent voir que les données de leur région.

**Solution recommandée :**

```
Structure:
- Workspace: "Sales Analytics"
- Lakehouse: "SalesLakehouse"
  └── Table: sales_orders (toutes les régions)

Configuration:
1. Rôle workspace "Viewer" pour tous les analystes
   → Ils voient le lakehouse mais pas les données

2. Permission lakehouse "ReadData" pour tous les analystes
   → Ils peuvent requêter via SQL

3. RLS sur le point de terminaison SQL:
   CREATE SECURITY POLICY RegionFilter
   ADD FILTER PREDICATE dbo.fn_region_filter(region_code)
   ON dbo.sales_orders;
   → Chaque analyste voit uniquement sa région
```

### Scénario 2 : Partenaire externe avec accès limité

**Contexte :** Un partenaire externe doit accéder à un rapport spécifique mais pas au workspace.

**Solution recommandée :**

```
1. Inviter le partenaire comme utilisateur invité dans Microsoft Entra ID
   (via Azure AD B2B)

2. Partager uniquement le rapport avec le partenaire:
   Rapport → Gérer les permissions → Ajouter l'utilisateur invité → Read

3. Si le rapport utilise DirectLake:
   Lakehouse → Gérer les permissions → Ajouter l'utilisateur → Read seulement
   + Créer un rôle OneLake avec accès aux tables nécessaires uniquement

Résultat:
- Le partenaire voit le rapport
- Le partenaire ne voit pas le workspace ni les autres éléments
- Le partenaire ne peut pas accéder directement au lakehouse
```

### Scénario 3 : Développeur avec accès en développement uniquement

**Contexte :** Un développeur junior travaille sur le lakehouse de DEV mais ne doit pas avoir accès à la PROD.

**Solution recommandée :**

```
Workspace DEV: "Analytics - DEV"
  └── Rôle: Contributor pour le développeur junior

Workspace PROD: "Analytics - PROD"
  └── Rôle: Viewer pour le développeur junior (ou aucun rôle)

Pipeline de déploiement:
  └── Seuls les Admins/Members peuvent déclencher le déploiement vers PROD
```

## 7. Exercice pratique — Sécuriser l'accès aux données

### Objectif

Configurer une sécurité multicouche : rôles workspace, permissions d'élément et rôles OneLake pour contrôler l'accès à un lakehouse.

### Prérequis pour cet exercice

Vous avez besoin de deux comptes utilisateur :
- **Utilisateur 1** : Admin du workspace (votre compte principal)
- **Utilisateur 2** : Un compte de test avec des permissions limitées

### Étapes

**Partie 1 : Créer le workspace et les éléments**

1. Connectez-vous à Fabric avec votre compte Admin
2. Créez un workspace avec une capacité Fabric
3. Créez un **Data Warehouse** (exemple de données)
4. Créez un **Lakehouse** et chargez les données d'exemple (vacances publiques)

**Partie 2 : Tester sans permissions**

1. Dans une fenêtre privée (InPrivate), connectez-vous avec l'Utilisateur 2
2. Vérifiez que l'Utilisateur 2 ne voit pas le workspace dans sa liste

**Partie 3 : Appliquer le rôle Viewer**

1. Dans le workspace (Utilisateur 1), cliquez sur **Gérer l'accès**
2. Ajoutez l'Utilisateur 2 avec le rôle **Viewer**
3. Dans la fenêtre privée, rafraîchissez et vérifiez que l'Utilisateur 2 voit maintenant tous les éléments du workspace
4. Vérifiez que l'Utilisateur 2 peut lire les données du warehouse (table Date)
5. Vérifiez que l'Utilisateur 2 peut lire les données du lakehouse via SQL Analytics

**Partie 4 : Appliquer des permissions d'élément (restreindre l'accès au lakehouse)**

1. (Utilisateur 1) Retirez le rôle Viewer de l'Utilisateur 2
2. Sur le warehouse : **Gérer les permissions** → Ajouter l'Utilisateur 2 avec **ReadData** uniquement
3. Dans la fenêtre privée, l'Utilisateur 2 ne voit plus le workspace directement
4. L'Utilisateur 2 trouve le warehouse via le **Catalogue OneLake** (filtre : Data items)
5. L'Utilisateur 2 peut lire les données du warehouse mais ne voit pas le lakehouse

**Partie 5 : Appliquer la sécurité OneLake**

1. (Utilisateur 1) Sur le lakehouse : **Gérer les permissions** → Ajouter l'Utilisateur 2 avec **Read** seulement (aucune checkbox cochée)
2. L'Utilisateur 2 voit le lakehouse dans le catalogue OneLake mais ne peut pas lire les données
3. (Utilisateur 1) Dans le lakehouse : **Gérer la sécurité OneLake** → Créer un rôle **publicholidays**
4. Ajouter la table `publicholidays` au rôle
5. Ajouter l'Utilisateur 2 comme membre du rôle
6. Dans la fenêtre privée, l'Utilisateur 2 peut maintenant lire la table publicholidays uniquement

**Nettoyage :** Supprimez le workspace.

## 8. Vérification des connaissances

**Question 1 :** Un utilisateur a le rôle **Contributor** dans un workspace Fabric. Quelle action peut-il effectuer ?

A) Supprimer le workspace
B) Ajouter d'autres utilisateurs comme Admins
C) Créer et modifier des éléments dans le workspace
D) Partager des éléments avec des utilisateurs externes

**Réponse correcte : C**
*Le rôle Contributor permet de créer et modifier des éléments, mais pas de gérer les accès, supprimer le workspace, ou partager des éléments. Ces actions sont réservées aux rôles Member et Admin.*

---

**Question 2 :** Un utilisateur a le rôle **Viewer** dans un workspace et a aussi une permission d'élément **Read** sur un rapport. L'administrateur retire la permission d'élément. L'utilisateur peut-il toujours voir le rapport ?

A) Non, car la permission d'élément a été retirée
B) Oui, car le rôle Viewer du workspace lui donne toujours accès
C) Non, car le rôle Viewer ne donne pas accès aux rapports
D) Oui, mais uniquement si le rapport est partagé publiquement

**Réponse correcte : B**
*Le rôle Viewer du workspace donne accès en lecture à tous les éléments du workspace. Retirer la permission d'élément ne suffit pas — il faut aussi retirer le rôle Viewer du workspace pour bloquer l'accès au rapport.*

---

**Question 3 :** Vous avez un lakehouse avec 10 tables. Vous souhaitez qu'un groupe d'analystes puisse accéder uniquement à 3 tables spécifiques, sans voir les 7 autres. Quelle fonctionnalité Fabric utilisez-vous ?

A) Les rôles d'espace de travail (Workspace Roles)
B) Les permissions d'élément avec ReadData
C) Les rôles de sécurité OneLake
D) Le chiffrement Microsoft Purview

**Réponse correcte : C**
*Les rôles de sécurité OneLake permettent de créer des rôles personnalisés avec accès à des tables et dossiers spécifiques dans un lakehouse. C'est le niveau de granularité le plus fin pour contrôler l'accès aux données dans OneLake.*

---

**Question 4 :** Vous partagez un rapport Power BI qui utilise le mode **DirectLake** avec un utilisateur externe. L'utilisateur peut voir le rapport mais pas les données. Que faut-il ajouter ?

A) Donner le rôle Viewer dans le workspace
B) Accorder la permission ReadAll sur le lakehouse
C) Ajouter l'utilisateur à un rôle OneLake qui donne accès aux tables nécessaires
D) Changer le mode du rapport de DirectLake à Import

**Réponse correcte : C**
*Avec DirectLake, le rapport lit les données directement depuis OneLake. L'utilisateur doit avoir des permissions OneLake sur les tables utilisées par le rapport. La solution recommandée est de créer un rôle OneLake et d'y ajouter l'utilisateur, sans pour autant lui donner un accès complet au lakehouse.*

---

**Question 5 :** Quelle est la bonne pratique pour gérer les accès d'une équipe de 50 ingénieurs data dans Microsoft Fabric ?

A) Assigner le rôle Contributor à chaque ingénieur individuellement dans chaque workspace
B) Créer un groupe de sécurité Microsoft Entra ID et assigner le rôle au groupe
C) Créer un compte partagé pour tous les ingénieurs
D) Utiliser uniquement les permissions d'élément pour chaque notebook

**Réponse correcte : B**
*Les groupes de sécurité Entra ID permettent de gérer les accès de manière centralisée. Pour donner ou retirer l'accès à un ingénieur, il suffit de l'ajouter ou le retirer du groupe, sans modifier les permissions de chaque workspace individuellement.*

## Résumé

Dans ce module, vous avez découvert le modèle de sécurité multicouche de Microsoft Fabric :

- **L'ordre d'évaluation** : Authentification Entra ID → Accès Fabric → Sécurité des données (workspace, élément, OneLake, calcul)
- **Les rôles d'espace de travail** (Admin, Member, Contributor, Viewer) définissent des permissions pour tous les éléments d'un workspace. L'utilisation de groupes de sécurité Entra ID est la bonne pratique.
- **Les permissions d'élément** permettent de partager un élément spécifique avec un utilisateur sans lui donner accès au workspace entier. Les types de permissions varient selon l'élément (Read, ReadData, ReadAll).
- **La sécurité OneLake** permet de créer des rôles personnalisés avec accès à des tables et dossiers spécifiques dans un lakehouse — le niveau de granularité le plus fin.
- **Microsoft Purview** s'intègre à Fabric pour appliquer des étiquettes de confidentialité, découvrir les données sensibles et gouverner les accès à l'échelle du tenant.
- Les permissions sont **cumulatives et additives** : un utilisateur bénéficie de toutes les permissions accordées, que ce soit via le rôle workspace ou les permissions d'élément.
