## 1. Introduction au CI/CD dans Microsoft Fabric

### Qu'est-ce que le CI/CD dans le contexte des données ?

L'intégration continue (CI) et la livraison continue (CD) sont des pratiques DevOps qui permettent aux équipes de développement de livrer des changements fréquemment, de manière fiable et automatisée. Dans le contexte de la data engineering, le CI/CD garantit que :

- Les pipelines de données, notebooks, et lakehouses sont versionnés comme du code applicatif
- Les modifications sont testées avant d'atteindre la production
- Les environnements DEV, TEST et PROD restent synchronisés et cohérents
- Les rollbacks sont possibles en cas de régression

Microsoft Fabric intègre nativement deux outils complémentaires pour le CI/CD :

1. **L'intégration Git** : connecte un workspace Fabric à un référentiel Git (Azure DevOps ou GitHub) pour le contrôle de version
2. **Les pipelines de déploiement** : permettent de promouvoir du contenu entre des étapes (DEV → TEST → PROD)

Ces deux outils peuvent être utilisés indépendamment ou ensemble pour une stratégie CI/CD complète.

### Pourquoi le CI/CD est-il critique pour la data engineering ?

Sans CI/CD, les équipes data font face à plusieurs problèmes récurrents :

- Des modifications manuelles effectuées directement en production qui cassent des pipelines critiques
- L'impossibilité de retrouver qui a modifié quoi et quand dans un notebook ou un dataflow
- Des environnements de développement qui divergent progressivement de la production
- Des déploiements risqués car non testés, effectués le week-end ou la nuit

Avec une stratégie CI/CD bien conçue dans Fabric, les équipes bénéficient d'une traçabilité complète, de déploiements répétables et d'un processus de validation rigoureux avant chaque mise en production.

## 2. Intégration Git dans Microsoft Fabric

### Présentation de l'intégration Git

L'intégration Git dans Microsoft Fabric permet aux développeurs de connecter un workspace à un référentiel Git. Une fois la connexion établie, les éléments Fabric supportés (notebooks, lakehouses, pipelines de données, dataflows Gen2, etc.) peuvent être validés (commit) dans Git et synchronisés depuis Git vers le workspace.

L'intégration se fait au niveau du workspace. Chaque workspace peut être connecté à une seule branche d'un seul référentiel Git.

**Fournisseurs Git supportés :**
- Azure DevOps (cloud uniquement)
- GitHub (cloud uniquement)
- GitHub Enterprise (cloud uniquement)

> **Note :** Les versions on-premises d'Azure DevOps Server ou GitHub Enterprise Server ne sont pas supportées.

### Éléments Fabric supportés par Git

L'intégration Git supporte un large éventail d'éléments Fabric :

**Ingénierie des données :**
- Lakehouse
- Notebooks
- Définitions de travaux Spark (Spark Job Definitions)
- Dataflows Gen2
- Pipelines de données
- Environnements Fabric

**Science des données :**
- Expériences Machine Learning (préversion)
- Modèles Machine Learning (préversion)

**Intelligence en temps réel :**
- Eventhouse
- EventStream
- Base de données KQL
- Ensemble de requêtes KQL
- Tableau de bord en temps réel

**Power BI :**
- Rapports (préversion)
- Modèles sémantiques (préversion)

**Data Warehouse :**
- Entrepôt de données (préversion)

Les éléments non supportés sont ignorés lors de la synchronisation — ils ne sont ni sauvegardés dans Git ni supprimés du workspace.

### Configurer l'intégration Git avec Azure DevOps

**Étape 1 : Préparer Azure DevOps**

Avant de connecter le workspace, créez un référentiel dédié dans Azure DevOps :

```
Organisation Azure DevOps : monorganisation
Projet : FabricDataPlatform
Référentiel : fabric-analytics
Branche principale : main
```

**Étape 2 : Connecter le workspace à Git**

1. Dans le workspace Fabric, accédez aux **Paramètres du workspace**
2. Sélectionnez l'onglet **Intégration Git**
3. Cliquez sur **Connecter Git**
4. Choisissez **Azure DevOps** comme fournisseur
5. Sélectionnez l'organisation, le projet et le référentiel
6. Définissez la branche cible (ex : `dev`)
7. Définissez le répertoire Git (ex : `/workspaces/sales-analytics-dev`)
8. Cliquez sur **Connecter et synchroniser**

**Étape 3 : Premier commit**

Après la connexion, les éléments du workspace apparaissent avec le statut "Non commité". Effectuez un commit initial :

1. Dans le panel Git, cochez les éléments à versionner
2. Ajoutez un message de commit descriptif : `Initial commit - Sales Analytics workspace`
3. Cliquez sur **Commit**

### Structure des fichiers dans Git

Lorsque des éléments Fabric sont validés dans Git, ils sont représentés par des fichiers et dossiers dans une structure spécifique. Voici un exemple de structure pour un workspace contenant un lakehouse et un notebook :

```
fabric-analytics/
└── workspaces/
    └── sales-analytics-dev/
        ├── .platform/
        │   └── config.json
        ├── SalesLakehouse.Lakehouse/
        │   ├── .platform/
        │   │   └── item.metadata.json
        │   └── lakehouse.metadata.json
        ├── Transform_Sales.Notebook/
        │   ├── .platform/
        │   │   └── item.metadata.json
        │   └── notebook-content.ipynb
        └── Sales_Pipeline.DataPipeline/
            ├── .platform/
            │   └── item.metadata.json
            └── pipeline-content.json
```

Le fichier `item.metadata.json` contient les métadonnées de l'élément :

```json
{
  "type": "Notebook",
  "displayName": "Transform_Sales",
  "description": "Transformations des données de ventes",
  "logicalId": "a1b2c3d4-e5f6-7890-abcd-ef1234567890"
}
```

Le fichier `config.json` au niveau du workspace contient la configuration Git :

```json
{
  "version": "1.0",
  "logicalId": "workspace-logical-id-xxxxxxxx"
}
```

### Synchronisation depuis Git vers le workspace

Lorsque d'autres membres de l'équipe poussent des modifications dans le référentiel Git, vous devez synchroniser (update) votre workspace :

1. Dans le panel Git du workspace, cliquez sur **Mettre à jour depuis Git**
2. Fabric compare les versions locales (workspace) et distantes (Git)
3. Les conflits éventuels sont signalés et doivent être résolus manuellement
4. Confirmez la mise à jour

### Stratégies de branchement pour les équipes data

Une bonne stratégie de branchement est essentielle pour coordonner le travail d'une équipe data. Voici deux approches courantes :

**Approche 1 : Feature Branching (recommandée)**

```
main (production)
  └── develop (intégration)
        ├── feature/ajout-pipeline-ventes    ← développeur A
        ├── feature/refactoring-notebook     ← développeur B
        └── fix/correction-null-values       ← développeur C
```

Chaque développeur travaille sur sa propre branche, connectée à son propre workspace. Après validation (Pull Request), les modifications sont fusionnées dans `develop` puis dans `main`.

**Approche 2 : Environment Branching**

```
main (production)
  └── test (validation)
        └── dev (développement)
```

Chaque branche correspond à un environnement. Les promotions se font par Pull Request entre branches.

**Correspondance branches / workspaces recommandée :**

| Branche Git | Workspace Fabric | Environnement |
|-------------|------------------|---------------|
| `dev`       | Sales Analytics DEV | Développement |
| `test`      | Sales Analytics TEST | Tests / Validation |
| `main`      | Sales Analytics PROD | Production |

## 3. Pipelines de déploiement Fabric

### Qu'est-ce qu'un pipeline de déploiement ?

Un pipeline de déploiement (Deployment Pipeline) est un outil de Microsoft Fabric qui permet de déployer du contenu d'un workspace vers un autre, en suivant un flux de promotion défini. Contrairement à l'intégration Git qui gère le contrôle de version, les pipelines de déploiement gèrent la **promotion d'environnement**.

Un pipeline de déploiement comprend entre 2 et 10 étapes. Les trois étapes par défaut sont :

- **Développement (DEV)** : espace de création et développement actif
- **Test** : espace de validation par les testeurs et utilisateurs métier
- **Production (PROD)** : espace de publication pour les utilisateurs finaux

### Créer un pipeline de déploiement

**Via l'interface Fabric :**

1. Dans la barre de navigation gauche, cliquez sur **Déploiements** (icône de pipeline)
2. Sélectionnez **Nouveau pipeline**
3. Donnez un nom au pipeline : `Sales Analytics Pipeline`
4. Confirmez la création

**Assigner des workspaces aux étapes :**

1. Pour chaque étape (DEV, Test, Production), cliquez sur **Assigner un workspace**
2. Sélectionnez le workspace correspondant
3. Cliquez sur **Assigner**

### Déployer du contenu entre étapes

Une fois les workspaces assignés, vous pouvez déployer du contenu :

1. Sélectionnez l'étape **Test** dans le canvas du pipeline
2. Sous le canvas, cochez les éléments à déployer (ex : `LabLakehouse`)
3. Cliquez sur **Déployer**
4. Dans la fenêtre de confirmation, examinez les changements et cliquez sur **Déployer**

Le statut de synchronisation est affiché entre les étapes :
- Coche verte : les étapes sont synchronisées
- Croix rouge : des éléments diffèrent entre les étapes

### Comparer le contenu entre étapes

Avant un déploiement, Fabric permet de visualiser les différences entre deux étapes adjacentes :

1. Sélectionnez une étape dans le pipeline
2. Cliquez sur **Comparer** entre deux étapes
3. Fabric affiche :
   - Les éléments identiques (synchronisés)
   - Les éléments modifiés (mis à jour dans la source)
   - Les éléments uniquement présents dans la source (nouveaux)
   - Les éléments uniquement présents dans la cible (supprimés dans la source)

### Règles de déploiement

Les règles de déploiement permettent d'adapter la configuration des éléments selon l'environnement cible. Par exemple, un rapport peut pointer vers une source de données différente entre DEV et PROD.

**Types de règles disponibles :**
- **Règle de connexion** : modifier la source de données d'un dataflow ou d'un pipeline
- **Règle de paramètre** : modifier les paramètres d'un modèle sémantique

**Configurer une règle de déploiement :**

1. Dans le pipeline, sélectionnez une étape cible (ex : Production)
2. Cliquez sur **Règles de déploiement**
3. Sélectionnez l'élément à configurer (ex : un Dataflow Gen2)
4. Définissez la règle :

```
Élément : Ingest_Sales_Data (Dataflow Gen2)
Règle : Connexion à la source
Valeur en DEV : Serveur SQL de développement (dev-sql.database.windows.net)
Valeur en PROD : Serveur SQL de production (prod-sql.database.windows.net)
```

Ainsi, lors du déploiement vers PROD, le dataflow se connectera automatiquement au serveur de production sans modification manuelle.

### Appairage des éléments

L'appairage (pairing) est le mécanisme par lequel Fabric associe un élément d'une étape à son équivalent dans l'étape adjacente. L'appairage est crucial pour comprendre le comportement lors d'un déploiement :

- **Éléments appairés** : lors du déploiement, l'élément source **remplace** l'élément cible
- **Éléments non appairés** : lors du déploiement, une **copie** est créée dans la cible

L'appairage se produit automatiquement lors de :
- L'assignation initiale d'un workspace à une étape (si les éléments portent le même nom)
- Le premier déploiement d'un élément d'une étape vers une autre

> **Important :** Si vous renommez un élément dans une étape, l'appairage est conservé. Deux éléments appairés peuvent donc avoir des noms différents entre DEV et PROD.

## 4. Automatisation via les API REST

Microsoft Fabric expose des API REST pour automatiser les opérations de déploiement. Cela permet d'intégrer Fabric dans des pipelines CI/CD existants (Azure Pipelines, GitHub Actions).

### Déploiement via l'API REST

**Authentification avec un Service Principal :**

```powershell
# Obtenir un token d'accès via Azure AD
$tenantId = "votre-tenant-id"
$clientId = "votre-client-id"
$clientSecret = "votre-client-secret"

$body = @{
    grant_type    = "client_credentials"
    client_id     = $clientId
    client_secret = $clientSecret
    scope         = "https://api.fabric.microsoft.com/.default"
}

$tokenResponse = Invoke-RestMethod `
    -Uri "https://login.microsoftonline.com/$tenantId/oauth2/v2.0/token" `
    -Method Post `
    -Body $body

$accessToken = $tokenResponse.access_token
```

**Déclencher un déploiement entre étapes :**

```powershell
$pipelineId = "votre-pipeline-id"
$sourceStageOrder = 0  # DEV = étape 0
$targetStageOrder = 1  # TEST = étape 1

$deploymentBody = @{
    sourceStageOrder = $sourceStageOrder
    isBackwardDeployment = $false
    newWorkspace = $null
    updateAppSettings = $false
    allowOverwriteTargetArtifact = $true
    note = "Déploiement automatique depuis Azure Pipeline"
} | ConvertTo-Json

$headers = @{
    Authorization = "Bearer $accessToken"
    "Content-Type" = "application/json"
}

$result = Invoke-RestMethod `
    -Uri "https://api.fabric.microsoft.com/v1/pipelines/$pipelineId/deploy" `
    -Method Post `
    -Headers $headers `
    -Body $deploymentBody

Write-Output "Déploiement démarré. ID opération : $($result.operationId)"
```

**Vérifier le statut d'un déploiement :**

```powershell
$operationId = $result.operationId

do {
    Start-Sleep -Seconds 10
    $status = Invoke-RestMethod `
        -Uri "https://api.fabric.microsoft.com/v1/operations/$operationId" `
        -Method Get `
        -Headers $headers

    Write-Output "Statut : $($status.status)"
} while ($status.status -eq "Running")

if ($status.status -eq "Succeeded") {
    Write-Output "Déploiement réussi !"
} else {
    Write-Output "Déploiement échoué : $($status.error.message)"
    exit 1
}
```

### Intégration dans GitHub Actions

```yaml
# .github/workflows/deploy-fabric.yml
name: Deploy to Microsoft Fabric

on:
  push:
    branches:
      - main

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v3

      - name: Deploy to Fabric TEST
        env:
          FABRIC_TENANT_ID: ${{ secrets.FABRIC_TENANT_ID }}
          FABRIC_CLIENT_ID: ${{ secrets.FABRIC_CLIENT_ID }}
          FABRIC_CLIENT_SECRET: ${{ secrets.FABRIC_CLIENT_SECRET }}
          FABRIC_PIPELINE_ID: ${{ secrets.FABRIC_PIPELINE_ID }}
        run: |
          # Obtenir le token
          TOKEN=$(curl -s -X POST \
            "https://login.microsoftonline.com/$FABRIC_TENANT_ID/oauth2/v2.0/token" \
            -d "grant_type=client_credentials&client_id=$FABRIC_CLIENT_ID&client_secret=$FABRIC_CLIENT_SECRET&scope=https://api.fabric.microsoft.com/.default" \
            | jq -r '.access_token')

          # Déclencher le déploiement DEV -> TEST
          curl -s -X POST \
            "https://api.fabric.microsoft.com/v1/pipelines/$FABRIC_PIPELINE_ID/deploy" \
            -H "Authorization: Bearer $TOKEN" \
            -H "Content-Type: application/json" \
            -d '{"sourceStageOrder": 0, "isBackwardDeployment": false}'
```

## 5. Bonnes pratiques CI/CD pour Microsoft Fabric

### Organisation des workspaces

Adoptez une convention de nommage claire pour vos workspaces :

```
[Domaine] - [Projet] - [Environnement]

Exemples :
- Sales - Analytics - DEV
- Sales - Analytics - TEST
- Sales - Analytics - PROD
- Finance - Reporting - DEV
- Finance - Reporting - PROD
```

### Séparation des préoccupations

Suivez le principe de séparation des préoccupations pour structurer vos workspaces :

```
Workspace de données (Lakehouse/Warehouse)
    ↓ (lecture seule pour les autres workspaces)
Workspace de transformation (Notebooks, Pipelines)
    ↓
Workspace de reporting (Modèles sémantiques, Rapports)
```

### Checklist avant déploiement en production

Avant tout déploiement en production, vérifiez :

- [ ] Les tests unitaires des notebooks ont réussi
- [ ] Le pipeline de données s'est exécuté avec succès en TEST avec des données réelles
- [ ] Les règles de déploiement sont correctement configurées pour la PROD
- [ ] Un backup de la PROD a été effectué (si applicable)
- [ ] L'approbation du responsable technique a été obtenue
- [ ] La fenêtre de maintenance est planifiée et communiquée
- [ ] Un plan de rollback est défini

### Gestion des secrets et des connexions

Ne stockez **jamais** de mots de passe, chaînes de connexion ou clés API directement dans les notebooks ou les pipelines. Utilisez :

- **Azure Key Vault** : pour stocker les secrets, accessibles via `mssparkutils.credentials`
- **Connexions Fabric** : pour les sources de données, gérez les connexions séparément des pipelines
- **Variables d'environnement** : pour les paramètres qui varient entre environnements

```python
# Bonne pratique : lire un secret depuis Azure Key Vault dans un notebook Fabric
from notebookutils import mssparkutils

# Lire le mot de passe depuis Key Vault
db_password = mssparkutils.credentials.getSecret(
    "https://mon-keyvault.vault.azure.net/",
    "database-password"
)

# Utiliser le secret pour la connexion
jdbc_url = f"jdbc:sqlserver://prod-server.database.windows.net:1433;databaseName=SalesDB"
connection_properties = {
    "user": "fabric-service-account",
    "password": db_password,
    "driver": "com.microsoft.sqlserver.jdbc.SQLServerDriver"
}
```

## 6. Exercice pratique — Créer un pipeline de déploiement

### Objectif

Créer un pipeline de déploiement avec trois environnements (DEV, TEST, PROD), y déployer un lakehouse et observer la synchronisation entre étapes.

### Étapes

**Partie 1 : Créer les workspaces**

1. Connectez-vous à [https://app.fabric.microsoft.com](https://app.fabric.microsoft.com)
2. Créez trois workspaces : `Development`, `Test`, `Production`
3. Pour chaque workspace, sélectionnez un mode de licence incluant une capacité Fabric (Trial, Premium ou Fabric)

**Partie 2 : Créer le pipeline**

1. Dans la barre de navigation gauche, sélectionnez **Déploiements**
2. Cliquez sur **Nouveau pipeline**, donnez-lui un nom et confirmez
3. Assignez les workspaces aux étapes correspondantes

**Partie 3 : Créer du contenu et déployer**

1. Dans le workspace `Development`, créez un Lakehouse nommé `LabLakehouse`
2. Sélectionnez **Commencer avec des données d'exemple** pour le peupler
3. Revenez au pipeline de déploiement
4. Déployez le lakehouse de DEV vers TEST, puis de TEST vers PROD
5. Vérifiez que le lakehouse apparaît bien dans les workspaces Test et Production

**Partie 4 : Nettoyer les ressources**

1. Supprimez le pipeline de déploiement
2. Supprimez les trois workspaces

## 8. Vérification des connaissances

**Question 1 :** Quelle est la différence principale entre l'intégration Git et les pipelines de déploiement dans Microsoft Fabric ?

A) L'intégration Git est payante tandis que les pipelines de déploiement sont gratuits
B) L'intégration Git gère le contrôle de version tandis que les pipelines de déploiement gèrent la promotion entre environnements
C) Les pipelines de déploiement supportent uniquement les rapports Power BI
D) L'intégration Git ne supporte que GitHub

**Réponse correcte : B**
*L'intégration Git permet de versionner les éléments Fabric dans un référentiel Git. Les pipelines de déploiement permettent de promouvoir du contenu d'un workspace (DEV) vers un autre (TEST, PROD). Les deux outils sont complémentaires.*

---

**Question 2 :** Un développeur a modifié un notebook dans le workspace DEV et souhaite le déployer en PROD. Après déploiement, le notebook en PROD porte un nom différent du notebook en DEV. Comment est-ce possible ?

A) Ce n'est pas possible, les noms doivent toujours être identiques
B) Les éléments appairés conservent leur appairage même après renommage
C) Un nouveau notebook a été créé en PROD (non appairé)
D) Le pipeline de déploiement a renommé automatiquement le notebook

**Réponse correcte : B**
*L'appairage est basé sur un identifiant logique, pas sur le nom. Une fois deux éléments appairés, ils restent associés même si leurs noms divergent.*

---

**Question 3 :** Vous souhaitez que le pipeline de données en PROD se connecte à un serveur SQL différent de celui en DEV. Quelle fonctionnalité Fabric utilisez-vous ?

A) Des paramètres d'environnement dans le notebook
B) Des règles de déploiement (Deployment Rules)
C) Des variables Git
D) La configuration du workspace

**Réponse correcte : B**
*Les règles de déploiement permettent de modifier la connexion à la source de données lors du déploiement vers une étape cible, sans modifier manuellement les éléments.*

---

**Question 4 :** Quelle est la bonne pratique pour gérer les mots de passe dans les notebooks Fabric déployés en production ?

A) Stocker les mots de passe dans les variables de cellule du notebook
B) Les coder en dur dans le script Python
C) Utiliser Azure Key Vault et `mssparkutils.credentials.getSecret()`
D) Les stocker dans un fichier de configuration dans Git

**Réponse correcte : C**
*Les secrets ne doivent jamais être stockés dans le code source ou dans Git. Azure Key Vault est la solution recommandée pour stocker les secrets, accessibles depuis un notebook via mssparkutils.*

---

**Question 5 :** Combien d'étapes peut contenir un pipeline de déploiement Microsoft Fabric ?

A) Exactement 3 (DEV, TEST, PROD)
B) Entre 2 et 5
C) Entre 2 et 10
D) Illimité

**Réponse correcte : C**
*Un pipeline de déploiement Fabric peut contenir entre 2 et 10 étapes. Les trois étapes par défaut (DEV, TEST, PROD) sont simplement un point de départ personnalisable.*

## Résumé

Dans ce module, vous avez appris à mettre en œuvre le CI/CD dans Microsoft Fabric :

- **L'intégration Git** connecte un workspace Fabric à Azure DevOps ou GitHub pour le contrôle de version. Les éléments sont représentés comme des fichiers dans le référentiel.
- **Les stratégies de branchement** (feature branching, environment branching) permettent aux équipes de collaborer efficacement.
- **Les pipelines de déploiement** permettent de promouvoir du contenu de DEV vers TEST puis vers PROD, avec comparaison visuelle entre étapes.
- **Les règles de déploiement** adaptent automatiquement les connexions et paramètres selon l'environnement cible.
- **L'appairage des éléments** détermine si un déploiement remplace ou copie un élément dans l'étape cible.
- **Les API REST** permettent d'automatiser les déploiements dans des pipelines CI/CD externes (Azure Pipelines, GitHub Actions).
- Les **bonnes pratiques** incluent : conventions de nommage, gestion des secrets via Key Vault, et checklist de validation avant déploiement en production.
