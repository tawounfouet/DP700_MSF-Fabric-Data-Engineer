## 1. La sécurité au niveau des lignes (Row-Level Security — RLS)

### Qu'est-ce que la RLS ?

La **Row-Level Security** (RLS — Sécurité au niveau des lignes) est un mécanisme de sécurité qui filtre les données retournées à un utilisateur en fonction de son identité ou de ses attributs. Au lieu de créer des vues ou des tables séparées pour chaque utilisateur, la RLS applique un filtre transparent et automatique sur les requêtes.

**Exemple concret :**

Une table `ventes` contient les ventes de toutes les régions (France, Belgique, Suisse). Sans RLS, tous les utilisateurs voient toutes les lignes. Avec RLS :
- L'analyste France voit uniquement les lignes où `region = 'France'`
- L'analyste Belgique voit uniquement les lignes où `region = 'Belgique'`
- Le directeur commercial voit toutes les lignes

### RLS dans le point de terminaison SQL Analytics (Lakehouse / Warehouse)

Dans un **Data Warehouse** ou via le **point de terminaison SQL Analytics** d'un Lakehouse, la RLS se configure avec des commandes T-SQL, en utilisant des **prédicats de filtre** et des **politiques de sécurité**.

**Étape 1 : Créer une fonction de prédicat**

La fonction de prédicat définit la logique de filtrage. Elle retourne 1 si l'utilisateur est autorisé à voir la ligne, 0 sinon.

```sql
-- Créer la fonction de prédicat pour le filtrage par région
CREATE FUNCTION dbo.fn_region_security_predicate
    (@region_code NVARCHAR(10))
RETURNS TABLE
WITH SCHEMABINDING
AS
RETURN SELECT 1 AS fn_result
WHERE
    -- Le directeur voit tout
    USER_NAME() = 'director@company.com'
    OR
    -- Chaque analyste voit uniquement sa région
    @region_code = (
        SELECT region_code
        FROM dbo.user_region_mapping
        WHERE user_email = USER_NAME()
    );
GO
```

**Étape 2 : Créer la politique de sécurité**

```sql
-- Appliquer la politique de sécurité sur la table de ventes
CREATE SECURITY POLICY SalesRegionPolicy
ADD FILTER PREDICATE dbo.fn_region_security_predicate(region_code)
ON dbo.sales_orders
WITH (STATE = ON, SCHEMABINDING = ON);
GO
```

**Étape 3 : Vérifier le fonctionnement**

```sql
-- En tant qu'analyste France (connecté via l'identité france-analyst@company.com)
SELECT * FROM dbo.sales_orders;
-- Retourne uniquement les lignes où region_code = 'FR'

-- En tant que directeur
SELECT * FROM dbo.sales_orders;
-- Retourne toutes les lignes
```

**Gérer la politique de sécurité :**

```sql
-- Désactiver temporairement la politique (pour maintenance)
ALTER SECURITY POLICY SalesRegionPolicy WITH (STATE = OFF);

-- Réactiver la politique
ALTER SECURITY POLICY SalesRegionPolicy WITH (STATE = ON);

-- Supprimer la politique
DROP SECURITY POLICY SalesRegionPolicy;

-- Vérifier les politiques actives
SELECT * FROM sys.security_policies;
SELECT * FROM sys.security_predicates;
```

### RLS dans les modèles sémantiques Power BI (DAX)

Pour les **modèles sémantiques** utilisés dans les rapports Power BI, la RLS se configure via des expressions **DAX** dans Power BI Desktop ou directement dans le service.

**Étape 1 : Créer un rôle dans le modèle sémantique**

Dans Power BI Desktop :
1. Allez dans l'onglet **Modélisation** → **Gérer les rôles**
2. Cliquez sur **Créer**
3. Nommez le rôle : `AnalystRegion`
4. Pour la table `sales_orders`, ajoutez le filtre DAX :

```dax
[region_code] = LOOKUPVALUE(
    UserRegions[region_code],
    UserRegions[user_email], USERPRINCIPALNAME()
)
```

Cette expression DAX utilise `USERPRINCIPALNAME()` pour obtenir l'identité de l'utilisateur connecté, puis cherche sa région dans une table de mapping.

**Étape 2 : Assigner des utilisateurs aux rôles**

Dans le service Fabric (Power BI) :
1. Ouvrez le modèle sémantique → **...** → **Sécurité**
2. Pour le rôle `AnalystRegion`, ajoutez les utilisateurs ou groupes de sécurité appropriés
3. Cliquez sur **Enregistrer**

**Tester la RLS :**

```dax
-- Tester en tant qu'un autre utilisateur (dans Power BI Desktop)
-- Modélisation → Afficher en tant que → Sélectionner un rôle + entrer un email
```

**RLS dynamique via une table de mapping :**

Une approche plus scalable utilise une table `UserRegionMapping` dans le modèle :

```dax
-- Table de mapping (importée depuis le lakehouse)
-- UserEmail | RegionCode
-- alice@company.com | FR
-- bob@company.com | BE
-- carol@company.com | CH

-- Filtre DAX sur la table sales_orders
[region_code] IN
CALCULATETABLE(
    VALUES(UserRegionMapping[RegionCode]),
    FILTER(
        UserRegionMapping,
        UserRegionMapping[UserEmail] = USERPRINCIPALNAME()
    )
)
```

## 2. La sécurité au niveau des colonnes (Column-Level Security — CLS)

### Qu'est-ce que la CLS ?

La **Column-Level Security** (CLS) restreint l'accès à des colonnes spécifiques d'une table. Certaines colonnes peuvent contenir des données sensibles (salaires, numéros de sécurité sociale, données médicales) qui ne doivent être visibles que par certains utilisateurs.

**Exemple :**

La table `employees` contient les colonnes : `employee_id`, `name`, `department`, `salary`, `national_id`. La CLS permet de :
- Masquer `salary` pour tous les utilisateurs sauf la RH
- Masquer `national_id` pour tous sauf le service juridique

### Configurer la CLS dans un Data Warehouse Fabric

La CLS dans un Data Warehouse Fabric s'implémente via des permissions `GRANT` et `DENY` au niveau des colonnes :

```sql
-- Créer un schéma de sécurité pour les colonnes sensibles
-- Créer la table employees
CREATE TABLE dbo.employees (
    employee_id INT,
    name NVARCHAR(100),
    department NVARCHAR(50),
    salary DECIMAL(10, 2),       -- Colonne sensible
    national_id NVARCHAR(20)     -- Colonne très sensible
);

-- Créer un rôle pour les analystes RH
CREATE ROLE HRAnalyst;

-- Accorder l'accès à toutes les colonnes sauf les sensibles
GRANT SELECT ON dbo.employees TO HRAnalyst;

-- Révoquer l'accès aux colonnes sensibles pour les analystes généraux
DENY SELECT ON dbo.employees (salary) TO GeneralAnalyst;
DENY SELECT ON dbo.employees (national_id) TO GeneralAnalyst;

-- Accorder l'accès complet à la RH
GRANT SELECT ON dbo.employees TO HRRole;
```

**Résultat pour un analyste général :**
```sql
-- Cette requête réussit (colonnes autorisées)
SELECT employee_id, name, department FROM dbo.employees;

-- Cette requête échoue (colonne refusée)
SELECT salary FROM dbo.employees;
-- Erreur : "The SELECT permission was denied on the column 'salary'..."
```

### CLS via des vues SQL

Une approche alternative et plus flexible consiste à créer des **vues** qui exposent uniquement les colonnes autorisées :

```sql
-- Vue pour les analystes généraux (sans données sensibles)
CREATE VIEW dbo.vw_employees_general AS
SELECT
    employee_id,
    name,
    department
    -- salary et national_id sont exclus
FROM dbo.employees;

-- Vue pour la RH (toutes les colonnes)
CREATE VIEW dbo.vw_employees_hr AS
SELECT
    employee_id,
    name,
    department,
    salary,
    national_id
FROM dbo.employees;

-- Accorder l'accès aux vues appropriées
GRANT SELECT ON dbo.vw_employees_general TO GeneralAnalyst;
GRANT SELECT ON dbo.vw_employees_hr TO HRRole;
-- Révoquer l'accès direct à la table
REVOKE SELECT ON dbo.employees FROM GeneralAnalyst;
```

## 3. La sécurité au niveau des objets (Object-Level Security — OLS)

### Qu'est-ce que l'OLS ?

La **Object-Level Security** (OLS) dans le contexte des modèles sémantiques Power BI permet de masquer des tables entières ou des colonnes entières à certains utilisateurs. Contrairement à la RLS qui filtre les lignes, l'OLS masque complètement l'existence d'un objet.

**Différence RLS vs OLS :**

```
RLS : La table sales_orders est visible
      Mais chaque utilisateur voit des lignes différentes
      (filtrage transparent)

OLS : La table salaries est complètement invisible
      pour certains rôles
      (l'objet n'existe pas pour ces utilisateurs)
```

### Configurer l'OLS dans un modèle sémantique

L'OLS se configure via l'éditeur tabulaire ou Tabular Model Scripting Language (TMSL). Voici comment l'activer avec un exemple JSON de définition de métadonnées :

**Via l'API Fabric / Tabular Editor :**

```json
{
  "roles": [
    {
      "name": "GeneralAnalyst",
      "modelPermission": "read",
      "tablePermissions": [
        {
          "name": "salaries",
          "filterExpression": "false"
        }
      ]
    }
  ]
}
```

Avec `"filterExpression": "false"`, la table `salaries` est complètement masquée pour les membres du rôle `GeneralAnalyst`. Ces utilisateurs ne verront même pas le nom de la table dans la liste des champs du rapport.

**Via PowerShell avec le module SqlServer :**

```powershell
# Connexion au modèle sémantique via XMLA
$server = "powerbi://api.powerbi.com/v1.0/myorg/MonWorkspace"
$database = "MonModeleSemantiqueDP700"

# Modifier les permissions OLS via TMSL
$tmslScript = @"
{
  "createOrReplace": {
    "object": {
      "database": "$database",
      "role": "GeneralAnalyst"
    },
    "role": {
      "name": "GeneralAnalyst",
      "modelPermission": "read",
      "tablePermissions": [
        {
          "name": "salaries",
          "filterExpression": "false"
        },
        {
          "name": "personal_data",
          "filterExpression": "false"
        }
      ]
    }
  }
}
"@

Invoke-ASCmd -Server $server -Database $database -Query $tmslScript
```

## 4. Le masquage dynamique des données (Dynamic Data Masking)

### Qu'est-ce que le masquage dynamique des données ?

Le **Dynamic Data Masking** (DDM) permet d'obscurcir automatiquement des données sensibles dans les résultats de requêtes pour les utilisateurs non privilégiés, sans modifier les données stockées. Les données réelles sont conservées intactes dans la base de données.

**Exemple de masquage :**

```
Données réelles dans la base :
national_id = "2850312345678"
email       = "alice.dupont@company.com"
salary      = 65000.00

Ce que voit un utilisateur non privilégié :
national_id = "XXXX"
email       = "aXXX@XXXX.com"
salary      = 0.00

Ce que voit un utilisateur privilégié (UNMASK permission) :
national_id = "2850312345678"
email       = "alice.dupont@company.com"
salary      = 65000.00
```

### Types de masques disponibles

| Type de masque | Fonction SQL | Exemple de résultat |
|----------------|-------------|---------------------|
| **Default** | `MASKED WITH (FUNCTION = 'default()')` | Texte → XXXX, Nombre → 0, Date → 01-01-1900 |
| **Email** | `MASKED WITH (FUNCTION = 'email()')` | `aXXX@XXXX.com` |
| **Partiel** | `MASKED WITH (FUNCTION = 'partial(1, "XXXX", 4)')` | `2XXX...5678` |
| **Aléatoire** | `MASKED WITH (FUNCTION = 'random(1, 100)')` | Nombre aléatoire entre 1 et 100 |

### Configurer le DDM dans un Data Warehouse Fabric

```sql
-- Créer une table avec des colonnes masquées
CREATE TABLE dbo.customers (
    customer_id   INT PRIMARY KEY,
    full_name     NVARCHAR(100) MASKED WITH (FUNCTION = 'partial(1, "XXXXXXX", 1)'),
    email         NVARCHAR(200) MASKED WITH (FUNCTION = 'email()'),
    phone         NVARCHAR(20)  MASKED WITH (FUNCTION = 'partial(0, "XXX-XXX-", 4)'),
    national_id   NVARCHAR(20)  MASKED WITH (FUNCTION = 'default()'),
    credit_score  INT           MASKED WITH (FUNCTION = 'random(300, 850)'),
    annual_revenue DECIMAL(12,2) MASKED WITH (FUNCTION = 'default()')
);

-- Ajouter un masque à une colonne existante
ALTER TABLE dbo.employees
ALTER COLUMN salary ADD MASKED WITH (FUNCTION = 'default()');

-- Supprimer un masque d'une colonne
ALTER TABLE dbo.employees
ALTER COLUMN salary DROP MASKED;
```

**Accorder la permission UNMASK à un utilisateur privilégié :**

```sql
-- Par défaut, tous les utilisateurs voient les données masquées
-- Accorder l'accès aux données réelles pour certains rôles

-- Accorder UNMASK au rôle RH
GRANT UNMASK ON dbo.customers TO HRRole;

-- Accorder UNMASK sur une colonne spécifique uniquement
GRANT UNMASK ON dbo.customers(annual_revenue) TO FinanceAnalyst;

-- Vérifier les masques configurés
SELECT
    t.name AS table_name,
    c.name AS column_name,
    c.masking_function
FROM sys.masked_columns c
JOIN sys.tables t ON c.object_id = t.object_id;
```

**Test du comportement :**

```sql
-- En tant qu'utilisateur standard (masquage appliqué)
SELECT customer_id, full_name, email, national_id
FROM dbo.customers;
-- Résultat : A*****e | aXXX@XXXX.com | XXXX

-- En tant qu'utilisateur avec UNMASK
SELECT customer_id, full_name, email, national_id
FROM dbo.customers;
-- Résultat : Alice Dupont | alice.dupont@company.com | 2850312345678
```

## 5. Les paramètres de sécurité au niveau du tenant

### Qu'est-ce que les Tenant Settings ?

Les **Tenant Settings** (paramètres du tenant) sont des paramètres de configuration globaux qui contrôlent quelles fonctionnalités sont disponibles pour l'ensemble de l'organisation dans Microsoft Fabric. Seuls les **administrateurs Fabric** peuvent modifier ces paramètres.

Pour accéder aux paramètres du tenant :
1. Dans Fabric, cliquez sur l'icône **Paramètres** (engrenage)
2. Sélectionnez **Portail d'administration**
3. Cliquez sur **Paramètres du locataire**

### Catégories de paramètres tenant importants

**Paramètres de sécurité et de gouvernance :**

| Paramètre | Description | Recommandation |
|-----------|-------------|----------------|
| **Partage de contenu avec des utilisateurs externes** | Permet de partager des éléments Fabric avec des utilisateurs hors du tenant | Restreindre aux groupes de sécurité approuvés |
| **Publier sur le Web** | Permet de publier des rapports Power BI publiquement | Désactiver dans les environnements sensibles |
| **Intégration Git** | Active la connexion des workspaces à Git | Activé pour les équipes IT/Data |
| **Pipelines de déploiement** | Active la fonctionnalité de déploiement pipeline | Activé pour les équipes IT/Data |
| **Copier les données dans le Presse-papiers** | Permet de copier les données de visuels | Désactiver pour les données confidentielles |

**Exemples de paramètres tenant à configurer :**

```
Paramètre : "Partager le contenu avec des utilisateurs externes"
État : Activé uniquement pour les groupes : [fabric-external-sharing@company.com]

Paramètre : "Les utilisateurs peuvent créer des espaces de travail"
État : Désactivé (seuls les admins créent les workspaces)

Paramètre : "Étiquettes de confidentialité de Microsoft Purview"
État : Activé pour l'ensemble de l'organisation

Paramètre : "Auditer et consigner les activités de vérification"
État : Activé pour l'ensemble de l'organisation
```

### Déléguer les paramètres aux administrateurs de capacité ou de domaine

Les administrateurs Fabric peuvent déléguer certains paramètres aux **administrateurs de capacité** ou aux **administrateurs de domaine**, évitant ainsi que l'administrateur central ne soit un goulot d'étranglement :

```
Hiérarchie de délégation :
Administrateur Fabric (global)
    ↓ délègue
Administrateur de capacité (pour la capacité F64)
    ↓ délègue
Administrateur de domaine (pour le domaine "Finance")
    ↓ peut gérer
Administrateur de workspace (pour les workspaces du domaine)
```

## 6. Sécurité réseau : liaisons privées et VNets managés

### Les liaisons privées (Private Links / Private Endpoints)

Les **liaisons privées** permettent de restreindre l'accès à Microsoft Fabric via un réseau virtuel Azure privé, bloquant tout accès depuis l'Internet public. C'est la solution recommandée pour les organisations qui ont des exigences strictes de sécurité réseau.

**Architecture avec liaisons privées :**

```
Internet public            Réseau Azure privé
     ✗                          ✓
     |                          |
     |               ┌──────────────────────┐
     |               │  Virtual Network     │
     |               │  (VNet Azure)        │
     |               │                      │
     |               │  ┌──────────────┐   │
     |               │  │ Private      │   │
     |               │  │ Endpoint     │───┼──► Microsoft Fabric
     |               │  └──────────────┘   │    (accès sécurisé)
     |               │                      │
     |               │  ┌──────────────┐   │
     |               │  │ VM / Service │   │
     |               │  │ on-premises  │   │
     |               │  └──────────────┘   │
     |               └──────────────────────┘
```

**Configurer les liaisons privées :**

1. Dans le **Portail d'administration** Fabric → **Paramètres du locataire**
2. Recherchez **Azure Private Link**
3. Activez le paramètre "Bloquer l'accès Internet public"
4. Dans le portail Azure, créez un **Private Endpoint** pour votre tenant Fabric
5. Configurez le DNS privé pour résoudre `*.pbidedicated.microsoft.com` vers l'IP privée

> **Attention :** Une fois activé, l'accès à Fabric depuis Internet public est bloqué. Assurez-vous que tous les utilisateurs accèdent via le réseau privé avant d'activer ce paramètre.

### Points de terminaison privés managés (Managed Private Endpoints)

Les **Managed Private Endpoints** permettent aux workloads Fabric (notamment Spark) de se connecter de manière sécurisée à des sources de données Azure (Azure SQL, Azure Data Lake, etc.) sans exposer ces sources sur Internet.

**Créer un Managed Private Endpoint :**

1. Dans un workspace Fabric, accédez aux **Paramètres du workspace**
2. Sélectionnez **Sécurité réseau**
3. Sous **Points de terminaison privés managés**, cliquez sur **Ajouter**
4. Sélectionnez la ressource Azure cible (ex : Azure SQL Database)
5. Le propriétaire de la ressource Azure doit approuver la demande de connexion

**Architecture avec Managed Private Endpoints :**

```
Fabric Workspace (VNet managé)
├── Notebook Spark ──────────────────────────────────────────────┐
│                                                                 │
│   Managed Private Endpoint                                      │
│   ────────────────────────                                      │
│   Connexion privée approuvée ──► Azure SQL Database            │
│                                  (sans accès Internet public)  │
└───────────────────────────────────────────────────────────────┘
```

### VNets managés (Managed Virtual Networks)

Les **VNets managés** sont des réseaux virtuels créés et gérés automatiquement par Microsoft Fabric pour chaque workspace Fabric. Ils fournissent un **isolement réseau** pour les charges de travail Spark — les clusters de calcul Spark ne sont plus dans un réseau virtuel partagé, mais dans un réseau dédié.

**Avantages des VNets managés :**
- Isolation réseau complète des workloads Spark
- Support des Managed Private Endpoints
- Support des liaisons privées pour les éléments d'ingénierie des données

## 7. Accès conditionnel Microsoft Entra ID

### Qu'est-ce que l'accès conditionnel ?

L'**accès conditionnel** (Conditional Access) est une fonctionnalité de Microsoft Entra ID qui permet de définir des conditions sous lesquelles les utilisateurs peuvent accéder à Microsoft Fabric. Contrairement aux permissions qui contrôlent ce qu'un utilisateur peut faire dans Fabric, l'accès conditionnel contrôle **s'il peut se connecter à Fabric** selon son contexte.

**Politiques d'accès conditionnel typiques pour Fabric :**

```
Politique 1 : Exiger l'MFA pour l'accès à Fabric
  Condition : Utilisateur se connecte à Microsoft Fabric
  Contrôle : Requérir l'authentification multifacteur (MFA)

Politique 2 : Restreindre l'accès par localisation
  Condition : L'utilisateur se connecte depuis hors de France/UE
  Contrôle : Bloquer l'accès (ou requérir MFA + appareil conforme)

Politique 3 : Exiger un appareil conforme
  Condition : Accès depuis un appareil non géré par Intune
  Contrôle : Bloquer l'accès ou accès en lecture seule uniquement

Politique 4 : Administrateurs Fabric
  Condition : Rôle Administrateur Fabric
  Contrôle : MFA + appareil géré + localisation approuvée
```

### Configurer une politique d'accès conditionnel

La configuration se fait dans le **portail Microsoft Entra ID** :

1. Accédez à [https://entra.microsoft.com](https://entra.microsoft.com)
2. Sélectionnez **Protection** → **Accès conditionnel**
3. Cliquez sur **+ Nouvelle politique**
4. Nommez la politique : `Fabric - Exiger MFA`
5. **Utilisateurs** : Sélectionnez "Tous les utilisateurs" ou un groupe spécifique
6. **Ressources cibles** : Sélectionnez "Microsoft Fabric" ou "Power BI Service"
7. **Conditions** : configurez les conditions souhaitées
8. **Contrôles d'accès** : sélectionnez "Exiger l'authentification multifacteur"
9. Activez la politique et cliquez sur **Créer**

## 8. Journaux d'audit et conformité

### Journaux d'audit Fabric

Microsoft Fabric enregistre toutes les activités des utilisateurs dans des **journaux d'audit** disponibles via Microsoft Purview. Les journaux capturent :

- Connexions et accès
- Création, modification et suppression d'éléments
- Partages et modifications de permissions
- Exports de données
- Exécutions de rapports et requêtes

**Accéder aux journaux d'audit :**

1. Portail d'administration Fabric → **Journaux d'audit**
2. Ou directement dans **Microsoft Purview** → **Audit** → **Recherche dans le journal d'audit**

**Opérations auditées importantes :**

| Opération | Description |
|-----------|-------------|
| `ViewReport` | Un utilisateur a consulté un rapport |
| `ExportReport` | Un utilisateur a exporté des données |
| `ShareDashboard` | Un tableau de bord a été partagé |
| `UpdateDatasetParameters` | Les paramètres d'un modèle sémantique ont été modifiés |
| `DeleteDataset` | Un modèle sémantique a été supprimé |
| `ChangeWorkspaceAccess` | Les permissions d'un workspace ont changé |

**Requête PowerShell pour extraire les logs d'audit :**

```powershell
# Installer le module Power BI
Install-Module -Name MicrosoftPowerBIMgmt -Force

# Se connecter
Connect-PowerBIServiceAccount

# Obtenir les logs d'audit des 7 derniers jours
$startDate = (Get-Date).AddDays(-7).ToString("yyyy-MM-dd")
$endDate = (Get-Date).ToString("yyyy-MM-dd")

$auditLogs = Get-PowerBIActivityEvent `
    -StartDateTime "$startDate" `
    -EndDateTime "$endDate" `
    -ActivityType "ExportReport"

$auditLogs | Select-Object -Property `
    CreationTime, UserId, Activity, WorkSpaceName, `
    ReportName, DatasetName | Export-Csv `
    -Path "audit_exports.csv" -NoTypeInformation

Write-Output "Nombre d'exports : $($auditLogs.Count)"
```

## 9. Vérification des connaissances

**Question 1 :** Vous avez une table `transactions` dans un Data Warehouse Fabric. Les analystes junior doivent voir uniquement les transactions de leur agence, tandis que les managers voient tout. Quelle technologie Fabric utilisez-vous ?

A) Column-Level Security avec DENY
B) Row-Level Security avec une Security Policy et un prédicat de filtre
C) Object-Level Security avec filterExpression
D) Dynamic Data Masking sur la colonne agency_id

**Réponse correcte : B**
*La RLS est conçue pour filtrer les lignes visibles par chaque utilisateur selon son identité. On crée une fonction de prédicat qui retourne les lignes autorisées, puis une Security Policy qui applique ce prédicat sur la table.*

**Question 2 :** Une analyste doit voir toutes les lignes de la table `employees` mais pas la colonne `salary`. Quelle technologie implémentez-vous ?

A) Row-Level Security avec un filtre sur salary IS NULL
B) Object-Level Security pour masquer la colonne
C) Column-Level Security avec DENY SELECT sur la colonne salary
D) Dynamic Data Masking avec la fonction default()

**Réponse correcte : C**
*La CLS permet de restreindre l'accès à des colonnes spécifiques avec DENY SELECT ON table(colonne) TO role. Cela empêche l'utilisateur de requêter cette colonne.*

**Question 3 :** Vous avez des données de numéros de carte bancaire dans un warehouse. Certains utilisateurs du service client doivent voir les 4 derniers chiffres seulement. Quelle approche est la plus appropriée ?

A) Créer une vue qui concatène les caractères masqués
B) Dynamic Data Masking avec la fonction partial()
C) Row-Level Security filtrant les numéros de carte visibles
D) Object-Level Security masquant la table entière

**Réponse correcte : B**
*Dynamic Data Masking avec la fonction partial() permet d'afficher une partie d'un champ (ex : les 4 derniers chiffres) tout en masquant le reste. La syntaxe serait : `MASKED WITH (FUNCTION = 'partial(0, "XXXX-XXXX-XXXX-", 4)')`.*

**Question 4 :** Votre organisation exige que personne ne puisse accéder à Fabric depuis Internet public — uniquement via le réseau d'entreprise. Quelle fonctionnalité Fabric activez-vous ?

A) Accès conditionnel Entra ID avec filtre sur l'adresse IP
B) Liaisons privées (Private Links) + blocage de l'accès Internet public
C) VNet managé pour chaque workspace
D) Managed Private Endpoints pour toutes les sources de données

**Réponse correcte : B**
*Les liaisons privées (Private Links) permettent de router tout le trafic vers Fabric via un réseau virtuel Azure privé. En activant le blocage de l'accès public, tout accès depuis Internet est refusé.*

**Question 5 :** Quelle est la différence entre la RLS dans un modèle sémantique (DAX) et la RLS dans le point de terminaison SQL d'un lakehouse (T-SQL) ?

A) Il n'y a aucune différence, les deux utilisent DAX
B) La RLS T-SQL s'applique uniquement aux requêtes SQL, la RLS DAX s'applique aux requêtes via le modèle sémantique et les rapports Power BI
C) La RLS T-SQL ne fonctionne pas dans les lakehouses Fabric
D) La RLS DAX est plus performante que la RLS T-SQL

**Réponse correcte : B**
*Les deux types de RLS sont complémentaires. La RLS T-SQL filtre les données au niveau du moteur SQL et s'applique à toutes les requêtes SQL sur le warehouse/lakehouse SQL. La RLS DAX dans le modèle sémantique s'applique aux rapports Power BI et aux requêtes DAX. Il est recommandé de configurer les deux pour une protection complète.*

## Résumé

Dans ce module, vous avez appris à implémenter des mécanismes de sécurité avancés dans Microsoft Fabric :

- **Row-Level Security (RLS)** : filtre les lignes visibles par chaque utilisateur. En T-SQL via des Security Policies et prédicats de filtre ; en DAX via des rôles dans les modèles sémantiques.
- **Column-Level Security (CLS)** : restreint l'accès à des colonnes spécifiques via des permissions `DENY SELECT` ou des vues SQL.
- **Object-Level Security (OLS)** : masque complètement des tables ou colonnes dans les modèles sémantiques via `filterExpression: false`.
- **Dynamic Data Masking** : obscurcit automatiquement les données sensibles (emails, numéros, etc.) pour les utilisateurs non autorisés, sans modifier les données stockées.
- **Tenant Settings** : paramètres globaux contrôlant les fonctionnalités Fabric pour toute l'organisation, configurés dans le portail d'administration.
- **Liaisons privées** : connexion sécurisée à Fabric via un VNet Azure, bloquant l'accès Internet public.
- **Managed Private Endpoints** : connexion sécurisée depuis les workloads Spark vers les sources de données Azure.
- **Accès conditionnel** : contrôle si un utilisateur peut se connecter à Fabric selon son contexte (localisation, appareil, MFA).
- **Journaux d'audit** : enregistrement de toutes les activités pour la conformité et la détection d'anomalies.
