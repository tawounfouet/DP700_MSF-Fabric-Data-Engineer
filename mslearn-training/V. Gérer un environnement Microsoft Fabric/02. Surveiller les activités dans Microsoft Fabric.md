## 1. Introduction à la supervision dans Microsoft Fabric

### Pourquoi surveiller les activités Fabric ?

Dans une plateforme de données, la supervision (monitoring) est essentielle pour garantir la fiabilité et la performance des processus de données. Microsoft Fabric exécute de nombreuses activités en arrière-plan ou selon des planifications : pipelines d'ingestion, transformations de données, actualisations de modèles sémantiques, traitements Spark. Sans supervision, les erreurs peuvent passer inaperçues pendant des heures, voire des jours.

La surveillance vous permet de :

- **Détecter les erreurs rapidement** : identifier si un pipeline a échoué avant que les utilisateurs ne s'en aperçoivent
- **Comprendre les performances** : comparer les durées d'exécution actuelles avec les exécutions passées
- **Identifier les goulots d'étranglement** : repérer les étapes lentes dans un pipeline ou un notebook
- **Assurer la résilience** : vérifier que les données arrivent à destination dans les délais attendus
- **Auditer les activités** : savoir qui a exécuté quoi et quand

### La surveillance comme pratique continue

La surveillance n'est pas une activité ponctuelle. C'est un processus continu qui suit le cycle de vie des données :

```
Planification → Exécution → Surveillance → Analyse → Correction → Optimisation
      ↑                                                                    |
      └────────────────────────────────────────────────────────────────────┘
```

Les **meilleures pratiques de supervision** dans Fabric sont :

1. **Identifier les éléments critiques à surveiller** : quels pipelines, quels dataflows sont essentiels pour le métier ?
2. **Définir des métriques de référence** : quelle est la durée normale d'exécution ? Quel est le volume de données attendu ?
3. **Collecter et analyser régulièrement** les données de supervision pour détecter les anomalies
4. **Examiner les journaux et métriques** pour identifier des patterns d'erreurs récurrents
5. **Prendre des mesures correctives** dès qu'une déviation par rapport au comportement normal est détectée
6. **Optimiser les performances** en utilisant les données historiques pour identifier les opportunités d'amélioration

## 2. Les activités à surveiller dans Fabric

Microsoft Fabric propose plusieurs types d'activités qui génèrent des données de surveillance. Comprendre chaque type vous aide à cibler votre supervision.

### Activités de pipeline de données

Un **pipeline de données** est un groupe d'activités qui effectuent ensemble une tâche d'ingestion ou de transformation (ETL/ELT). Les pipelines peuvent contenir des activités de copie, des transformations, des scripts SQL, des appels à des notebooks, etc.

**Ce qu'il faut surveiller :**
- La réussite ou l'échec de chaque exécution du pipeline
- La durée totale et la durée de chaque activité individuelle
- Les messages d'erreur en cas d'échec
- L'historique des exécutions pour détecter des dégradations de performance progressives

**Schéma d'un pipeline type :**

```
Pipeline: Ingest_Sales_Data
├── Activité 1: Copy_From_SQL_Server    [5 min] ✓
├── Activité 2: Transform_With_Notebook [12 min] ✓
├── Activité 3: Load_To_Lakehouse       [3 min] ✓
└── Activité 4: Refresh_Semantic_Model  [8 min] ✗ ERREUR
```

### Dataflows Gen2

Un **dataflow** est un outil à faible code (Power Query) permettant d'ingérer, transformer et charger des données. Les dataflows peuvent être exécutés manuellement, selon une planification ou via un pipeline.

**Ce qu'il faut surveiller :**
- Les heures de début et de fin
- L'état (En cours, Réussi, Échoué, Annulé)
- La durée d'exécution
- Le nombre de lignes traitées
- Les détails des erreurs en cas d'échec

### Actualisations de modèles sémantiques

Les **modèles sémantiques** (anciennement datasets Power BI) doivent être actualisés régulièrement pour refléter les données les plus récentes. Une actualisation échouée signifie que les rapports affichent des données obsolètes.

**Ce qu'il faut surveiller :**
- Le statut de chaque actualisation (planifiée ou manuelle)
- Le nombre de tentatives (retry) — les nouvelles tentatives signalent des problèmes temporaires
- La durée d'actualisation — une augmentation progressive peut indiquer une croissance non maîtrisée du volume de données

### Tâches Spark, notebooks et lakehouses

Les **notebooks Spark** permettent d'exécuter du code Python, Scala ou SQL pour traiter de grands volumes de données dans des lakehouses.

**Ce qu'il faut surveiller :**
- La progression des tâches Spark (stages, jobs, tasks)
- L'utilisation des ressources (CPU, mémoire, shuffle)
- Les journaux d'application Spark (logs)
- Les erreurs et exceptions dans le code

### Microsoft Fabric Eventstreams

Les **Eventstreams** sont configurés pour ingérer des données en streaming en continu. Contrairement aux traitements batch, les eventstreams s'exécutent perpétuellement.

**Ce qu'il faut surveiller :**
- L'état d'ingestion (actif, suspendu, en erreur)
- Le débit d'ingestion (événements par seconde)
- La latence de traitement
- Les données perdues ou retardées

## 3. Le Monitor Hub

### Qu'est-ce que le Monitor Hub ?

Le **Monitor Hub** est l'outil central de surveillance dans Microsoft Fabric. C'est une interface unifiée qui collecte et affiche les métadonnées d'activité pour tous les éléments Fabric de vos workspaces. Plutôt que de surveiller chaque élément individuellement dans son espace de travail, le Monitor Hub regroupe toutes les activités en un seul endroit.

**Accéder au Monitor Hub :**

1. Dans la barre de navigation gauche de Fabric, cliquez sur l'icône **Monitor** (ou sélectionnez "Surveiller" dans le menu)
2. Le Monitor Hub s'ouvre avec la liste de toutes les activités récentes

### Activités affichées dans le Monitor Hub

Le Monitor Hub affiche les métadonnées de surveillance pour :

| Type d'activité | Ce qui est affiché |
|-----------------|---------------------|
| Pipelines de données | Exécutions, statut, durée, activités individuelles |
| Dataflows Gen2 | Exécutions, statut, durée, chargement de tables |
| Actualisations de modèles sémantiques | Statut, nouvelles tentatives, durée |
| Notebooks Spark | Exécutions, statut, logs Spark |
| Définitions de travaux Spark | Exécutions, statut, détails des tâches |
| Datamarts | Actualisations, statut |

> **Note :** Le Monitor Hub affiche uniquement les activités des éléments pour lesquels vous avez les permissions de consultation.

### Naviguer dans le Monitor Hub

**Vue principale**

La vue principale du Monitor Hub affiche une liste des activités récentes avec les colonnes suivantes :
- **Nom** : nom de l'activité ou de l'élément
- **Type** : type de l'élément (Dataflow Gen2, Pipeline, Notebook...)
- **Statut** : En cours, Réussi, Échoué, Annulé
- **Heure de début**
- **Durée**
- **Soumis par** : l'utilisateur ou le service ayant déclenché l'exécution
- **Emplacement** : workspace contenant l'élément

**Actions disponibles sur une activité**

En survolant une activité dans le Monitor Hub, cliquez sur les points de suspension (**...**) pour accéder aux actions disponibles :

- **Ouvrir** : naviguer vers l'élément dans son workspace
- **Réessayer** : relancer l'exécution (si applicable)
- **Afficher les détails** : ouvrir le panneau de détails de l'exécution
- **Exécutions historiques** : consulter l'historique des exécutions précédentes

### Afficher les détails d'une activité

Cliquez sur **Afficher les détails** pour accéder à un panneau de détails personnalisé selon le type d'activité. Ce panneau affiche :

- **Statut** : le statut global de l'exécution
- **Heure de début et de fin** : les horodatages précis
- **Durée totale** : calculée automatiquement
- **Message d'erreur** : en cas d'échec, le message complet de l'erreur
- **Statistiques** : données spécifiques au type d'activité (ex : nombre de lignes pour un dataflow)

**Pour un pipeline de données**, les détails montrent également le statut de chaque activité individuelle du pipeline, ce qui permet d'identifier précisément quelle étape a échoué.

**Pour un notebook Spark**, les détails incluent des liens vers l'interface Spark (Spark UI) permettant d'analyser l'exécution des jobs, stages et tasks.

### Consulter l'historique des exécutions

Pour un élément qui s'exécute régulièrement (ex : un dataflow planifié chaque heure), vous pouvez consulter l'historique des exécutions passées :

1. Dans le Monitor Hub, trouvez l'élément souhaité
2. Cliquez sur **...** → **Exécutions historiques**
3. Une liste de toutes les exécutions passées s'affiche avec leur statut et durée

Cet historique est précieux pour :
- **Identifier des tendances** : la durée augmente-t-elle progressivement ?
- **Détecter des pannes récurrentes** : y a-t-il des échecs à une heure précise chaque jour ?
- **Corréler des erreurs** : une erreur dans un pipeline correspond-elle à une panne dans un système source ?

## 4. Filtrer et personnaliser les vues du Monitor Hub

Dans un environnement avec de nombreux workspaces et éléments, le Monitor Hub peut afficher des centaines d'activités. Les filtres et options de vue permettent de cibler rapidement les informations pertinentes.

### Appliquer des filtres

Cliquez sur le bouton **Filtrer** dans le Monitor Hub pour accéder aux options de filtrage :

| Critère de filtre | Valeurs possibles |
|-------------------|------------------|
| **Statut** | En cours, Réussi, Échoué, Annulé |
| **Type d'élément** | Dataflow Gen2, Pipeline, Notebook, Modèle sémantique... |
| **Workspace** | Sélectionner un ou plusieurs workspaces |
| **Soumis par** | Filtrer par utilisateur |
| **Plage de dates** | Définir une période |

**Exemple d'utilisation des filtres :**

Pour voir uniquement les dataflows ayant échoué aujourd'hui :
- Statut : **Échoué**
- Type d'élément : **Dataflow Gen2**
- Plage de dates : **Aujourd'hui**

### Personnaliser les colonnes affichées

Cliquez sur **Options de colonnes** pour choisir quelles colonnes afficher dans la vue du Monitor Hub. Les colonnes disponibles incluent :

- Nom de l'activité
- Statut
- Type d'élément
- Heure de début
- Heure de fin
- Durée
- Soumis par
- Emplacement (workspace)
- Type d'actualisation

> **Conseil :** Pour une vue de production quotidienne, affichez : Nom, Statut, Type d'élément, Heure de début, Durée, Soumis par. Triez par Heure de début décroissante pour voir les activités les plus récentes en premier.

## 5. Surveiller avec la Capacity Metrics App

### Présentation de la Capacity Metrics App

Pour aller au-delà de la surveillance des activités individuelles, Microsoft Fabric propose la **Fabric Capacity Metrics App** (application Power BI) qui mesure la consommation de ressources de la capacité Fabric.

Cette application est essentielle pour les administrateurs Fabric et les architectes data qui doivent :
- Surveiller la consommation de Compute Units (CU) de la capacité
- Identifier les pics de consommation et les workspaces les plus gourmands
- Anticiper les besoins de mise à l'échelle de la capacité
- Diagnostiquer les phénomènes de **throttling** (ralentissement dû à une surconsommation)

### Concepts clés de la Capacity Metrics App

**Compute Units (CU)**

Les CU sont l'unité de mesure de la consommation des ressources dans Microsoft Fabric. Chaque type d'opération consomme un certain nombre de CU :
- Un job Spark consomme des CU proportionnellement à sa durée et aux ressources allouées
- Un pipeline de données consomme des CU selon les activités exécutées
- Une actualisation de modèle sémantique consomme des CU

**Throttling**

Lorsque la consommation de CU dépasse la limite allouée à la capacité, Fabric applique un **throttling** : les nouvelles opérations sont mises en file d'attente ou ralenties. Cela peut impacter les SLA des rapports et des pipelines.

```
Fonctionnement du throttling :
┌─────────────────────────────────────────────┐
│  Capacité F64 = 64 CU disponibles          │
│                                             │
│  Consommation actuelle : 70 CU             │
│                          ^^^ Dépassement ! │
│                                             │
│  Résultat : Throttling activé              │
│  - Nouvelles requêtes mises en attente     │
│  - Exécutions ralenties                    │
└─────────────────────────────────────────────┘
```

**Smoothing (lissage)**

Fabric applique un mécanisme de lissage sur 24 heures pour éviter les impacts du throttling sur les pics courts. Une consommation élevée pendant 10 minutes ne déclenche pas immédiatement le throttling si la consommation moyenne sur 24 heures reste dans les limites.

### Installer la Capacity Metrics App

1. Accédez au portail d'administration Fabric ou à AppSource
2. Recherchez **Microsoft Fabric Capacity Metrics**
3. Installez l'application Power BI dans votre tenant
4. Configurez la connexion à votre capacité Fabric

### Analyser la consommation avec la Capacity Metrics App

L'application offre plusieurs vues :

**Vue Timepoint** : consommation CU par intervalle de 30 secondes — idéal pour identifier des pics ponctuels

**Vue Multi-metric** : comparaison de plusieurs métriques sur une période — idéal pour analyser les tendances

**Vue Item** : décomposition de la consommation par workspace et par élément — idéal pour identifier les workloads les plus coûteux

## 6. Déclencher des actions avec Microsoft Fabric Activator

### Qu'est-ce que Microsoft Fabric Activator ?

**Microsoft Fabric Activator** (anciennement Data Activator) est un composant de Real-Time Intelligence dans Fabric qui permet de déclencher automatiquement des actions en réponse à des événements ou des conditions dans des données en streaming.

Contrairement au Monitor Hub qui observe les activités passées, Activator agit en **temps réel** sur des flux de données pour répondre à des conditions définies.

**Cas d'usage typiques :**
- Envoyer un email d'alerte quand la température mesurée par un capteur IoT dépasse 80°C
- Déclencher un pipeline de données quand un nouveau fichier est détecté dans un dossier
- Alerter les gestionnaires quand le stock d'un produit tombe en dessous d'un seuil critique
- Lancer un workflow Power Automate quand une anomalie est détectée dans un flux financier
- Alerter l'équipe ops quand un pipeline de données échoue pour la 3ème fois consécutive

### Les quatre concepts fondamentaux d'Activator

Activator fonctionne selon quatre concepts fondamentaux :

**1. Événements (Events)**

Chaque enregistrement dans un flux de données représente un **événement** survenu à un moment précis. Par exemple :
```json
{
  "timestamp": "2026-05-27T14:30:00Z",
  "sensor_id": "SENSOR-001",
  "temperature": 82.5,
  "location": "DataCenter-A"
}
```

**2. Objets (Objects)**

Les données de l'événement peuvent être utilisées pour représenter un **objet** métier — une entité réelle comme un capteur, une commande client, ou un véhicule. Dans l'exemple ci-dessus, l'objet serait le capteur `SENSOR-001`.

**3. Propriétés (Properties)**

Les champs des données d'événement sont mappés sur les **propriétés** de l'objet. La propriété `temperature` représente l'état actuel du capteur.

**4. Règles (Rules)**

Les **règles** définissent les conditions qui déclenchent une action. Une règle compare les valeurs de propriété à un seuil ou un pattern. Exemple :

```
Règle : "Alerte surchauffe"
Condition : temperature > 80
Action : Envoyer un email à l'équipe ops
```

### Architecture d'Activator

```
Sources de données                Activator              Actions
─────────────────                 ─────────              ───────
Eventstream  ──┐                 ┌──────────┐           Email
               ├──► Événements ──► Objets   ──► Règles ──► Teams
KQL Database ──┘   (streaming)   │ Propriétés│           Pipeline
                                 └──────────┘           Power Automate
                                                         Notebook
```

### Créer une règle Activator

**Étape 1 : Créer un élément Activator**

1. Dans un workspace Fabric, cliquez sur **+ Nouvel élément**
2. Sélectionnez **Activator** dans la section Real-Time Intelligence
3. Donnez un nom à l'élément

**Étape 2 : Connecter une source de données**

Activator peut recevoir des données depuis :
- Un **Eventstream** Fabric (données en streaming)
- Une **base de données KQL** (données historiques + temps réel)
- Un tableau de bord **Real-Time Dashboard** (via les alertes visuelles)

**Étape 3 : Définir les objets et propriétés**

Après la connexion à la source, définissez comment les données sont mappées sur des objets :
- Sélectionnez la colonne qui identifie l'objet (ex : `sensor_id`)
- Mappez les colonnes sur les propriétés de l'objet

**Étape 4 : Créer une règle**

1. Sélectionnez une propriété (ex : `temperature`)
2. Définissez la condition : **Est supérieur à** `80`
3. Choisissez l'action : **Envoyer un email**
4. Configurez les destinataires et le contenu du message

**Étape 5 : Activer la règle**

Cliquez sur **Activer** pour que la règle commence à surveiller le flux de données.

### Actions disponibles dans Activator

| Type d'action | Description |
|---------------|-------------|
| **Email** | Envoyer un email personnalisé avec les valeurs de l'événement |
| **Teams** | Envoyer une notification dans un canal Microsoft Teams |
| **Pipeline Fabric** | Déclencher l'exécution d'un pipeline de données |
| **Notebook Fabric** | Exécuter un notebook Spark |
| **Power Automate** | Lancer un flux Power Automate pour des actions complexes |
| **Alert visuelle** | Afficher une alerte dans un tableau de bord Real-Time |

### Exemples de règles Activator avancées

**Règle basée sur un pattern (répétition) :**
```
Condition : La valeur de "pipeline_status" est "Failed"
Pattern : 3 fois consécutives
Action : Envoyer un email d'escalade au responsable
```

**Règle basée sur une requête KQL :**
```kql
-- Requête KQL pour détecter une anomalie
SensorData
| where timestamp > ago(5m)
| summarize avg_temp = avg(temperature) by sensor_id
| where avg_temp > 75
```

## 7. Exercice pratique — Surveiller des activités dans le Monitor Hub

### Objectif

Créer des activités Fabric (dataflow et notebook) et les surveiller dans le Monitor Hub, en explorant les filtres, l'historique et les détails des exécutions.

### Étapes

**Partie 1 : Créer les éléments**

1. Connectez-vous à [https://app.fabric.microsoft.com](https://app.fabric.microsoft.com)
2. Créez un workspace avec une capacité Fabric (Trial, Premium ou Fabric)
3. Dans le workspace, créez un **Lakehouse** (laissez les schemas activés)

**Partie 2 : Créer et surveiller un Dataflow**

1. Sur la page d'accueil du lakehouse, sélectionnez **Obtenir des données** → **Nouveau Dataflow Gen2**
2. Nommez le dataflow `Get Product Data` et cliquez sur **Créer**
3. Dans le concepteur de dataflow, sélectionnez **Importer depuis un fichier CSV/Texte**
4. Connectez-vous au fichier CSV : `https://raw.githubusercontent.com/MicrosoftLearning/dp-data/main/products.csv` (authentification anonyme)
5. Utilisez **Enregistrer et exécuter** pour sauvegarder et lancer le dataflow
6. Dans la barre de navigation gauche, cliquez sur **Monitor**
7. Observez le dataflow en cours d'exécution dans le Monitor Hub
8. Attendez que le statut passe à **Réussi**

**Partie 3 : Créer et surveiller un Notebook Spark**

1. Dans le workspace, créez un **Notebook**
2. Dans le notebook, ajoutez le lakehouse comme source de données
3. Chargez la table `products` avec **Charger les données** → **Spark**
4. Exécutez toutes les cellules avec **Exécuter tout**
5. Retournez dans le Monitor Hub et observez l'activité du notebook

**Partie 4 : Explorer l'historique**

1. Relancez le dataflow depuis le workspace
2. Dans le Monitor Hub, sélectionnez **...** → **Exécutions historiques** sur le dataflow
3. Observez les deux exécutions avec leurs durées et statuts
4. Cliquez sur **Afficher les détails** sur une exécution pour explorer les métadonnées

**Partie 5 : Utiliser les filtres**

1. Dans le Monitor Hub, cliquez sur **Filtrer**
2. Appliquez les filtres : Statut = **Réussi**, Type = **Dataflow Gen2**
3. Observez que seuls les dataflows réussis sont affichés
4. Personnalisez les colonnes avec **Options de colonnes**

**Nettoyage :** Supprimez le workspace créé pour l'exercice.

## 8. Troubleshooting courant

### Erreur : "Pipeline failed - Source connection timeout"

**Symptôme :** Un pipeline de données échoue avec une erreur de timeout sur la connexion à la source.

**Investigation via le Monitor Hub :**
1. Ouvrez les détails de l'exécution du pipeline
2. Identifiez l'activité qui a échoué (ex : "Copy_From_SQL")
3. Lisez le message d'erreur complet

**Solutions possibles :**
- Vérifier que la source de données est accessible
- Augmenter le timeout dans les paramètres de l'activité de copie
- Vérifier les règles de pare-feu réseau

### Erreur : "Notebook execution failed - Out of Memory"

**Symptôme :** Un notebook Spark échoue avec une erreur "OutOfMemoryError" ou "GC overhead limit exceeded".

**Investigation :**
1. Dans le Monitor Hub, ouvrez les détails de l'exécution du notebook
2. Cliquez sur le lien vers l'interface Spark (Spark UI)
3. Dans l'onglet **Executors**, vérifiez l'utilisation de la mémoire

**Solutions possibles :**
```python
# Optimisation : partitionner les données pour réduire la mémoire par partition
df = df.repartition(100)  # Augmenter le nombre de partitions

# Libérer les DataFrames non utilisés
df_temp.unpersist()

# Utiliser des types de données optimisés
from pyspark.sql.types import IntegerType
df = df.withColumn("id", df["id"].cast(IntegerType()))
```

### Erreur : "Dataflow refresh failed - Evaluation kind was Folding"

**Symptôme :** Un dataflow Gen2 échoue avec une erreur liée au "folding" des requêtes.

**Diagnostic :**
1. Dans les détails du dataflow, identifiez la table qui a échoué
2. Vérifiez si la source de données supporte le query folding

**Solution :**
- Dans Power Query, désactivez le query folding pour les étapes problématiques
- Ou simplifiez les transformations pour qu'elles soient compatibles avec la source

C) Une méthode de chiffrement des données en transit
D) Un processus de nettoyage automatique des anciens logs

**Réponse correcte : B**
*Le throttling se produit lorsque la capacité Fabric est surexploitée (consommation de CU supérieure à l'allocation). Les nouvelles opérations sont alors mises en file d'attente ou ralenties pour protéger les opérations critiques en cours.*

---

**Question 5 :** Dans Microsoft Fabric Activator, qu'est-ce qu'une "règle" (Rule) ?

A) Une politique de gouvernance des données
B) Une condition qui, lorsqu'elle est remplie, déclenche automatiquement une action définie
C) Un filtre de sécurité sur les colonnes d'un lakehouse
D) Un script de validation des données

**Réponse correcte : B**
*Dans Activator, une règle combine une condition (ex : temperature > 80) avec une action à déclencher (ex : envoyer un email). Lorsque la condition est remplie sur les données en streaming, l'action est exécutée automatiquement.*

## Résumé

Dans ce module, vous avez découvert comment surveiller les activités dans Microsoft Fabric :

- **Les activités à surveiller** : pipelines de données, dataflows Gen2, actualisations de modèles sémantiques, notebooks Spark et Eventstreams — chacun avec ses métriques spécifiques.
- **Le Monitor Hub** est le tableau de bord central de surveillance qui regroupe toutes les activités Fabric. Il permet d'afficher les détails des exécutions, consulter l'historique et identifier les erreurs.
- **Les filtres et options de colonnes** permettent de cibler les informations pertinentes dans un environnement avec de nombreux éléments.
- **La Capacity Metrics App** mesure la consommation de CU et aide à identifier les phénomènes de throttling et les workloads les plus coûteux.
- **Microsoft Fabric Activator** permet de déclencher automatiquement des actions (emails, pipelines, notebooks) en réponse à des conditions détectées dans des données en streaming, via les concepts d'Événements, Objets, Propriétés et Règles.
- Les **meilleures pratiques** de surveillance incluent : définir des métriques de référence, surveiller en continu, consulter régulièrement les historiques d'exécution, et agir rapidement sur les anomalies détectées.
